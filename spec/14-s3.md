# S3 gateway

The S3 model and API, and S3 over RDMA. Part of the hyperstor design; sections keep their numbers across documents, so `§N` in one document is the same section everywhere (see [README.md](README.md)).

## 14. S3 gateway (D36)

### 14.1 Model

- `hyperstor-s3` is stateless. Any number run behind a load balancer;
  each is a client of the object layer and of `hyperstor-kv`.
- **Buckets** belong to a tenant (a glidex project, or an account when
  standalone). Each has a data pool and an index pool, chosen at
  creation (D198): data on bulk classes, replicated until EC pools are
  built (D191), the index on flash. Bucket names are one namespace per
  cluster, kept as keys in `hyperstor-kv`'s root range (D197).
- **Bucket index** in `hyperstor-kv`: one key per object (and per
  version, with versioning), holding size, checksum, ETag, content type,
  user metadata and the object's data location. Listing is a range scan
  of these keys, so `ListObjectsV2` with a prefix and delimiter is
  ordered and paginated without a separate index.
- **Object data** goes to `s3` chunk objects named
  `(bucket id, object id, part, chunk_index)` and placed by hash, so a
  large object is spread over many PGs and read in parallel. Objects
  up to 64 KiB are stored inline in their index entry.
- **Writes** go to new object ids, never over existing data. A PUT writes
  the data, then inserts the index entry in one atomic operation on its
  range, which is the moment the object becomes visible. Conditional
  writes add an assertion on the entry's key to that operation (D194).
- **Collection** (D192): the operation that overwrites or deletes an
  entry also writes, in the same range, a record naming the old
  object's chunks. A collector deletes the chunks, then the record.
  Copy object copies the data (D193).
  The data never changes after it is written, so full-stripe EC writes
  (09-replication.md §8.6) apply to nearly every byte.
- **Multipart upload:** each part is written as its own chunk objects;
  completion is one atomic operation on the range that writes the index
  entry naming the parts in order. Nothing is copied.

### 14.2 API

- **First milestone:** PUT, GET (with ranges), HEAD, DELETE and
  multi-object delete, `ListObjectsV2`, `ListBuckets`, create and
  delete bucket, multipart upload (create, upload part, complete, abort,
  list), copy object, conditional requests (`If-Match`,
  `If-None-Match`, including conditional writes), and the checksum
  headers (CRC32C is stored natively, others computed on write).
- **Authentication:** SigV4 (headers and presigned URLs). Access keys
  belong to a tenant. The map service issues and revokes them
  (`hyperstorctl s3 key`, and mgmt's UI and glidex through the cluster
  API); they are secrets never shown again after creation
  (credentials.md). The map service keeps them with their secrets
  encrypted under its cluster key; gateways fetch them over mutual TLS
  with an `s3` certificate and cache them in memory, so S3 doesn't stop
  while mgmt or the map service is down (D231, amending D197). In
  glidex, bucket access is checked with Cedar.
- **Buckets** are made with CreateBucket by any key, for its tenant,
  on the cluster's default S3 pools or a named placement that
  `LocationConstraint` chooses (D232).
- **ETags** are MD5s as S3 computes them, multipart ones from the
  parts' MD5s (D196).
- **Addressing:** path-style (`/bucket/key`) first, then
  virtual-hosted (`bucket.endpoint/key`, with a wildcard DNS name and
  certificate) (D199).
- **Process:** the gateway runs on hyper and rustls over tokio and hands
  chunks to the client library's reactors (D195).
  It runs on any joined host with its own `s3` identity:
  `hyperstor-install --s3`, or `--role s3` alone (D233).
- **Later:** versioning, lifecycle rules, object lock, bucket policies,
  event notifications. Replication between clusters is `hyperstor-sync`
  (D64, 21-federation.md §25.3); a bucket index spanning clusters is the
  global namespace (D65, 21-federation.md §25.4).
- TLS on the S3 endpoint always, with the site's certificate.

### 14.3 S3 over RDMA

- A client using cuObject or hipObject sends an ordinary S3 request with
  an `x-amz-rdma-token` header describing its buffer (GPU or host
  memory) for RDMA.
- **GET:** the gateway resolves the object, then asks the storage nodes
  holding its chunks to write each chunk's range into the client's
  buffer by RDMA, at the right offset. When all have completed, it
  answers the HTTP request with `x-amz-rdma-reply` and no body. The data
  doesn't pass through the gateway.
- **PUT** and **upload part:** the same in the other direction; storage
  nodes read the data from the client's buffer as they write it.
- **Transport:** the token names a DC target on the client's NIC, which
  any storage node can reach without a connection of its own. The
  milestone therefore includes DC queue pairs on mlx5 devices
  (13-protocol.md §13.2). Requests without a token, or from clients not reachable by
  RDMA, are served over HTTP as usual.
- **Authorization** is the same as for the HTTP request: the token only
  says where the data goes; the signed request says what may be read or
  written.

### 14.5 Starting sooner (settled 2026-11-01)

Points 128–137 of 05-decision-log.md, settled as D191–D199, start S3
before transactions across ranges (HS11b) and before EC pools (HS7):
the gateway needs `hyperstor-kv`'s ranges (HS11), and its buckets use
replicated pools until EC pools are built. §14.1 and §14.2 above
include them.

### 14.6 Layout

Decided while building HS12 (I262, I264), open for review. Stages 1 and
2 of §14.7 are built (2026-11-04).

- **A bucket is a table** of store 1 (25-kv-ranges.md §28.3). The table
  record's appended bytes hold the bucket's own record: a format byte,
  the tenant and the creation time. Why: one atomic operation on the
  root makes a bucket (D197), and ListBuckets is one ordered scan.
- **Rows:** `o` + object name for an object; `u` + the time it expires
  (u64 seconds, big-endian) + upload id (u128) for an upload under way. Why
  a prefix byte: object names may hold any byte, and uploads must sort
  by age apart from them.
- **An object's row** holds column `l` (its latest version, the index
  entry of §14.1) and, while an upload of that name is under way,
  `p` + upload id (the upload, naming its `u` row) and `p` + upload id
  + part number (each part uploaded). Versioning will add a column per
  version.
- **Index entry:** a format byte, the time written (ms), size, the ETag
  (MD5 and part count), CRC32C of the body, content type, user metadata,
  then the data: inline bytes (64 KiB at most), or the object id, the
  chunk size and the parts (number and size).
- **Chunks:** `s3` objects of the data pool named bucket id (u64),
  object id (u128), part (u32) and chunk index (u32), all big-endian;
  4 MiB each, the last one cut to its size. A single PUT is part 0.
- **Every upload is recorded before its chunks are written**, so a
  gateway that dies in the middle leaves a record, not chunks nothing
  names. A PUT larger than the inline limit:
  1. puts row `u` + expiry + id (naming the object row), then column
     `p` + id in the object's row;
  2. writes the chunks;
  3. in one batch on the object's row, asserts `p` + id, deletes it,
     puts `l`, and queues the old version's chunks for deletion (D192),
     due in 15 minutes;
  4. deletes the `u` row.

  Multipart uploads are the same, with parts as columns until the
  completion's batch (step 3). An abort is that batch without `l`, its
  parts' chunks queued instead.
- **Uploads expire:** a PUT a day after it starts, a multipart upload
  after 7 days (MinIO drops them after a day; S3 keeps them until a
  lifecycle rule says). Every hour a gateway looks at each bucket's `u`
  rows that have expired. If the object's row still has `p` + id, one
  batch asserts it, deletes it and its parts and queues their chunks;
  then the `u` row goes. Why this is safe: completing and cleaning up
  both assert `p` + id in one row, so exactly one of them happens, and
  gateways refuse to complete or add to an upload within an hour of its
  expiry, so their clocks may differ by up to an hour.
- **Deletion queue entries** name a part's chunks as a series (a prefix
  and a count), so deleting a 5 TiB object queues one entry per part,
  not one name per chunk.
- **Replaced chunks linger** 15 minutes before they are deleted (an
  overwrite or a DELETE; 25-kv-ranges.md §28.6), so a GET that read the
  old entry still reads its chunks, as S3 lets it. A GET slower than
  that fails part-way. Built in stage 2 (I264), open for review.
- **A PUT writes four chunks at once**, the gateway's reactor moving on
  while they are written. Built in stage 2 (I264).

### 14.7 Stages

| Stage | What | Tested by |
|---|---|---|
| 1 | The object layer, `hyperstor-s3`'s library on the client's reactor: buckets (create with pools, list, delete when empty), PUT, GET with a range, HEAD, DELETE, ListObjectsV2 with prefix, delimiter and pages, uploads left behind | A randomized test against a model on a cluster, with gateways and nodes killed; every chunk not in the model is deleted |

### 14.8 Host checks

- **G56. A tunnel keeps what SigV4 and the gateway need.** Through a
  Cloudflare Tunnel (`cloudflared`, with the gateway as an HTTPS origin
  checked against the cluster's root), a plain PUT reaches the gateway
  with its `Content-Length` (the gateway answers 411 without one, but for
  `aws-chunked` bodies), the `Host` header is the public name the client
  signed, and `aws-chunked` bodies arrive unchanged. Check with boto3
  through a tunnel to a pilot gateway: PUTs of 1 KiB, 8 MiB and 90 MiB,
  signed and unsigned. Until then, the installation guide's tunnel
  section is a proposal.
