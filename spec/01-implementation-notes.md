## Engine (HS0)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I1 | **A device is split into shards, one per reactor**, each with its own log ring, allocator and index; a PG lives in one shard. | No locks or cross-core traffic on the I/O path (08-engine.md §6.1), and recovery runs per shard in parallel. | Load across shards depends on PG placement; moving a PG between shards of one device (a local backfill) is not built yet. |
| I2 | **Commits are batch-synchronous (group commit).** `Shard::commit` resolves a batch of lists, writes new data extents and the log record together, flushes once, and returns. The reactor calls it with everything that arrived since its last pass. | The simplest design that is correct and still amortizes the flush over a batch. | The reactor waits during the flush. On NVMe with power-loss protection a flush costs microseconds; on drives without it, milliseconds. A completion-driven engine (submit, return to polling, finish on completion) is the next step once the reactor carries real traffic (HS1). |
| I3 | **The index lives in memory; a checkpoint is the whole index serialized** into freshly allocated extents, named by the shard's superblock. The on-device copy-on-write B+tree of 08-engine.md §7.1 is deferred. | Small and easy to verify; recovery is load plus log replay. | Open: 05-decision-log.md, point 5 (fuzzy checkpoint now, paged index next). |
| I4 | **One flush per commit round**, not a flush of new data and then of the log record. Recovery checks the last commit group's new data against its checksums, and drops a record whose data didn't reach the media, with everything after it. Only blocks the replayed index still maps to the same place are checked. | Halves flushes per commit. A dropped record was never acknowledged: rounds are sequential, so only the last group can be incomplete. | Correct only while rounds don't overlap. If commits are pipelined later, recovery must check every group not known to be flushed. |
| I5 | **The log's checksums are seeded with a random salt that changes every time a shard is opened**, and opening always ends with a checkpoint under the new salt. | Stale blocks from an earlier pass of the ring or an earlier format, and tenant data that happens to look like a record (deferred writes carry tenant bytes into the log), never pass as records. | The salt is 32 bits and CRC32C is not a MAC: forging a record still needs the salt guessed, and a crash at the right moment. A keyed MAC per record would close it at some CPU cost. |
| I6 | **Revisions come from a shard-wide counter** and are never reused, even across delete and recreate. | Compare-and-set on revisions can't suffer ABA. | — |
| I7 | **A write is never deferred onto blocks allocated in the same round.** | Recovery's data check (I4) compares those blocks with the checksums their `Map` logged; an in-place write in the same round would contradict it and drop an acknowledged group. | — |
| I8 | **Data offsets and lengths are 4 KiB aligned.** | Matches the device and the checksum granularity. | S3 objects and file tails need padding by the caller (the S3 gateway, the filesystem client), with the logical size kept separately (`Truncate`). |
| I9 | **`Truncate` keeps the bytes of a partial last block** past the new size. | Avoids a read-modify-write. | A later extension shows the old bytes. Filesystem semantics need zeroing there (00-filesystem.md). |
| I10 | **Assertions are checked against the object before the list**, not at their position in it. | Simple to reason about: a list is validated whole, then applied, so a refused list never leaves a trace. | — |
| I11 | **NVMe passthrough (`uring_cmd`) is not implemented yet.** The block back end (io_uring, `O_DIRECT`) serves every device. | The development host has one NVMe device and it holds the root filesystem; passthrough needs a namespace of its own. | G5 is only half run (02-benchmarks.md); passthrough and its benchmark need a test host with a spare namespace. |
| I12 | **Write data is copied once** into an aligned buffer before it goes to the device. | Network buffers aren't aligned yet. | Zero copy comes with registered buffers shared by the reactor's network and disk paths (08-engine.md §6.2). |
| I14 | **The deferral threshold is a per-shard setting** (`Shard::set_defer_max`). Storage nodes turn deferral off unless told the device is a hard disk (`hyperstord --hdd`). | On flash, deferral writes small overwrites twice; redirecting them reached 1.6× the 4 KiB write throughput on dev-1 (02-benchmarks.md). | **Settled: D38.** |
| I13 | **A checkpoint must fit in 200 extents** (named in one superblock). | Keeps the superblock one block. | On a badly fragmented shard a checkpoint can fail with `NoSpace`; a chained extent list removes the limit. |

### Bugs the tests found

Across the sessions, tests found these bugs before anything else did:

1. Engine: `[Delete, Touch]` deleted the object (crash test).
2. Engine: recovery checked freed and reused blocks, dropping an
   acknowledged group (crash test).
3. Placement: positional EC placement moved twice the necessary shards
   (movement test, I16).
4. Daemon: a write could be acknowledged without a target that had just
   finished backfilling (cluster test, 2 in 25 runs; I26).
5. Reactor: a task that yields in a loop starved all I/O, because each
   pass ran ready tasks until none were left (the returning-node cluster
   test hung). Each pass now runs only the tasks ready when it starts;
   `a_yielding_task_does_not_starve_io` guards it.

7. Engine: a deferred write lost when an absorb moved its block in the
   same round, and a deferred write replayed onto a remapped block
   (crash test, once checkpoints were paged; I149).

Found in review while designing leases:

6. Map: a PG whose acting members were all down was reset to an empty
   acting set, so when the members returned, backfill from the empty
   primary would have wiped them. Such a PG now stays down with its acting
   set until a member returns (`a_pg_whose_copies_are_all_down_stays_down`).

### Details of the engine bugs

The randomized crash test (`crates/hyperstor-engine/tests/crash.rs`) found
two engine bugs before any other test did:

1. `[Delete, Touch]` in one list deleted the object; `Touch` must recreate
   it. Fixed by tracking whether the object is alive through the list.
2. Recovery's data check (I4) looked at blocks that a later part of the
   same group had freed. Those can legitimately be reused (by the next
   round's data, or by the checkpoint an earlier recovery wrote), so an
   acknowledged group was dropped. Fixed by checking only blocks the
   replayed index still references.

| # | Decision | Why | To discuss |
|---|---|---|---|
| I15 | **The placement hashes are spelled out** (SplitMix64 mixing, FNV-1a for names), with pinned test values, instead of `std`'s hashers. | Every node and client must compute the same placement from the same map, across Rust releases and architectures. | Changing them is a format change: it would move every PG. |
| I16 | **EC shard positions are kept in the PG table, not recomputed.** `place` chooses the members; `assign_positions` keeps each surviving member at its shard index and fills vacated positions with new members. | A stateless positional choice (CRUSH-style `indep`, tried first) moved 2.1× the necessary shards when a device was removed, because changed positions collide with others. | I17 | **Weights are hierarchical**: a device's weight counts for its host and rack, and choices go rack, host, device. | Load follows capacity at every level, which is what keeps devices evenly full. | Removing one device moves 1.44× the theoretical minimum of PGs in the test (its host's share drops, so some PGs that used the host's other devices move too). ## Failure handling (HS2, first part)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I25 | **Liveness by heartbeats to the map service** (every 150 ms from each reactor; a node is down after a timeout, 600 ms in tests and 2 s in the benchmark). Each PG has an `up` set (placement) and an `acting` set (who has every acknowledged write). When a node goes down, `acting` keeps its live members in order, so the new primary is a surviving member that has every acknowledged write. | Writes are acknowledged only when every acting member has them (§8.1), so any surviving member is complete. Keeping order avoids an election. | Detection by the map service only: a node that can reach the map service but not its peers isn't detected (06-metadata.md §4.1 asks peers to report each other; not built). |
| I26 | **Backfill**: the primary resets the target's copy of the PG, then pushes every object whole, each read taken only when no commit is queued and sent on the same connection as live writes. Live writes also go to the target meanwhile (best effort). If any write or push to the target fails, the backfill starts over. When it finishes, the target becomes *required* for every write before the primary waits out in-flight writes to it and reports `BackfillDone`; the map service then adds it to `acting`, and once all of `up` is there, `acting = up`. | Ordering on one connection makes each pushed object exactly the primary's state at that point, with later writes following. Making the target required before reporting closes a race the cluster test found (2 failures in 25 runs before the fix, 0 in 30 after): a write could be acknowledged while its copy to a target that had just joined `acting` failed. | Objects are pushed whole, holes included (reads materialize zeros), so a backfill writes every byte of each chunk; an extent list from the engine would send only what's there. No throttling or priorities yet (09-replication.md §8.5). A node that returns with old data gets a reset and a full copy, not a delta from the PG log (no PG log yet). |
| I27 | **Storage nodes refuse `Repl` and `Push` for PGs they are in neither `acting` nor `up` of**, and for PG epochs they don't have. | A node that is no longer a member must not accept writes. | — |

## Dense maps and fuzzy checkpoints (D43)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I33 | **Fuzzy checkpoints** (08-engine.md §7.3): one starts when a quarter of the log is used; each commit round writes a slice (64 KiB, eight times that once half the log is used); it finishes at once if the log reaches three quarters first. The blob is a stream of objects; a directory, named by the superblock, lists the blob's extents (no limit on how many). Recovery replays from the checkpoint's start over the fuzzy image. | Removes the checkpoint pause (02-benchmarks.md: worst commit 3.8 ms whole, 0.15 ms with 64 KiB slices). Replay over a fuzzy image works because every log record sets state absolutely; the one exception, deferred writes onto blocks a later trim unmapped, is skipped during replay. The crash tests run with 1 KiB slices, so about 400 of each run's crashes land mid-checkpoint; a planted bug (log head at the end instead of the start) fails them at once. | Checkpoints still rewrite the whole index (2 GiB per TiB with dense maps), only spread out. Paged checkpoints (05-decision-log.md, point 5, option B) would write only what changed. |
| I34 | **Dense maps switch by estimated memory**, with hysteresis: to dense when runs cost more than 8 bytes per block of span, back to runs below 60% of that (a contiguous chunk is about 51%). A dense map is only reconsidered after a change of at least an eighth of its span. 32-bit physical blocks: a shard over 16 TiB keeps runs for blocks beyond. | Measured: every chunk was dense after only 5% random overwrites, so dense is the steady state for VM disks; the threshold matters less than first thought. Reconsidering after every write scanned 1,024 slots and made commits 13× slower; the size condition removes that. | — |
| I35 | **Run overhead calibrated to 128 bytes** (was an assumed 96), from the process's growth per run in the aging benchmark. | Decides when a chunk goes dense. | — |
| I36 | **Benchmarks for decisions are a repeatable suite**: `hyperstor-bench decisions` and `redb`, run through `scripts/collect-decision-data.sh`, which records the host; the procedure is the agent skill `.claude/skills/collect-decision-data`. | The owner decides from data; the data must be repeatable, with the host and the exact commands. | — |
| I37 | **`Shard::stats()` is constant-time; index-wide totals are `index_stats()`.** | The decision-data run caught a 3.5× regression in replicated writes: with dense maps, `stats()` walked every block map, and the daemon called it after every commit. | Benchmarks belong in every session for exactly this reason (the skill's step 2). |
| I38 | **Adaptive polling** (`hyperstor_reactor::set_spin`): after activity, a reactor polls (entering the kernel without waiting, so network completions arrive) for the window before sleeping. `hyperstord` defaults to 200 µs (`--spin-us`); everything else to 0. | QD1 latency −15 to −23%, 4-reactor write p99 −80% (02-benchmarks.md, adaptive polling). | The window is a CPU cost at low load; see 05-decision-log.md point 16. |
| I39 | **Peer reports** (D40): every storage reactor pings, every 100 ms, the nodes it shares a PG with, and reports one silent for the peer timeout (`hyperstord --peer-timeout-ms`, default 0.3 s since D48; 1 s before) to the map service; a node reported by two distinct nodes within half the liveness timeout is marked down and gets no lease until the reports stop. | Measured: failover 3.0 → 2.5 s at the default lease, 0.78 → 0.55 s with a 0.5 s lease (02-benchmarks.md, failover). The cluster test fails with peer reports turned off. | "Two distinct nodes" doesn't yet require different failure domains (the cluster file's racks); with one rack per site, any two nodes count. Pings scale with the number of peer nodes, not PGs. |


## Cache pools (D45, first part)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I40 | **A cache pool is a third pool kind** (`pool N name cache copies K` in the cluster file; tag 2 in the map codec). Its acting set is always its up set: no backfill, no stand-ins. A read of an object the shard doesn't have answers `NotFound` rather than zeros. A storage reactor that sees a cache PG at an epoch it hasn't served before deletes everything it holds for that PG, committed before the request goes on. | A node returning with an old copy must not serve it: a write made while it was away went to another node, and placement can hand the PG back. The cluster test writes different data while the holder is down and fails if the old copy is ever read back; it caught that the first version queued the deletes without committing them, so a read on the new epoch still saw the old copy (reads don't pass through the commit queue). | Not built: expiry, eviction under space pressure, least-recently-read tracking. With `copies` > 1, any change of membership empties every copy, including those that stayed; keeping survivors would need a per-PG "last written epoch". The purge costs one delete per object of the PG on the first request after a change. |

## Delta recovery and scrub (HS2)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I57 | **Delta recovery compares content digests instead of replaying a PG log** (09-replication.md §8.3, §8.5). `Shard::digest` hashes (FNV-1a, 64 bits) an object's size in blocks, each mapped block's number and CRC, its attributes and its key–value table, all from the index; a block of zeros counts as a hole. A `Digests` request returns a member's `(key, digest)` list of a PG, in the frame's payload. Backfill asks the target for it instead of resetting it, then pushes objects whose digests differ and deletes for keys the primary lacks, each read and sent after the queue drains, on the connection live writes use. A target that doesn't know `Digests` (a rolling upgrade, 15-operations.md §18.4) answers "unsupported request" and gets a reset and a whole refill, as before. | No new persisted state, so nothing new to crash-test, trim or keep in step with the data; it also covers a member that was away longer than any log would reach, and copies that diverged for any reason. Measured: a node that returns after 1% of a 256 MiB volume changed is sent 2 MiB instead of 192 MiB, and is clean in 0.14–0.18 s instead of 0.46–0.48 s (02-benchmarks.md, rejoin). The cluster test fails if every object is pushed; another restarts a node as an old one and checks it is refilled whole; a randomized test (writes, node stops and restarts against a model; 23 seeds passed) fails on all three default seeds if changed objects aren't pushed. | Cost grows with the objects in a PG, not with what was missed: both sides walk the PG's index entries (in memory today; pages of the B+tree after D43). A PG log would make a short absence cost only its writes, and remains the way to go if PGs grow to millions of objects. 64 bits of FNV over CRC32Cs can collide in principle; a collision leaves one stale object until a write or a deep scrub finds it. |
| I58 | **Light scrub repairs by majority** (09-replication.md §8.5). Each primary compares every acting member's digests of its clean PGs once per `--scrub-hours` (default 24, 0: off), one PG at a time spread evenly over the interval, looks again at keys that differ after 200 ms (a write in flight isn't damage), and for a difference that persists pushes its copy (or a delete) to the members that differ when a majority of copies agree with it; otherwise it counts the object as unresolved and logs it. Counted in `hyperstor_scrub_objects_total`. | Digests can't say which copy is right; a majority can, and two copies can't decide. Pushing from the primary reuses backfill's ordered push, so a repair can't overtake a live write. The cluster test overwrites a replica behind the primary's back and fails if the repair isn't sent. | When the primary is the copy outvoted, nothing is repaired: the primary would need to pull, or hand primacy to a member that agrees. Light scrub is paced only by spreading PGs over the interval; it reads no data, so it has no byte rate. |
| I59 | **(Superseded by I69.)** **A pushed copy's size is rounded up to whole blocks**: `Push` carries the data from offset 0 to the size rounded up, and no size. The digest therefore compares sizes in blocks. | Client writes are whole blocks today, so the sizes agree; comparing byte sizes would make every pushed copy of an object with a partial last block differ forever. | Byte-exact sizes (S3 objects, files) need `Push` to carry the size and the target to truncate; to do with the S3 gateway (HS12). |
| I60 | **Deep scrub is every seventh scrub pass, and the first** (09-replication.md §8.5: light daily, deep weekly). `Digests` takes a `deep` flag: each member, in a task of its own so replication on that connection goes on, reads every object of the PG (the engine checks each block's CRC) at most 64 MiB/s per device, pausing between objects, and marks objects that fail. A marked object's digest is `DAMAGED` (0, never a healthy digest) until a push replaces it; light scrub's majority rule then repairs it, and a damaged copy never counts toward a majority (each gets a value of its own). | No new flag or schedule to configure, and the repair path is light scrub's. The cluster test flips a byte of a replica's data under the engine, where the index (and the digest) still look right, and fails if deep reads don't mark it. | A damaged primary is reported, not repaired (as in I58), and a client read of it fails meanwhile instead of falling back to a replica. Its cost on I/O (02-benchmarks.md, deep scrub against I/O), with a deep pass every 3.5 s: 4–6% of throughput and up to +45% p99 for QD32 reads. Reading in 256 KiB pieces to bound each synchronous read made it worse (−12% throughput), so the cost is the extra device and CPU work, not one long stall; deep scrub should run in the `bulk` class (D46) once it exists, at a rate measured on dedicated drives. **Found while testing:** damage in the data of a device's *last* commit group isn't silent: on reopen, recovery checks that group's data and drops the record as torn (I4), so the object is missing, and light scrub restores it. |
| I61 | **Peering by digests** (09-replication.md §8.4). Before a primary serves a PG at a new epoch, the first request to it compares every acting member's digests with its own and pushes its copy (or a delete) where they differ; requests arriving meanwhile wait (up to 2 s, then `Unavailable`, and the client retries). A member that doesn't know `Digests` (rolling upgrade) is taken to agree, as before; an object whose own copy is damaged is left to scrub. Counted in `hyperstor_scrub_objects_total{kind="peering"}`. | Every acknowledged write is on every acting member, so the new primary's copy has them all; what differs can only be a write that never completed, and making every copy the primary's means a read can't see it and later not see it. The cluster test diverges the third copy and kills the primary, and fails if peering pushes nothing. | Not the log-based peering of §8.4: the new primary's copy wins even where another member holds a later, unacknowledged write, which §8.4 would keep ("the longest log"). Both are allowed; this one never keeps a write the client wasn't told about. A read served by the old primary *before* its write was replicated could still be undone (reads don't wait for replication), which only replica-granted read leases or reading after commit on all members would close. Each failover pays one digest round trip per PG on its first request (02-benchmarks.md, failover). |

## Volume leases and the blocklist (HS1, HS2)

| # | Decision | Why | To discuss |
|---|---|---|---|
| I74 | **A lease is the header's `lease` attribute plus an expiry in the primary's memory.** Attaching writes the holder (instance, mode) to the header through the primary, as an operation list does; a renewal writes nothing and sets the expiry to 4 s from when it arrives (D75).
