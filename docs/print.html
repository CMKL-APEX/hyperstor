Hyperstor

Introduction

Hyperstor is a sharded, distributed storage system written in Rust. It stores data on many storage nodes, keeps two or three copies of every piece, and keeps serving reads and writes when a node fails. It is built for glidex clusters and also runs on its own.

Early implementation. Hyperstor is not ready for production data. Today it provides replicated storage over TCP, used through a Rust client library or, for testing, as Linux block devices through ublk, with failure detection and recovery, snapshots and clones. There is no front end for virtual machines or remote hosts yet, and the data path between clients and storage nodes has no authentication or encryption (the cluster API and the map service’s members use mutual TLS). See Status for what is built and what comes next.

What it does today

  • Replicated pools. Data is split into chunks, and each chunk is written to two or three storage nodes in different failure domains (devices, hosts or racks). A write returns once every copy has it.
  • Its own storage engine. Each storage device is driven directly through Linux io_uring, with checksums on every 4 KiB block and crash recovery.
  • Failure handling. The map service notices when a node stops answering, moves its work to other nodes, and refills a node when it comes back with only what it missed. A short reboot moves no data. A failed device, or a replica too slow to answer, is replaced at once. A background scrub compares the copies and repairs one that is damaged or differs.
  • A replicated map service. Three or five members keep the cluster map with Raft, so losing one doesn’t stop the cluster.
  • Volumes with one writer at a time: a client attaches a volume by holding its lease, and one that dies is fenced off when another takes the volume over.
  • Snapshots and clones. Crash-consistent snapshots of one volume or of a group at one instant, instant clones and rollbacks, and snapshot deletion that moves no data.
  • Block devices for testing. hyperstor-ublk serves a volume as /dev/ublkbN, for mkfs, mount and fio.
  • A client library for Rust programs to read and write volumes, and hyperstorctl and hyperstor-install for administrators.

What is planned

Block volumes for virtual machines (vhost-user-blk), NVMe over TCP and RDMA, a host-wide read cache, erasure coding, GPU-direct storage, an S3 gateway and a distributed filesystem, all on the same object layer. The Status page lists the milestones.

Quick start

To install a trial cluster as system services in one command instead, see Installing a trial cluster.

This starts a cluster of three storage nodes and a map service on one Linux machine, writes to it, and shows a node failure. It needs the build requirements and about 3 GiB of free disk space.

1. Build

git clone https://github.com/CMKL-APEX/hyperstor
cd hyperstor
cargo build --release

The binaries are in target/release/: hyperstor-meta (the map service), hyperstord (a storage node) and hyperstor-bench (a load generator).

2. Describe the cluster

The cluster file lists the storage nodes, the address each one listens on, and the pools:

cat > cluster.txt <<'END'
cluster 1
node 0 rack 0 127.0.0.1:19100
node 1 rack 0 127.0.0.1:19200
node 2 rack 0 127.0.0.1:19300
pool 1 vol replicated size 3 min 2 pgs 128 chunk 4194304 domain host
END

Pool 1 keeps three copies of every 4 MiB chunk, each on a different node, and accepts writes while at least two copies are reachable.

3. Start the services

target/release/hyperstor-meta --listen 127.0.0.1:19000 --cluster cluster.txt &
for n in 0 1 2; do
  target/release/hyperstord --node $n --meta 127.0.0.1:19000 \
    --shard 127.0.0.1:19$((n+1))00=/var/tmp/hs-n$n.img:1 &
done

Each storage node creates a 1 GiB file as its device and formats it on first start.

4. Write and read

hyperstor-bench remote connects as a client, writes and reads for a few seconds, and prints the throughput as table rows:

HS_BENCH_SECS=2 target/release/hyperstor-bench remote 127.0.0.1:19000

5. Fail a node

Stop one storage node and run the load again:

kill %2          # the first hyperstord
sleep 5
HS_BENCH_SECS=2 target/release/hyperstor-bench remote 127.0.0.1:19000

Within a second of the node stopping, the map service marks it down and the other nodes take over as primaries of its placement groups; writes then go on with two copies. Start the node again with the same command and it is refilled with the writes it missed (see Failures and recovery).

6. Clean up

kill $(jobs -p)
rm /var/tmp/hs-n?.img cluster.txt

Concepts

Processes

ProcessRuns onDoes
hyperstor-metathree or five machines (one for a trial), replicated with RaftKeeps the cluster map, notices failed nodes, hands out map leases
hyperstordevery storage nodeStores data on local devices and serves reads and writes

The cluster map

The map describes the whole cluster: its nodes, their devices, the pools and where each placement group lives. Every node and client holds a copy and computes data locations from it, so no lookup is needed per I/O. Each change to the map has a new epoch number; a node or client with an older map is told so and fetches the new one.

Nodes, devices and shards

A node is one hyperstord process. It drives one or more devices: files or block devices, each served by its own thread (a reactor, pinned to a CPU if you choose) that listens on its own TCP port. In the cluster file, each address listed for a node is one device.

Pools

A pool is a set of data with one protection rule:

  • size: how many copies of each chunk (2 or 3);
  • min: how many copies must be reachable to accept a write;
  • failure domain: what the copies must not share: a device, a host or a rack;
  • chunk size: how volumes in the pool are cut into chunks.

Placement groups

A pool is divided into a fixed number of placement groups (PGs), a power of two. Each chunk belongs to one PG, by a hash of its name, and each PG is stored on size devices, its acting set. The first device of the acting set is the PG’s primary: clients send it reads and writes, and it forwards writes to the other copies. When a node fails, only the PGs it held move.

Volumes

A volume is a sparse range of bytes in a pool, with a 128-bit id, a size and a name. The cluster keeps a header for each volume, and its chunks are created as they are written: blocks never written read as zeros. Offsets and lengths are multiples of 4 KiB.

Snapshots and clones

A snapshot keeps a volume as it was at one instant. Taking one only moves the volume’s epoch on: later writes go to new versions of the chunks, tagged with the new epoch, and the snapshot reads the versions up to its own. So a snapshot copies nothing, and a clone is a new volume that reads through its snapshot’s versions until it writes its own. A consistency group snapshots several volumes at one instant.

Volume leases and the blocklist

One client at a time attaches a volume, by holding its lease, which it renews every second. To take a volume from a client that died or is cut off, another client waits for the lease to run out and blocklists the old one: every storage node refuses it from then on. So a volume never has two writers.

Map leases

A storage node may act as a primary only while it holds a current map lease from the map service, renewed by its heartbeats. A node cut off from the map service stops serving before the map service gives its PGs to other nodes, so two nodes never both accept writes for one PG.

Down and out

A node that stops answering is down: its PGs go on with the other copies, and nothing is copied, so a reboot moves no data. A device that is out, because its node has been down for ten minutes, it failed, or an administrator took it out, gets no placement, and its PGs are copied to other devices.

Using Hyperstor

Today a program stores data in Hyperstor through the Rust client library, hyperstor-client. For testing, a volume can also be served as a Linux block device with hyperstor-ublk, and used through any filesystem or tool. The client library

hyperstor-client is a Rust crate. It holds a copy of the cluster map, keeps connections to storage nodes, splits each request at chunk boundaries, sends the pieces in parallel to their primaries, and retries when the map changes.

Adding the dependency

The crate is not on crates.io yet. Depend on it from git, with the reactor it runs on:

[dependencies]
hyperstor-client = { git = "https://github.com/CMKL-APEX/hyperstor" }
hyperstor-reactor = { git = "https://github.com/CMKL-APEX/hyperstor" }

Pin a revision (rev = "...") while the API is changing.

The reactor

The client runs on Hyperstor’s own io_uring reactor, not on tokio or another async runtime. hyperstor_reactor::block_on runs a future, and everything it spawns, on the current thread. A Client belongs to the thread that created it (it is not Send); use one client per thread.

Writing and reading

use hyperstor_client::Client;
use hyperstor_reactor::block_on;

fn main() {
    let meta = "127.0.0.1:19000".parse().unwrap();
    block_on(async move {
        // The second argument identifies this client to the cluster.
        let client = Client::connect(meta, 1).await.expect("connect");

        let pool = 1;
        let volume: u128 = 0x1234;
        let data = vec![0xab; 64 * 1024];

        // Offsets and lengths are multiples of 4096.
        client.write(pool, volume, 0, data.clone()).await.expect("write");
        let back = client.read(pool, volume, 0, 64 * 1024).await.expect("read");
        assert_eq!(back, data);
    });
}
  • Client::connect(meta, id) fetches the map from the map service at meta. With several map service members, use Client::connect_members(vec![a, b, c], id): any member serves the map, and requests only the leader answers follow its redirects.
  • write(pool, volume, offset, data) returns once every reachable copy of every chunk touched has the data (see guarantees).
  • read(pool, volume, offset, len) returns len bytes; blocks never written are zeros.
  • map() returns the client’s current copy of the cluster map, for example to list pools.

The full API is in the client API reference.

Volumes

write and read above address a lineage directly: nothing records that it exists, and nothing stops two programs from writing to it at once. Programs that share a cluster use volumes, which the cluster keeps a record of, and which one client at a time attaches:

#![allow(unused)]
fn main() {
// Create a 1 GiB volume in pool 1, with a random id (or Some(id)).
let v = client.create_volume(1, 1 << 30, None, "scratch").await?;

// Attach it: take its lease. I/O goes through the handle.
let disk = client.attach(v.id).await?;
disk.write(0, vec![0xab; 4096]).await?;
let back = disk.read(0, 4096).await?;
disk.detach().await?;
}
  • create_volume(pool, size, id, name) makes the volume’s header; the size is a multiple of 4096. A retried create is recognised, not doubled. volume(id), list_volumes(pool), expand_volume(id, size) (volumes don’t shrink) and delete_volume(id) manage them; hyperstorctl does the same for administrators.
  • Ids are 128-bit, chosen by you (for example a disk’s UUID) or drawn at random. Names are shown, not unique.

Attaching a volume

attach(id) takes the volume’s lease. The client renews it every second in the background, and a lease not renewed for 4 s runs out. While one client holds it, another’s attach fails with LeaseHeld.

  • detach() gives the lease up. A handle dropped without it stops renewing, and its lease runs out.
  • take_over(id) attaches a volume whose holder has died or is cut off: it waits for the holder’s lease to run out, blocklists the holder, then takes the lease. From then on every storage node refuses the old holder, so none of its writes can land after the new holder’s. A holder that is still renewing is left alone (LeaseHeld).
  • preempt(id) takes a volume from a live holder, for example one an operator moves: it blocklists the holder first. A blocklisted client instance has lost every lease; make a new Client to go on.
  • Once a handle’s lease is lost, its I/O fails with LeaseLost, and lost() returns true.
  • An attached volume can’t be deleted (VolumeAttached); detach it first, or use force_delete_volume(id), which preempts the holder.
  • Read-only attachments (of snapshots, by several clients at once) are planned.

Snapshots and clones

#![allow(unused)]
fn main() {
let snap = client.snapshot(v.id, "before-upgrade").await?;   // crash-consistent
let copy = client.clone_snapshot(v.id, snap.epoch, "copy", None).await?;
client.rollback(v.id, snap.epoch).await?;                    // detached volumes only
client.delete_snapshot(v.id, snap.epoch).await?;
}
  • snapshot(id, name) takes a crash-consistent snapshot: the volume as it would be after a power cut at one instant. If a client has the volume attached, its writes are paused while the snapshot is cut, at most 2 s; past that the snapshot is abandoned (Server with code Busy), and you can try again. A snapshot is identified by its epoch; volume(id) lists them in snapshots.
  • snapshot_group(ids, name) takes a snapshot of several volumes at one instant (a consistency group), for example a database’s data and log volumes; delete_group removes them all.
  • clone_snapshot(id, epoch, name, new_id) makes a new volume from a snapshot at once: it shares the snapshot’s data, and writes to the clone go to its own copies.
  • rollback(id, epoch) returns a detached volume to a snapshot. To the newest snapshot it is done in place and is instant.
  • flatten(id) copies into a clone what it still reads from its parents, so they can be deleted.
  • delete_snapshot(id, epoch) merges the snapshot’s data into what still needs it, without copying blocks, and is refused (SnapshotInUse) while a clone or a rollback depends on it.

Data guarantees and errors

What a successful write means

When write returns Ok, every copy of the data that the pool’s PGs currently use has written it to its device and flushed it. Normally that is size copies; while a node is down, it can be as few as the pool’s min. A write that returned Ok survives a crash or power loss of any node holding a copy, and the failure of all but one of its copies.

A write that returns an error may have reached some copies and not others. Write the same data again: writes to a range are idempotent.

Order and concurrency

  • A read that starts after a write returned sees that write.
  • Two writes in flight at the same time to overlapping ranges land in an order you can’t choose. Wait for one before starting the other if the order matters.
  • A write that spans several chunks is not atomic across them: after a failure, some chunks may have the new data and others the old.

Integrity

Every 4 KiB block carries a CRC32C checksum from the client to the device and back. A block that doesn’t match its checksum is never returned as data. When the primary’s copy is damaged, the primary reads another copy, repairs its own and returns the good data. If no copy is good, the read fails (Server with code Checksum); Checksum on its own means the data was damaged on the way to the client.

Volumes and leases

A volume attached through attach, take_over or preempt has one writer at a time. After a take-over or preemption, the old holder is refused by every storage node, so no write of its lands after the new holder’s first write. A write that failed with LeaseLost may have landed or not.

Snapshots

A snapshot holds every write acknowledged before it was cut, and none issued after. A write in flight while it is cut is in it or not, as after a power cut. A consistency group gives the same guarantee across all its volumes at one instant. Writes to a clone never change its snapshot, and writes to the volume never change its snapshots.

Errors

The client already retries what is worth retrying: a map change, a primary that moved, a PG with no reachable primary, too few copies reachable (Unavailable), a dropped connection. It refreshes its map between attempts and gives up after 20 attempts, about two seconds. A node failure takes a few seconds to detect (see the administrator’s failures page), so a program should be ready to retry an Exhausted error itself.

Running a cluster

A Hyperstor cluster today is:

  • one map service (hyperstor-meta), which holds the cluster map, detects failed nodes and grants map leases;
  • three or more storage nodes (hyperstord), each with one or more devices;
  • clients: programs using the client library.

The cluster is described by one text file, the cluster file, read by the map service at start.

Security. Only the cluster API has authentication (mutual TLS with --api-tls). The map service’s and storage nodes’ ports have none and no encryption yet: anyone who can reach them can read and overwrite every volume. Run clusters only on an isolated network that untrusted hosts cannot reach, and keep test data only. Installation

There are no packages yet: build the binaries from source and copy them to each machine.

Requirements

  • Linux on x86-64 (other architectures are untested), with io_uring enabled: Linux 5.6 or later, and a current long-term kernel is recommended. Some distributions turn io_uring off with the kernel.io_uring_disabled sysctl; it must be 0.
  • Rust 1.88 or later, with cargo.
  • For storage devices: a filesystem that supports O_DIRECT for device files, or whole block devices.
  • TCP connectivity between all storage nodes, and from clients to the map service and to every storage node. See the security note in Running a cluster.

Installing a trial cluster

hyperstor-install sets up a whole cluster on one Linux host: the map service with its cluster API, three storage nodes on files, a pool with three copies and a cache pool, systemd units, and hyperstorctl. It is for trying Hyperstor and testing changes, not for data you want to keep.

cargo build --release
target/release/hyperstor-install check           # host checks, changes nothing
sudo target/release/hyperstor-install install --all-in-one
hyperstorctl status
hyperstorctl io-test

check reports each requirement as ok, info, warn or FAIL. install runs the checks, copies the binaries to /usr/local/bin, creates the hyperstor user, writes the configuration in /etc/hyperstor, the cluster’s certificates in /etc/hyperstor/pki, and the units, and starts hyperstor-meta and hyperstord@0 to hyperstord@2. Everything listens on 127.0.0.1: the cluster API on 8850, the map service on 8849, the storage nodes on 9100 to 9102. Device files go to /var/lib/hyperstor (4 GiB each, sparse).

The installer is convergent: run it again after rebuilding and it updates what changed (binaries, configuration, units) and restarts the services affected; with nothing changed it says so and does nothing. The options of the last run are saved, so sudo hyperstor-install install is enough later. sudo hyperstor-install uninstall stops and removes the services and binaries and keeps the configuration and data. All options are in the reference.

hyperstorctl needs the administrator certificate, readable by root and the hyperstor-admin group: run it with sudo, or join the group (sudo usermod -aG hyperstor-admin $USER, then log in again).

Then see Managing a cluster.

Joining hosts with tokens

Install the map service on one host first. It makes the cluster’s certificates and serves the cluster API on its own address, where the other hosts reach it:

# on the map service's host (192.0.2.10); the cluster file may list no
# storage node at all: they join
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role meta --map 192.0.2.10:8849

Then, for each storage host, make a token on the map service’s host and use it on the new host:

# on the map service's host; umask 077 keeps the file private
(umask 077; sudo hyperstorctl token create --role node > token)
# copy `token` to the new host, readable by root only, then there:
sudo target/release/hyperstor-install install --join 192.0.2.10:8850 \
    --token-file token --role storage --address 192.0.2.21 --reactors 2

The new host pins the cluster by the root fingerprint in the token before it sends anything, makes its own key (which never leaves it), and gets a certificate for a new storage node number. The map service adds the node to the map, down until its first heartbeat, and its PGs start moving to it once it runs. The node gets one reactor per --reactors, each on a file of --size-gib GiB in the data directory and on its own port from --node-port, and its metrics on --address at port 8853.

  • A token is used once, expires after an hour (--ttl SECS, at most a week), and can be revoked with hyperstorctl token revoke --id ID; hyperstorctl token list shows them, never the secrets. Tokens are kept in the map service’s replicated store, so they survive restarts; they are made and used through the leader.
  • The token is never saved. Later runs of the installer, such as the daily timer’s, need none; they renew the host’s certificate through the API with the certificate itself.
  • Installing a host again with the same addresses gets its node back.

Several map service members. Install the first member with the whole member list, then join the others with meta tokens; they get the cluster file, the root’s certificate and the intermediate CA, so every member signs with the same CA (the root’s key stays on the first host):

M=1=192.0.2.10:8851/192.0.2.10:8849,2=192.0.2.11:8851/192.0.2.11:8849,3=192.0.2.12:8851/192.0.2.12:8849
# first member
sudo hyperstor-install install --cluster cluster.txt --role meta --members $M --member-id 1
(umask 077; sudo hyperstorctl token create --role meta > token-2)
# second member (and likewise the third)
sudo hyperstor-install install --join 192.0.2.10:8850 --token-file token-2 \
    --role meta --members $M --member-id 2

A member’s host can also run a storage node: list the nodes in the cluster file, and give each member --role both --node N (the first with --cluster, the others with --join); a joined member gets the file, and so its node, from the first.

Tokens are made and used through the leader; the other members refuse with the leader’s address. Before the members have formed a group, the first member makes the meta tokens itself.

Back up the root CA’s key on the first host, which alone has it (see hyperstor-install):

sudo hyperstor-install root-backup --out /media/usb/root.bak --passphrase-file pass

Installing a cluster across hosts from one file

Without tokens, write the cluster file once, copy it to every host, and install each host’s part of it:

# on the map service's host (192.0.2.10)
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role meta --map 192.0.2.10:8849
# on each storage host, with its node number from the file
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role storage --node 0 --map 192.0.2.10:8849

A storage node gets one reactor for each address the cluster file lists for it. Adding a host means editing every copy of the file. Storage hosts installed this way get no certificate; joined ones do, though the storage network doesn’t use them yet: it has no authentication (see Running a cluster).

Hosts that run VMs

hyperstor-vhost serves volumes to the VMs on a host, for glidex’s hyperstor datastores. Add it to a host’s role, or install a host that only runs VMs:

sudo hyperstor-install install --vhost --vhost-user glidex          # with what the host runs already
sudo hyperstor-install install --role vhost --map 192.0.2.10:8849 --vhost-user glidex

--vhost-user glidex lets glidex’s control plane attach volumes and its hypervisors open their sockets. Restarting the service (an upgrade, say) keeps the VMs’ disks.

Without the installer, a minimal unit for a storage node:

[Unit]

Planning a cluster

Nodes and devices

  • Use at least as many storage nodes as the largest pool’s size, in distinct failure domains, plus one so that a failed node’s data can be copied to a stand-in (see Failures and recovery). Three nodes run a three-copy pool; it keeps working with two copies while one node is down, but can’t restore the third until the node returns.
  • Give each node one device per CPU core you want to dedicate to storage. Each device has its own thread and its own TCP port.
  • Device files grow up to the size given to hyperstord as data is written. Keep that much room on the filesystem.

Node numbers and addresses

Every node has a number, unique in the cluster, and one address per device. The addresses in the cluster file and the --shard options of hyperstord must match, in the same order: the first address listed for node 3 is node 3’s first --shard.

Failure domains

The rack number of each node in the cluster file, and each pool’s domain, decide what two copies of a chunk may share:

domainCopies are on differentUse when
devicedevices (possibly on one host)testing on one machine
hoststorage nodesthe default
rackracksnodes in a rack share power or a switch

When there are fewer domains than copies, a PG gets fewer copies than size: plan at least size domains.

Pools

SettingGuidance
size3 for data you care about; 2 halves the space but survives only one failure
minsize - 1: writes go on with one copy missing, and stop rather than run on one copy
pgsa power of two; about 100 PGs per device across all pools spreads data evenly. It can’t be changed later yet
chunk4 MiB (4194304) suits most volumes; it must be a multiple of 4096

Erasure-coded pools (ec4+2) are accepted by the cluster file but not served yet; use replicated pools.

Network

Each storage node device needs one TCP port reachable from every client and every other storage node. The map service needs one port reachable from all of them. Pick ports and firewall rules accordingly, and keep the storage network isolated (see Running a cluster).

Managing a cluster

hyperstorctl talks to the cluster API. On a host set up with hyperstor-install it finds the API by itself; elsewhere, give --api IP:PORT or set HYPERSTOR_API.

Dashboard

The installer runs the management service (hyperstor-mgmt) on the map service’s host, at http://127.0.0.1:8852/. Installed with --ui (see hyperstor-install), it serves the web UI: an overview, nodes and devices (take out, bring in, drain), pools and PGs, volumes with their snapshots and clones, operations, the map service’s members, and security (people and roles, API tokens, join tokens, certificates); each action shows its hyperstorctl command. Without it, a built-in dashboard shows health with its reasons, I/O rates, space, pools with their PG states (and each PG’s acting and up sets), and every storage node with its state, last heartbeat, I/O, write and read p99 latency, space, log use and map epoch. It refreshes every two seconds.

People log in with their user name and password on that host; they must be in the group hyperstor-users:

sudo usermod -aG hyperstor-users ann

The first to log in with the claim code becomes the first security administrator, who then gives people roles (viewer, operator, storage-admin, security-admin; see hyperstor-mgmt). The code is in the service’s log, valid for an hour:

journalctl -u hyperstor-mgmt | grep 'claim code'
# a new one: sudo systemctl restart hyperstor-mgmt

Someone who logs in without a role sees nothing until given one.

Reaching it. mgmt listens on every address of the map service’s host, over HTTPS: https://HOST:8852/. Its certificate comes from the cluster’s own CA, so a browser warns until you import the cluster’s root once (/etc/hyperstor/pki/root.crt, as a trusted authority for websites). To avoid that, give it a certificate browsers already trust:

  • your own, kept current by an ACME client: sudo hyperstor-install install --web-tls /etc/hyperstor/web (see hyperstor-mgmt);
  • on Tailscale, the node’s own: sudo hyperstor-install install --tailscale-cert, then https://NODE.TAILNET.ts.net:8852/.

Air-gapped sites. Nothing here needs the internet: the cluster’s CA and mgmt’s certificate are made on the map service’s host, and renewed there. To have browsers trust it without a warning, either distribute the cluster’s root (/etc/hyperstor/pki/root.crt) to the site’s machines once, with whatever configuration management the site uses, after which every hyperstor host verifies; or issue mgmt a certificate from the site’s own internal CA and give it with --web-tls DIR (mgmt re-reads the files when they are renewed). mgmt serves no self-signed certificate.

To keep it on loopback instead, --mgmt-listen loopback, and reach it through a tunnel:

ssh -L 8852:127.0.0.1:8852 the-map-service-host
# then open http://127.0.0.1:8852/

The dashboard only shows; changes go through hyperstorctl, or the cluster API through hyperstor-mgmt (POST /api/hyperstor.v1.…) as the person logged in, with an API token for scripts.

The trash

Deleting a volume or a snapshot moves it to the trash: it disappears from the lists and can’t be attached, but its data stays, and its space still counts against the pool, for the pool’s grace period (a day by default). Then the map service purges it.

hyperstorctl delete-volume --id ID        # → the trash, purged in a day
hyperstorctl trash list
hyperstorctl trash restore --id ID        # back, under its name
hyperstorctl trash purge --id ID --wait 600   # gone now (a fresh login, through mgmt)
hyperstorctl trash settings --pool 1 --grace 604800   # keep a week

A restored volume whose name another volume took meanwhile comes back as NAME-restored. --on-full purge lets a full pool purge its oldest trash first rather than refuse writes; it acts once pools have fullness thresholds. The UI’s Trash page does the same.

The audit log

Every change, every refused call and every break-glass call is recorded: when, who (a certificate’s identity, local:uid=N on the socket, or a person user:NAME through hyperstor-mgmt), what, on what, and how it went. Each record goes to the service’s journal at once, and to the cluster’s audit log in .meta within a second, kept a year by default:

hyperstorctl audit list --since 1d --op DeleteVolume
hyperstorctl audit list --principal user:ann --json
hyperstorctl audit settings --retention-days 730
journalctl -u hyperstor-meta -u hyperstor-mgmt | grep '"audit":1'

Security administrators read it on the UI’s Audit page, and can export it there as JSON lines.

Taking a device out for service

hyperstorctl out --node 2 --wait 600   # or --device D; waits for the PGs to move
...                                    # service the node
hyperstorctl in --node 2 --wait 600    # and for them to come back

A device that is out gets no placement: its PGs go to other devices, which are refilled from the remaining copies. With as many storage nodes as copies, there is nowhere to move them, so the PGs run with one copy fewer (degraded) until the device is back in. Writes go on while each PG keeps at least the pool’s min copies.

Without --data, out doesn’t survive a map service restart. A map service without a store reads the cluster file when it starts and doesn’t keep changes made since, so after a restart every device is in again. With --data (every install does this) the map, out devices included, is kept.

Draining a node

hyperstorctl drain --node N takes every device of node N out and follows its PGs as an operation, until none lives on the node and none is still moving: then the node can be switched off or serviced.

hyperstorctl drain --node 3 --dry-run   # what would move; nothing changes
hyperstorctl drain --node 3 --wait 600  # drain and follow it to the end
hyperstorctl op list                    # running and recent operations
hyperstorctl op watch --id ID           # follow one
hyperstorctl op cancel --id ID          # stop; the devices come back in
hyperstorctl in --node 3                # after the service

drain prints each PG that moves, with its acting set before and where it goes. Flattening a clone and purging from the trash are operations too, as is each purge the map service makes when a grace period ends. Operations are kept in the map service’s replicated store, a week after they finish, and a new leader carries on with those still running. Only a drain can be cancelled. op watch exits with status 1 if the operation failed or was cancelled, for scripts.

Revoking a certificate

A certificate that leaked, or a host that is gone, is revoked by serial:

hyperstorctl cert list                       # certificates issued through the API
hyperstorctl cert show --file /path/node.crt # a certificate file's serial
hyperstorctl cert revoke --serial SERIAL

Every map service member then refuses it, on the cluster API and between members, until it would have expired anyway (30 days at most). The local socket on a map service host needs no certificate, so revoking the administrator’s own never locks root out.

hyperstorctl create-volume --size 10G --name db      # prints its id

The map service

hyperstor-meta holds the cluster map, answers map requests from storage nodes and clients, detects failed nodes from their heartbeats, and grants map leases: a storage node serves I/O only while its lease is current.

Starting it

hyperstor-meta --listen 192.0.2.10:9000 --cluster /etc/hyperstor/cluster.txt

It prints the size of the map it loaded, then runs until stopped. All options are in the reference.

With --api 127.0.0.1:8850 it also serves the cluster API, which hyperstorctl uses to report health and take devices out and in. Add --api-tls DIR to require client certificates; without it, keep the API on loopback.

Leases and failure detection

OptionDefaultEffect
--lease-ms600How long a storage node may serve after its last heartbeat was answered
--down-after-ms800How long without a heartbeat before a node is marked down; at least 1.25 × the lease
--down-out-secs600How long a node stays down before its devices are marked out and its data is copied elsewhere

A node marked down loses its roles: its placement groups get new primaries and run with the other copies, and a node cut off from the map service has already stopped serving, because its lease ran out first. Nothing is copied until --down-out-secs pass, so a reboot moves no data (see Failures and recovery). Shorter times detect failures sooner, at the cost of false alarms on a slow or busy network.

Several members

Run the map service as a group of three members (five for large clusters), each on its own host, so that it keeps working when one is down (two, with five). Each member keeps the map in a store of its own (--data), and they replicate it with Raft:

# On each of the three hosts, with its own --id and the same --member list:
hyperstor-meta --listen 192.0.2.10:9000 --cluster /etc/hyperstor/cluster.txt \
  --data /var/lib/hyperstor/meta --id 1 \
  --member 1=192.0.2.10:8851/192.0.2.10:9000 \
  --member 2=192.0.2.11:8851/192.0.2.11:9000 \
  --member 3=192.0.2.12:8851/192.0.2.12:9000 \
  --api-tls /etc/hyperstor/pki

Give storage nodes and clients every member (hyperstord --meta 192.0.2.10:9000,192.0.2.11:9000,192.0.2.12:9000). Any member serves the map; the leader also grants leases, watches heartbeats and changes the map, and the others send nodes to it.

  • When the leader fails, the others elect a new one within about half a second. Storage nodes keep serving on their leases meanwhile and get new ones from the new leader at once, so I/O pauses for about one lease at most. The new leader then waits until every lease the old one gave has run out before it marks any node down or moves any data.
  • The map survives restarts, of one member or all of them: a member that comes back catches up with the others. The cluster file seeds the map the first time; after that, hosts and pools you add to the file (on every member) are added when a leader is next elected: restart the members, one at a time. Removing them goes through hyperstorctl out and in.
  • Members talk over mutual TLS with their --api-tls certificates, which must name each member’s address. hyperstor-install sets this up when members join the first one with a token (see Installation).
  • Changing members while the group runs, and recovering a group that lost its majority, are below: see Adding and removing members and Recovering a lost majority.

One member

Without --member, the map service is one member: with --data it keeps its map across restarts, and without it, it keeps the map in memory only. A single member is a single point of failure:

  • While it is down, clients can’t connect, and storage nodes stop serving I/O once their leases run out. Run it on a reliable host and restart it automatically.
  • Without --data, it forgets. On restart it reads the cluster file again and starts with every node up; it forgets which nodes were down and which were being refilled, so restart it only while all storage nodes are up and no recovery is running (see Failures and recovery).

Backups and restoring

Installed map services keep backups of their store in /var/lib/hyperstor/meta-backups: the leader writes one when the map, the join tokens or the certificate lists have changed, at most every 5 minutes, and keeps the last 24. Take one at any time, to keep off the cluster:

hyperstorctl map backup --out map.hsbackup

A backup holds what the map service holds, not data: volumes and their contents live on the storage nodes. If every member’s store is lost, start one member from a backup, into an empty data directory, and the storage nodes reconnect to it:

sudo systemctl stop hyperstor-meta
sudo mv /var/lib/hyperstor/meta /var/lib/hyperstor/meta.lost
# The backup must be readable by the service's user.
echo "HS_ONCE=--restore /var/lib/hyperstor/meta-backups/map-…hsbackup" \
    | sudo tee /etc/hyperstor/meta-once.env
sudo systemctl start hyperstor-meta
hyperstorctl status --wait 60
sudo rm /etc/hyperstor/meta-once.env

/etc/hyperstor/meta-once.env holds options for one start; the restored store stays in the data directory, and the next start needs none. It is a map service of one; with several members, the others join it again. Changes made after the backup was taken are lost: hosts joined since then join again.

Adding and removing members

Members can be added and removed while the map service runs. Install the new member first, with a meta token from the leader and a member list that includes it, and start it; then add it on the leader:

# on the new host (member 4)
sudo hyperstor-install install --join 192.0.2.10:8850 --token-file token \
    --role meta --members "$M,4=192.0.2.13:8851/192.0.2.13:8849" --member-id 4
# on the leader
hyperstorctl member add --id 4 --raft 192.0.2.13:8851 --map 192.0.2.13:8849
hyperstorctl member list

The new member is a learner until it has the log, then a voter. member remove --id N takes one out; fewer than three voters survive no failure, so going below three needs --force. Replacing a member on another host is add, then remove. Storage nodes keep the member list they were installed with and are redirected to the leader by any member they reach; installing them again gives them the new list.

Recovering a lost majority

If most members are lost for good, the rest can serve the map but not change it: nothing is marked down and no host joins. Force one survivor alone, on its host, with every other member stopped:

sudo systemctl stop hyperstor-meta
echo "HS_ONCE=--force-alone CLUSTER_ID" | sudo tee /etc/hyperstor/meta-once.env
sudo systemctl start hyperstor-meta
hyperstorctl member list            # one member, leading
sudo rm /etc/hyperstor/meta-once.env

It refuses while another member answers, since two groups would then split the cluster, and unless given the cluster’s id. It revokes the other members’ certificates issued until then, so an old member that comes back with its log is refused; reinstall those with fresh data directories, join them with meta tokens, and add them. Map changes the survivor hadn’t received before the loss are lost: hosts joined in that window join again.

Storage nodes

hyperstord runs one storage node. Each --shard gives it one device and the address it serves that device on:

hyperstord --node 3 --meta 192.0.2.10:9000 \
    --shard 192.0.2.23:9100=/var/lib/hyperstor/dev0.img:100 \
    --shard 192.0.2.23:9101=/dev/nvme1n1:0 \
    --cpus 2,3

All options are in the reference.

Devices

A device is a file or a block device:

  • A file is created if needed and extended to the size given, in GiB, after the colon. It is sparse at first and fills up as data is written; keep that much space free on its filesystem.
  • A block device is used whole. Give its size as 0 (/dev/nvme1n1:0).
  • A device without Hyperstor’s format is formatted on first start, without asking. Check the paths before starting a node: a typo can format the wrong device.

Devices are opened with O_DIRECT and driven through io_uring. --buffered goes through the page cache instead, for filesystems that refuse O_DIRECT; use it for testing only.

Hard disks

Flash devices write every change to a new place. --hdd tells the node its devices are hard disks: small overwrites then go through the log first and are applied in place later, which suits disks’ slow seeks. It applies to every device of the node.

CPUs

Each device is served by one thread. --cpus 2,3 pins the thread of the first --shard to CPU 2 and the second to CPU 3. Pin to cores that nothing else busy uses, and keep them on the same NUMA node as the device and the network card where you can.

Starting, stopping and restarting

  • A node stops on SIGINT or SIGTERM by exiting.
  • On the next start, each device recovers on its own: it replays its log and checks the last writes against their checksums. Writes that were acknowledged are never lost.
  • While a node is stopped, the map service marks it down after --down-after-ms, and its placement groups go on without it. When it starts again it is refilled (see Failures and recovery).
  • Keep a node’s number and device paths the same across restarts: they identify its data.

Failures and recovery

A storage node fails

  1. The node stops sending heartbeats. Clients’ requests to it fail, and the client library retries.
  2. After --down-after-ms (0.8 s by default) the map service marks the node down. Each placement group the node held goes on with the copies left, if at least the pool’s min remain; a new primary takes over where the failed node was primary. Before it serves, the new primary makes the other copies match its own, so a write the failed node never confirmed to its client is kept by every copy or by none.
  3. Writes continue with fewer copies (the PGs are degraded). Nothing is copied yet: the node keeps its place, so a short reboot moves no data.
  4. If the node is still down after hyperstor-meta --down-out-secs (10 minutes by default), its devices are marked out. Where the pool’s failure domain allows, their PGs are placed on other devices, and each primary backfills the new copy (copies every object of the PG to it) while writes go on. Once full, it counts as a copy. Where no other domain is free (three nodes and three copies by host), the PGs stay degraded until the node returns.

If every copy of a PG is down, the PG stays down, and requests for its data fail until one of its nodes returns. It is never reset to empty.

A storage node returns

When the node starts again and sends heartbeats, the map service marks it up, and marks its devices in again if they were marked out while it was down. Placement wants it back for the PGs it held. For each of them, the current primary backfills it: it compares what the node holds with its own copy, object by object, and sends only the objects that differ (deleting those it no longer has), since the node may have missed writes. Only then does the node count as a full copy again, and any copy placed elsewhere meanwhile is dropped.

So a node that was down briefly receives about what was written while it was away. A new or empty node receives all of its PGs’ data: plan for that traffic when you add or replace one.

A device you took out yourself (hyperstorctl out) stays out until you bring it back in.

A replica is slow or unreachable

A primary that gets no answer from one of a PG’s copies within 2 s, or can’t connect to it at all, reports it to the map service. The map service takes that copy out of that one PG, as long as the pool’s min copies remain, and the primary backfills it back once it answers again. The node itself stays up, and its other PGs are not affected. This also covers a network cut between two storage nodes only, which the map service can’t see from heartbeats.

The client sees Unavailable for the write that timed out, and retries. A slow primary is not handled yet: its clients wait for it.

A device fails

A device that returns an I/O error is failed: its node answers every request for it with Unavailable (clients retry) and reports it to the map service, which marks it failed and out and places its PGs elsewhere at once, without waiting for --down-out-secs. The node’s other devices go on serving. One I/O error is enough: there is no error-rate threshold yet.

If the device is broken, replace it and start the node again (the new device is formatted), then bring it back in with hyperstorctl in --device D: its PGs are backfilled.

Damaged data

Every 4 KiB block carries a checksum. When a primary reads a block whose checksum doesn’t match, it fetches the object from another copy, replaces its own copy and answers the read with the good data. A damaged block is never returned to a client.

Scrub

Every storage node compares, once a day by default (hyperstord --scrub-hours), the copies of each placement group it leads. A copy that differs from the others, when the rest agree, is replaced from the majority’s copy, the primary’s own included. Once a week (and on the first scrub after a start) the scrub is deep: every copy is read in full and each block’s checksum checked, at a limited rate, so damage that no client has read yet is found and replaced from the other copies (kind="damaged"). When no majority agrees, nothing is changed: the object is counted under hyperstor_scrub_objects_total{kind="unresolved"} and logged, and hyperstorctl status warns with the PG (PG(s) inconsistent), for an operator to look at.

A storage node is cut off from the map service

A node that can reach clients but not the map service keeps serving until its map lease runs out (--lease-ms, 0.6 s by default), then stops. The map service waits longer than the lease before giving its PGs to other nodes, so no acknowledged write is lost and two nodes never serve the same PG.

A client holding a volume fails

A volume is attached by one client at a time, which renews its lease every second. If that client dies or is cut off, another client takes the volume over: it waits for the old lease to run out (up to 4 s) and blocklists the old client, so every storage node refuses it from then on, even if it comes back. See the client library.

The map service fails

See The map service: with three or five members, the others elect a new leader within about half a second and I/O pauses for about one lease. A single member is a single point of failure: the cluster stops serving within a lease period, and resumes when it is back.

Not handled yet

  • A slow primary.

Goals in one paragraph

Hyperstor is a sharded, distributed store written in pure Rust on Linux io_uring. It keeps two or three copies of every chunk (erasure coding is planned) on many storage nodes, places them by failure domain, and keeps serving when nodes, devices or links fail. Block volumes come first: for virtual machines through vhost-user-blk, and for other hosts through NVMe over Fabrics (both planned). The same object layer is meant to carry GPU-direct reads into GPU memory, a host-wide read cache, an S3 gateway and a distributed filesystem later. It is built for the glidex platform, which runs agent VMs, inference, fine-tuning and retrieval workloads, and it also runs on its own.

A write, end to end

  1. The client splits the request at chunk boundaries (4 MiB chunks by default; offsets and lengths are multiples of 4 KiB). Each piece is sent in parallel.
  2. It routes each piece without asking anyone: the chunk’s placement group (PG) is a hash of the volume’s lineage and the chunk index, and the PG’s primary is the first device of its acting set in the client’s copy of the map (placement).
  3. The primary checks the request: it holds a current map lease, the PG is not fenced for a map change, the request’s PG epoch matches its own, it is the primary, the client is not blocklisted, and every block’s CRC32C matches. A request at an old epoch is answered StaleMap; at a new epoch, the primary first makes the other copies match its own (peering).
  4. It replicates: it gives the write the PG’s next sequence number, sends it to every other copy and queues its own commit, with nothing in between, so every copy applies the PG’s writes in the same order.
  5. Each copy commits through its engine’s group commit: the reactor gathers queued changes, writes their data to new extents and one log record, flushes once, and acknowledges them all.
  6. The primary answers the client only when its own commit and every copy’s have been acknowledged.
  7. On failure the client retries: on a stale map, a moved primary, Unavailable, or a dropped connection, it refreshes its map and tries again, up to 20 times with a growing back-off (about two seconds in all).

A read, end to end

The client sends the read to the PG’s primary, which serves it from its own engine while it holds its map lease. Every block’s CRC is checked on the device and again by the client. If the primary’s copy fails its check, the primary fetches the object from another copy, replaces its own, and answers with the good data. Blocks never written read as zeros.

Why reads go to the primary only: it is the one copy guaranteed to have every acknowledged write. Reads from any copy are planned for snapshots, which never change. A read of a volume with snapshots or clones carries its layers (see snapshots), and the primary reads each block from the newest version that holds it.

The map and its epochs

Every node and client holds a copy of the cluster map: nodes and their devices, pools and their rules, and for every PG its up set (where placement wants it), its acting set (the copies that have every acknowledged write) and its primary. Each change bumps the map epoch; each PG also has a PG epoch, the map epoch of the last change to its acting set. A request carries both, so a node or client with an older map is told so and fetches the new one, and no copy acts on a write meant for an earlier arrangement. See the map service.

The data path: reactor and engine

Each storage device is split into shards, and each shard is owned by one reactor: a thread pinned to a core, running Hyperstor’s own io_uring event loop. The shard’s engine, its network port, its replication and its recovery all run on that thread. Nothing on the data path takes a lock shared with another core.

The engine

The engine stores objects. An object has sparse data in 4 KiB blocks, a table of attributes, and an ordered key–value table. Volumes are made of chunk objects; volume headers, and later the key–value store, S3 and the filesystem, use the same objects in their own namespaces.

Operation lists

A change is an operation list, applied atomically: all of it or none of it survives a crash. Operations include Write, Zero, Truncate, SetAttr, KvPut, KvDelRange, Delete, and asserts (AssertRevision, AssertExists, AssertAbsent) checked before the list applies. Asserts make compare-and-set possible, which the volume headers use. Absorb serves snapshot deletion: it hands the blocks an older version of a chunk holds, and a newer one lacks, to the newer one, then deletes the older, all in one log record and without copying any data. Reads can go through layers: each block comes from the first of a list of objects (a chunk’s versions) that holds it, zeros if none does. Every change gets a revision from a counter that never repeats, so compare-and-set has no ABA problem.

On-device format

device:  [superblock A][superblock B][shard 0][shard 1] ... [shard n]
shard:   [super A][super B][log ring][data area]
  • The two shard superblocks alternate by sequence number, so a torn superblock write leaves the other one valid.
  • The log ring is a sixteenth of the shard, between 1 MiB and 1 GiB. It holds whole-block records, each with a CRC32C seeded by a salt that changes on every open, so an old record left in the ring is never mistaken for a new one.
  • The data area holds extents. Every 4 KiB block in an extent has its own CRC32C, kept in the index and carried on the wire unchanged from the client to the device and back.

Redirect-on-write, and deferral for hard disks

On flash, every write goes to new extents, and the log record that commits it names them: data is written once. On hard disks (hyperstord --hdd), a small overwrite (under 64 KiB) of blocks an object already holds goes into the log record and is applied in place later, so the disk doesn’t seek to a new place for every small write.

Why: on flash, deferring writes data twice. Measured on the same drive, redirecting gave 1.6× the 4 KiB write throughput, and end to end 19 % more throughput with a 2.6× lower p99 (Performance).

Group commit

A per-reactor committer drains the queue of operation lists: it writes their new extents and one log record, issues one flush for the whole round, then acknowledges every list in it. At batch 32 the log costs about 128 bytes per update (257 B with checkpoints).

Checkpoints

The index lives in memory and is written out by fuzzy checkpoints: starting when a quarter of the log is used, each commit round also writes 64 KiB of the checkpoint (8× that past half), and the checkpoint must be done by three quarters. The superblock then names the new checkpoint and the log position after it.

Why fuzzy: writing the whole checkpoint at once stalled commits for 8–13 ms at p99. In slices, commit p99 is 109 µs at the same throughput.

Recovery

On open, the engine loads the checkpoint the newer superblock names, replays the log from there, and checks the data CRCs of the last commit group: a record whose data didn’t reach the media is dropped, with everything after it. Replay runs at about 270 MiB of log per second; opening takes about 0.3 s plus 4.5 ms per MiB replayed.

The index

Each object’s block map starts as a list of runs (extents). When a chunk gets fragmented by random overwrites, it switches to a dense map: 8 bytes per block (a 32-bit physical block and its CRC), and back to runs when it compacts again.

Why: after random overwrites, run maps cost about 33 GiB of memory per TiB of data; dense maps cap it at 2 GiB per TiB. A copy-on-write B+tree on the device, which pages the index, is planned after checkpoints that seal the index and write only what changed (see decisions). Snapshots don’t wait for it: they are versions of chunk objects (volumes).

Content digests

The engine can compute a 64-bit digest of each object from its index alone, reading no data: FNV-1a over its size, each non-zero block’s number and CRC32C, its attributes and its key–value table. Replication uses these digests for peering, delta recovery and light scrub (replication). Listing them costs about 0.5 µs per small object and 20–50 µs per 4 MiB chunk.

Crash testing

The engine’s crash test runs random operation lists against a reference model (a sorted map in memory), and cuts the power at random device operations: blocks not yet flushed are randomly kept or lost, so writes are torn and reordered, and it cuts the power again during recovery. After each crash the recovered shard must equal the model after every acknowledged list plus some prefix of the ones in flight. 300 seeds run on every change (HS_CRASH_SEEDS sets more); a 5,000-seed run (30,000 crashes) has passed.

Placement and replication

Placement

Chunks and placement groups

A volume is cut into chunks (4 MiB by default). A chunk’s name is its volume’s lineage (128 bits) and its index. A pool has a fixed, power-of-two number of placement groups (PGs), and a chunk’s PG is a hash of its lineage and index, masked to the PG count. Hashes are SplitMix64’s finalizer for integers and FNV-1a for byte strings; their values are pinned in tests, because changing them would move every chunk.

Why PGs: a cluster with millions of chunks needs placement, recovery and peering decisions for only thousands of PGs. Why by lineage: a clone shares its parent’s lineage, so a read that falls through to the parent’s chunks stays on the same devices (clones are planned).

Weighted rendezvous hashing

Each PG is placed on devices by weighted rendezvous hashing (also called highest random weight, HRW): every candidate gets a score from a hash of the PG and the candidate, and the best scores win. Hyperstor uses the exponential form, score = −ln(u) / weight with u from the hash’s top 53 bits, lowest score winning, so a candidate wins with probability proportional to its weight.

Placement is hierarchical, over the pool’s failure domain: it ranks racks, then hosts within a rack, then devices within a host, each level salted differently, with device weights summed up the tree. No two copies share the failure domain (device, host or rack).

Up, acting and primary

For each PG, placement gives the up set: where it wants the copies. The acting set is the copies that hold every acknowledged write; the first one is the primary. When up and acting differ (a device was added, or one returns), the primary backfills the new copies while writes go on, and once they are full a map change makes acting equal to up with a new PG epoch.

The replicated write

Hyperstor uses primary-copy replication: the client sends a write to the PG’s primary, which sends it to every other copy in the acting set and answers the client only when every copy has made it durable.

  • A PG with fewer than its pool’s min copies refuses writes rather than accept them on fewer.
  • Each PG’s writes get a sequence number from the primary, and every copy applies them in that order.
  • A copy being backfilled also receives live writes, so it doesn’t fall behind while it fills.

Why all copies, not a quorum: with every acknowledged write on every acting copy, any copy can become primary without a log comparison, and reads need only the primary. The cost is that one slow copy slows the PG’s writes, which is why slow copies are dropped (below).

Map leases and fencing

A storage node serves a PG only while it holds a map lease, renewed by each heartbeat answer. The node counts its lease from the moment it sent the heartbeat, and the map service counts it from when it answered, plus a quarter: so whatever the network delay, the node’s lease ends first, and the extra quarter covers clocks that run at slightly different rates. No synchronized clocks are needed.

Before publishing a change that takes a role away from a device, the leader fences it: the device stops accepting new work for those PGs and answers once its writes in flight are done. A device that doesn’t answer gets no more leases, and the leader waits until its last lease has run out (1.25 leases after the last grant). Only then does it publish the new map and push it to every node.

The result: two primaries never accept writes for one PG, and the lease is also what makes reads from the primary safe, with no separate read leases. The cost: if the whole map service is down, I/O stops after one lease, which is why it runs as three or five members.

A new Raft leader serves the map at once but waits 1.25 leases before changing any role, because leases are kept in the old leader’s memory only. Replicating them would cost a Raft write per node per heartbeat.

Ignoring a primary that peers report silent keeps a primary that is itself cut off from dropping healthy copies.

Peering and recovery by content digests

When a PG gets a new primary, the primary peers before it serves: it asks every acting copy for its list of (object, digest) pairs (digests), compares them with its own, and pushes its own version, or a delete, of each object that differs.

Why this is safe: every acknowledged write is on every acting copy, the new primary included. So any difference is a write that was never acknowledged, and making every copy match the primary means no client can read a value and later find it gone.

Delta recovery and backfill work the same way: a returning or new copy lists its digests, and the primary sends only the objects that differ, as whole objects (data, CRCs, attributes, key–value table), on the same connection as live writes so a push never overtakes a write. A node returning after 1 % of a volume changed received 2 MiB instead of 192 MiB.

The alternative, a PG log (Ceph’s approach): keep the last operations of each PG, and replay the missing ones to a returning copy. It sends only what changed, but it is persisted state to write on every operation, crash-test, and trim, and a copy away longer than the log still needs a full comparison. Digests need no new state and cover every case with one mechanism. Their cost is a scan of the PG’s index entries (not its data) on both sides. The log will be built only if measurements on large PGs show the scan is too slow.

Scrub

Each storage node compares, every 24 hours by default (hyperstord --scrub-hours), the copies of each clean PG it leads, spread evenly over the interval:

  • Light scrub compares digests. A difference is looked at again after 200 ms, so a write in flight isn’t counted as damage.
  • Deep scrub, on the first pass after a start and every seventh, has every copy first read all its blocks and check their CRCs, at most 64 MiB/s per device. A damaged copy gets a digest that never matches, so it never counts toward a majority.
  • Repair by majority: if the primary’s copy is in a strict majority, it is pushed to the others; if another value is, the primary first pulls that copy, then pushes it. With no majority, nothing is changed: the object is reported, and cluster health warns.

When a client’s read finds a damaged block on the primary, the primary fetches the object from another copy, replaces its own and serves the read, holding writes to that object meanwhile.

Volumes, leases and the blocklist

Volume metadata

Volume records are not in the map service. They are objects in a replicated pool of their own, .meta (pool 0: three copies where there are three nodes, 256 PGs):

ObjectContents
Header h/{id}The volume’s pool, size, lineage, state and name, a version number, a creation token, and while attached, its lease holder
Directory d/{pool}/{shard}The pool’s volumes, in 64 shards by id, one key–value entry each

Every change to a header is a compare-and-set on its version: an operation list that asserts the version it read, then writes the new header, decided by the header’s PG primary under a lock on the key. Creating a volume carries a token, so a retry after a lost answer is recognised rather than doubled. Create writes the header and then the directory entry; delete marks the header deleting, removes the data, then the entry, then the header, so every step can be resumed.

Why not in Raft: volume operations then scale with the number of PGs, not with one Raft group, and a Raft write is needed only for map changes. This is the pattern Ceph’s RBD uses with its header objects.

One writer per volume: leases

A client attaches a volume by taking its lease: the header’s PG primary records the holder in the header and keeps the expiry in memory.

TimingValue
Renewalevery 1 s, in one message per holder and primary for all its volumes
Expiry4 s after the last renewal

A renewal writes nothing, so leases cost no metadata writes. A new primary for a header’s PG gives every holder a full lease, so a primary failure never takes a volume away from a live holder.

The blocklist and forced takeovers

If a holder dies or is cut off, another client must not start writing while the old one might still have writes in flight. Hyperstor uses a blocklist in the cluster map:

  1. take_over waits until the old holder’s lease has run out (up to 4 s). A holder that is still renewing is left alone.
  2. It adds the old holder’s client instance to the blocklist: one Raft write. The leader pushes the map and waits until every storage node has acknowledged it, or 1.25 map leases have passed (after which a node that didn’t acknowledge has stopped serving).
  3. It takes the lease.

From then on every storage node refuses requests from the old instance, checked again just before a write is queued, so none of its writes lands after the new holder’s. preempt does the same for a live holder, for example when glidex moves a VM off a node it has fenced: it blocklists first, then waits out the lease. A forced delete preempts the holder and deletes the volume while holding its lease. Blocklist entries expire after an hour.

Why a blocklist, not a token on every write: checking a lease token on every write adds work to every write and state to every copy. The blocklist costs nothing on the write path that could be measured, and one Raft write per takeover. Ceph uses the same approach for RBD exclusive locks.

A forced takeover takes one volume lease, about 4.0 s; a preemption about 3.8 s.

Snapshots and clones

Versions by epoch

A volume has a head epoch. Each chunk write creates or updates the chunk’s version at the head epoch: a separate engine object, named by the chunk and the epoch. A snapshot is one compare-and-set on the header that records the current epoch as a snapshot and moves the head epoch on. Nothing is copied, and storage nodes take no part in the cut: the next write to each chunk simply starts a new version, which holds only the blocks written since (redirect-on-write).

A read at the head goes through layers: the chunk’s versions from newest to oldest, and the primary takes each block from the first version that has it. A snapshot reads the versions up to its own epoch.

Pausing the writer

If a client has the volume attached, its writes in flight must be on the right side of the cut. The holder keeps one long-poll Watch request open on its header’s primary. To take a snapshot, the primary tells it to quiesce: it pauses new writes, drains those in flight, answers, and after the compare-and-set resumes at the new epoch. If it doesn’t drain within 2 s, the snapshot is abandoned (Busy) rather than stall the volume. Why a watch: news carried by the 1 s lease renewals could take most of a second to arrive; the watch costs milliseconds plus the drain.

A consistency group holds every member’s writer with one token, snapshots each under its hold, then releases them all and marks the group complete; on any failure it deletes the snapshots taken and releases the holds.

Clones, branches and rollback

A clone is a new volume on a new branch of the same lineage: its chunk versions carry its branch number, and it reads through its own branch first, then the snapshot’s chain. Sharing the lineage keeps a clone’s chunks in the same PGs as its parent’s, so a read that falls through stays on the same devices. A lineage object records every branch and what it reads, so a snapshot that something still reads can’t be deleted. Flatten copies into a clone what it still reads from its parents, so it no longer depends on them.

A rollback to the newest snapshot of the head’s branch is done in place: the header moves the head epoch on and records the epochs since the snapshot as skipped, so reads skip them at once, and their versions are deleted afterwards. A rollback to an older snapshot makes a new branch. Why in place: agent VMs are reset to a clean snapshot after every task. A new branch per reset would add a level to the read chain each time, and the chain is limited to 16 levels; in place, the chain never grows.

Deleting a snapshot

When nothing between them reads it, a snapshot’s versions are merged into the next newer ones with the engine’s Absorb: the newer version takes the blocks it lacks, by reference, and the older is deleted, in one log record. No data is copied. Versions nothing reads are deleted outright. Why: deleting snapshots is the hot background job when VMs are reset after every task; this way it costs index work, not device I/O.

Planned

  • Read-only attachments of snapshots, by several clients at once, with reads from any copy.
  • A host-wide read cache in the client library, for versions that can’t change.

tokio only on the control path

Raft, the cluster API, the installer and the CLI use tokio, on threads of their own, and pass changes to reactors over channels. They need TLS, HTTP/2 and gRPC, and none is latency-critical. Running openraft on the reactor was rejected: a runtime adapter would be large and risky for no gain.

A custom framed protocol between nodes

Every frame has a 32-byte header with its own CRC32C; block data travels after the body with a CRC per block. Every request carries the map and PG epochs. Alternative: NVMe-oF between nodes, which would need reservations and vendor commands for fencing. NVMe-oF is planned as a front end for clients instead.

Redirect-on-write on flash, deferral only on hard disks

See the data path. Deferral everywhere was the first design; measurement showed it cost about a third of batched 4 KiB write throughput on flash (85k against 133k writes per second at batch 128).

Cut CPU per operation before adding RDMA

Software costs 40–90 µs per request today, more than a TCP round trip on a fast network. Polling for 200 µs after each request took QD1 writes from 109 to 84 µs. Shorter polling (50 µs) gets about half the gain; it is the option for power-limited or shared-core hosts.

Protection and placement

Its own object store, not per-device volumes

Every device is an extent store of general objects with attributes and key–value tables, like Ceph’s RADOS with its object maps. Alternative: a thin volume manager per device (LVM-thin, SPDK logical volumes): every snapshot would then need coordination across replicas, and erasure coding doesn’t fit it.

4 MiB chunks, rendezvous hashing, placement by lineage

See placement. Alternative: CRUSH, which moves more data for erasure-coded pools and needs tuning.

Erasure coding through a replicated log (planned)

Small writes to an erasure-coded pool go to a three-copy log and are written out as full stripes later; full-stripe writes skip the log. Why: replica-like write latency, with no read-modify-write in the foreground.

Cache pools for data that can be recomputed

A third pool kind beside replicated and erasure-coded: one copy, no recovery, evicted by expiry then least recent use (eviction is planned). Why: replicating an inference engine’s offloaded KV cache wastes bandwidth on data that can be recomputed. Alternative: a replicated pool with one copy, which would still pay for recovery.

Comparison with other systems

System by system

Ceph

The closest relative: Hyperstor shares its model of placement groups, a primary per PG, map epochs, min_size, header objects for volumes and a blocklist for exclusive locks.

  • Different pieces: rendezvous hashing instead of CRUSH, Raft instead of Paxos monitors, and content digests instead of the PG log (why).
  • Map leases: a cut-off primary stops within one 0.6 s lease, and the same lease makes primary reads safe.
  • The data path Ceph is moving to: Crimson rebuilds the OSD as thread-per-core on Seastar. Hyperstor started there, on io_uring without Seastar or SPDK.
  • Snapshots: Hyperstor deletes a snapshot by handing its blocks to the newer version in one log record, without copying data, and resets a volume to its newest snapshot in place, which suits VMs reset after every task.
  • Behind: Ceph has erasure coding, S3, a filesystem, multi-site replication and years of production at scale. Hyperstor has none of these yet.

Longhorn and OpenEBS Mayastor

Kubernetes-native block storage. Both replicate whole volumes: Longhorn with an engine per volume, Mayastor through a “nexus” on SPDK.

  • Sharding: Hyperstor cuts every volume into chunks over all PGs, so one volume spreads its load and its recovery over the whole cluster.
  • Kernel bypass: Mayastor and Longhorn’s V2 engine take devices from the kernel with SPDK and poll whole cores; Hyperstor keeps the kernel driver and sleeps when idle, and has yet to show how close it gets to SPDK on NVMe.
  • Behind: both ship NVMe/TCP, Kubernetes integration, backups and a UI today.

LINSTOR and DRBD

DRBD replicates a block device in the kernel; LINSTOR places resources across nodes. Very low latency on two or three nodes, and decades of production.

  • Different scale model: DRBD’s unit is a whole device on a fixed set of nodes; Hyperstor’s is a 4 MiB chunk placed by hash, so data and recovery spread over every node.
  • Fencing: DRBD uses quorum and tiebreakers; Hyperstor uses map leases for primaries and volume leases with a blocklist for clients.

Portworx

Enterprise Kubernetes storage. Its internal key–value store can be down while I/O goes on, with volume operations blocked. Hyperstor’s map service is off the I/O path too, but storage nodes stop after one map lease without it: that is the price of bounding a stale primary, which is why the map service runs as three or five members.

Lightbits and simplyblock

NVMe/TCP block storage: Lightbits with its own userspace target, simplyblock on SPDK with erasure coding first. Both ship what Hyperstor plans: an NVMe-oF target and erasure-coded pools. Hyperstor’s difference is the same object layer under VMs (vhost-user-blk, without NVMe-oF in between), GPU-direct reads, S3 and a filesystem.

DAOS

An object store for HPC and AI, with Raft-replicated services and key–value semantics close to Hyperstor’s object layer. It depends on SPDK and libfabric, and targets POSIX and MPI-IO. Hyperstor is block first for virtual machines, on io_uring and RDMA verbs.

WEKA and VAST Data

Parallel file and object systems for AI, both on NVIDIA’s GPUDirect Storage list. WEKA bypasses the kernel with DPDK; VAST separates stateless servers from shared flash enclosures and protects data with very wide codes.

  • GPU-direct: Hyperstor plans to keep the cuFile and hipFile APIs but move data by RDMA straight into GPU memory registered through dma-buf, which works for NVIDIA and AMD GPUs alike, in one hop to the storage node. Unmodified GDS programs keep a kernel NVMe-oF path. None of this is built.
  • Behind: both are qualified and in production for GPU clusters.

MinIO AIStor

S3 object storage. AIStor ships S3 over RDMA (the x-amz-rdma-token extension) into GPU memory. Hyperstor plans the same extension on its S3 gateway, with the transfer made by the storage nodes that hold the data, so the gateway stays off the data path.

Restarts

Stopping or restarting the service doesn’t detach its volumes. It keeps them in DIR/state.json, and its next start takes them back and opens their sockets again; the hypervisors reconnect and the guests carry on, after a pause of about 4 s. Requests the guest had in flight are run again from the hypervisor’s in-flight buffer. Cloud Hypervisor reconnects by itself; give QEMU’s chardev reconnect=1 (QEMU 9.2 and later: reconnect-ms=1000). A volume another node took while the service was down is left to it.

The state file is in the runtime directory: a reboot clears it, and with it the VMs that used the volumes. To stop the service for good, detach its volumes first (ctl detach); a stopped service’s volumes stay held. hyperstor-install uninstall and --no-vhost do this.

hyperstor-install --vhost installs it as hyperstor-vhost.service (see hyperstor-install).

Logins

People log in with their user name and password on the host (PAM service hyperstor); they must be in the group hyperstor-users. A first login makes an account with no roles. What a role allows:

RoleMay
viewerRead: status, PGs, volumes, snapshots, operations, members, the dashboard
operatorAlso take devices out and in, drain nodes, cancel operations, take snapshots, restore from the trash
storage-adminAlso create and delete volumes and snapshots, clones, roll volumes back, purge the trash and set its grace periods, add and remove members
security-adminPeople and their roles, join tokens, certificates, map backups, the audit log; nothing else

Everyone may make API tokens for themselves. Deleting a volume, a snapshot or a member, rolling a volume back, purging the trash or changing its grace period, changing how long the audit log is kept, making a join token or an API token, revoking a certificate, fetching a map backup, and changing people’s roles need a login of the last 10 minutes; an API token is never fresh enough for these.

The first security administrator. While no one is one, the service prints a claim code to its log (journalctl -u hyperstor-mgmt), valid for an hour: whoever logs in with it becomes the first. Restarting the service prints a new one while the cluster is unclaimed.

Sessions last 12 hours, or 30 minutes idle. They are kept, with accounts and tokens, in the map service’s store, so they outlive a restart of hyperstor-mgmt.

Protections

  • It answers only requests whose Host is one of its names on its port (against DNS rebinding).
  • The session cookie is HttpOnly; SameSite=Strict (and Secure over HTTPS). A write with the cookie must send its CSRF value in X-Hyperstor-CSRF, and a write from another site’s Origin is refused.
  • Pages carry a strict Content-Security-Policy and may not be framed.
  • Every login and every change is audited on standard error as a JSON line with the person (user:NAME) and how they logged in, and sent to the cluster’s audit log in .meta. mgmt names the person to the map service (X-Hyperstor-On-Behalf-Of, believed only from mgmt’s certificate), whose audit then reads …/mgmt/dashboard for user:NAME; a browser’s own such header is dropped.

Cluster API

hyperstor-meta --api ADDR serves the cluster API, hyperstor.v1, which hyperstorctl uses. One service answers the Connect protocol (JSON or protobuf over HTTP/1.1 or HTTP/2), gRPC and gRPC-Web, so any of these work: curl, grpcurl (with the proto file), generated clients.

The definitions are cluster.proto (ClusterService) and admin.proto (TokenService, CaService, NodeService, OperationService), in crates/hyperstor-api/proto/hyperstor/v1/.

Security

With --api-tls, the API speaks only TLS. Every call but Join needs a client certificate issued by the cluster’s CA, whose identity (hyperstor://<cluster>/<role>/<id>) decides what it may do:

RoleMay
admin (hyperstorctl), mgmtEverything
node, metaRead (GetStatus, ListPgs, ListVolumes, ListTokens, GetOperation, ListOperations, DrainNode with dry_run), and renew their own certificate
hostRenew its own certificate; nothing else

A certificate of another cluster is refused, and so is a revoked one: RevokeCertificate (hyperstorctl cert revoke) puts its serial on a list every map service member checks, on the API and between members, until the certificate would have expired. hyperstor-install makes the certificates in /etc/hyperstor/pki.

Joining. Join is the only call without a client certificate: a single-use token from CreateToken authorizes it. The joining host pins the cluster’s root by the fingerprint the token carries before it sends anything, and sends a certificate request for a key it keeps; the token decides the identity it gets. Tokens are kept in the map service’s replicated store, only their SHA-256, so they survive restarts and work through any member; the leader makes, uses and revokes them (another member refuses with not_leader and changes nothing). Before the map service has its first map, only its first member makes tokens, and only meta ones, for the other members to join.

Local socket. With --api-socket, the API is also served on a Unix socket (/run/hyperstor-meta/api.sock when installed). There the kernel names the caller: root, the service’s user and members of hyperstor-admin may do everything, others nothing. It is the way in when certificates are broken; its use is audited like any other.

Without --api-tls the API is plain HTTP and accepts every request: only for loopback and tests.

Audit. Every change (SetDeviceIn, CreateVolume, ExpandVolume, DeleteVolume, the snapshot calls but ListSnapshots, CreateToken, RevokeToken, Join, RenewCertificate, RevokeCertificate, DrainNode, CancelOperation) and every refused call is written as one JSON line on the map service’s standard error, which systemd keeps in the journal:

journalctl -u hyperstor-meta | grep '{"audit":1'

{"audit":1,"time":1792561403.512,"principal":"hyperstor://7311402/admin/local","op":"SetDeviceIn","target":"device 2 up_in=false","result":"ok, map epoch 5"}

Rate limit. Each caller may make 200 calls per second, in bursts of up to 1000; more are refused with resource_exhausted.

What the answers mean

  • Reads (GetStatus, ListPgs) come from the published map: what storage nodes and clients see.
  • SetDeviceIn changes the map service’s working map. The change is published once the devices losing roles have been fenced, usually within a second, and GetStatus then shows the PGs moving.
  • Health is HEALTH_ERROR when a PG can’t take writes (fewer copies than the pool’s min, or no primary), HEALTH_WARN while a node is down, a device is out, or PGs are degraded or backfilling, and HEALTH_OK otherwise. Each reason is listed. A node the map service hasn’t heard from since it started is also HEALTH_WARN: the map counts it up for a short grace period after a restart.
