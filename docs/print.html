Hyperstor

Introduction

Hyperstor is a sharded, distributed storage system written in Rust. It stores data on many storage nodes, keeps two or three copies of every piece, and keeps serving reads and writes when a node fails. It is built for glidex clusters and also runs on its own.

Early implementation. Hyperstor is not ready for production data. Today it provides replicated block volumes over TCP, used through a Rust client library, as virtual machines’ disks over vhost-user-blk, or, for testing, as Linux block devices through ublk, with failure handling, snapshots and clones, and tools to install and manage a cluster. There is no front end for remote hosts yet (NVMe over TCP), and the data path between clients and storage nodes has no authentication or encryption (the cluster API, the map service’s members and the management service use TLS). See Status for what is built and what comes next.

What it does today

  • Replicated pools. Data is split into chunks, and each chunk is written to two or three storage nodes in different failure domains (devices, hosts or racks). A write returns once every copy has it. Pools are made, changed and deleted while the cluster runs, on the device classes they name (nvme, ssd, hdd, or your own), and their placement groups are split as devices are added.
  • Cache pools keep one copy of data that can be recomputed: a failed device’s data is lost instead of recovered. Expiry and eviction are not built yet.
  • Devices at run time. Devices are added to and removed from running nodes. Each device gets data in proportion to its size. A device past its full threshold refuses new data, while overwrites and deletes go on, so space can always be freed.
  • Its own storage engine. Each storage device is driven directly through Linux io_uring, with checksums on every 4 KiB block and crash recovery.
  • Failure handling. The map service notices when a node stops answering, moves its work to other nodes, and refills a node when it comes back with only what it missed. A short reboot moves no data, and a node that keeps going down and up is held down. A failed device, or a replica too slow to answer, is replaced at once. A background scrub compares the copies and repairs one that is damaged or differs.
  • A replicated map service. Three or five members keep the cluster map with Raft, so losing one doesn’t stop the cluster.
  • Volumes with one writer at a time: a client attaches a volume by holding its lease, and one that dies is fenced off when another takes the volume over. Each attached volume is fenced on its own, so taking one volume from a client leaves its others alone.
  • Snapshots and clones. Crash-consistent snapshots of one volume or of a group at one instant, instant clones and rollbacks, and snapshot deletion that moves no data. Deleted volumes and snapshots go to a trash first.
  • Virtual machine disks. hyperstor-vhost serves volumes to the VMs of a host over vhost-user-blk. VMs boot from them under Cloud Hypervisor and QEMU, and restarting the service keeps their disks.
  • Block devices for testing. hyperstor-ublk serves a volume as /dev/ublkbN, for mkfs, mount and fio.
  • A client library for Rust programs to read and write volumes, with a read cache that the clones of one image on a host share.
  • Administration. hyperstor-install installs a trial cluster on one host, or a cluster across hosts that join with single-use tokens. hyperstorctl and a web UI manage it, with people’s logins (a password or an identity provider), roles, an audit log, and long operations such as draining a node.

What is planned

NVMe over TCP and RDMA, erasure coding, GPU-direct storage, hard-disk pools with flash log devices, expiry and eviction in cache pools, an S3 gateway and a distributed filesystem, all on the same object layer. The Status page lists the milestones.

Quick start

The easiest start is the installer, which sets up the map service, three storage nodes, hyperstorctl and the dashboard on one host, as system services, after the build below: sudo target/release/hyperstor-install install --all-in-one (see Installing a trial cluster). The steps here run the same kind of cluster by hand, installing nothing, to show its parts.

This starts a cluster of three storage nodes and a map service on one Linux machine, writes to it, and shows a node failure. It needs the build requirements and about 3 GiB of free disk space.

1. Build

git clone https://github.com/CMKL-APEX/hyperstor
cd hyperstor
cargo build --release

The binaries are in target/release/. This page uses hyperstor-meta (the map service), hyperstord (a storage node) and hyperstor-bench (a load generator); the reference describes the others.

2. Describe the cluster

The cluster file lists the storage nodes, the address each one listens on, and the pools:

cat > cluster.txt <<'END'
cluster 1
node 0 rack 0 127.0.0.1:19100
node 1 rack 0 127.0.0.1:19200
node 2 rack 0 127.0.0.1:19300
pool 1 vol replicated size 3 min 2 pgs 128 chunk 4194304 domain host
END

Pool 1 keeps three copies of every 4 MiB chunk, each on a different node, and accepts writes while at least two copies are reachable.

3. Start the services

target/release/hyperstor-meta --listen 127.0.0.1:19000 --cluster cluster.txt &
for n in 0 1 2; do
  target/release/hyperstord --node $n --meta 127.0.0.1:19000 \
    --shard 127.0.0.1:19$((n+1))00=/var/tmp/hs-n$n.img:1 &
done

Each storage node creates a 1 GiB file as its device and formats it on first start.

4. Write and read

hyperstor-bench remote connects as a client, writes and reads for a few seconds, and prints the throughput as table rows:

HS_BENCH_SECS=2 target/release/hyperstor-bench remote 127.0.0.1:19000

5. Fail a node

Stop one storage node and run the load again:

kill %2          # the first hyperstord
sleep 5
HS_BENCH_SECS=2 target/release/hyperstor-bench remote 127.0.0.1:19000

Within a second of the node stopping, the map service marks it down and the other nodes take over as primaries of its placement groups; writes then go on with two copies. Start the node again with the same command and it is refilled with the writes it missed (see Failures and recovery).

6. Clean up

kill $(jobs -p)
rm /var/tmp/hs-n?.img cluster.txt

The cluster map

The map describes the whole cluster: its nodes, their devices, the pools and where each placement group lives. Every node and client holds a copy and computes data locations from it, so no lookup is needed per I/O. Each change to the map has a new epoch number; a node or client with an older map is told so and fetches the new one.

Nodes, devices and shards

A node is one hyperstord process. It drives one or more devices: files or block devices, each served by its own thread (a reactor, pinned to a CPU if you choose) that listens on its own TCP port. In the cluster file, each address listed for a node is one device. Node N’s devices are numbered N × 1000, N × 1000 + 1 and so on; a number is never given again once its device is removed. Devices can be added to and removed from a running node.

Each device has:

  • a class: its kind (nvme, ssd, hdd, or file for a device file) unless an administrator sets another name;
  • a weight: by default its capacity in TiB, from the device’s own reports, so a device twice the size gets twice the data.

Pools

A pool is a set of data with one protection rule:

  • kind: replicated, or cache for data that can be recomputed;
  • size: how many copies of each chunk (2 or 3; 1 by default in a cache pool);
  • min: how many copies must be reachable to accept a write;
  • failure domain: what the copies must not share: a device, a host or a rack;
  • classes: the device classes it places data on, or every device;
  • chunk size: how volumes in the pool are cut into chunks.

Pools can be made, changed and deleted while the cluster runs. A pool’s usable space is its devices’ space divided by its copies, counting only what fits with each copy in a different failure domain.

A cache pool gives up durability for speed and space. A device or node that fails loses its data: nothing is recovered, and a volume reads zeros where its data was. A node that is only down for a moment (a restart) keeps its share: the pool waits for it up to its grace period, 60 seconds by default. Expiry and eviction are not built yet, so a full cache pool refuses new data as other pools do.

Placement groups

A pool is divided into a number of placement groups (PGs), a power of two. Each chunk belongs to one PG, by a hash of its name, and each PG is stored on size devices, its acting set. The first device of the acting set is the PG’s primary: clients send it reads and writes, and it forwards writes to the other copies. When a node fails, only the PGs it held move. As devices are added, the map service doubles a pool’s PG count, unless turned off for the pool: each PG is split in place, then the new PGs move to devices of their own.

Full devices

Each device is held to three thresholds, percentages of its space, the same across the cluster:

ThresholdDefaultPast it
nearfull85 %Health warns
backfillfull90 %No PG is copied onto the device
full95 %The device refuses new objects and writes to blocks not yet written

Overwrites of written blocks and deletes still work past full, so space can always be freed. A pool is as full as the fullest device it uses, and a full pool takes no new volumes, clones or snapshots.

Volumes

A volume is a sparse range of bytes in a pool, with a 128-bit id, a size and a name. The cluster keeps a header for each volume, and its chunks are created as they are written: blocks never written read as zeros. Offsets and lengths are multiples of 4 KiB. A volume is used through the client library, as a VM’s disk through hyperstor-vhost, or as a Linux block device through hyperstor-ublk (see Using Hyperstor).

Snapshots and clones

A snapshot keeps a volume as it was at one instant. Taking one only moves the volume’s epoch on: later writes go to new versions of the chunks, tagged with the new epoch, and the snapshot reads the versions up to its own. So a snapshot copies nothing, and a clone is a new volume that reads through its snapshot’s versions until it writes its own. A consistency group snapshots several volumes at one instant.

The trash

Deleting a volume or a snapshot through the cluster API, hyperstorctl or the web UI moves it to the trash: it can’t be attached, but its data stays, and counts against the pool, for the pool’s grace period (a day by default). Until then it can be restored; after it, the map service purges it. See The trash.

The read cache

A version of a chunk that is no longer a volume’s newest (a snapshot’s, or a clone’s parent’s) never changes. The client library caches blocks of such versions in memory, shared by every volume it serves, so the VMs of a host that boot clones of one image read it from the cluster once.

Volume leases and the blocklist

One client at a time attaches a volume, by holding its lease, which it renews every second. To take a volume from a client that died or is cut off, another client waits for the lease to run out and blocklists the old lease: every storage node refuses requests made under it from then on. So a volume never has two writers. Each attached volume has a lease of its own, so taking one volume from a client leaves its other volumes alone. The holder can let delegates, such as a library inside a VM, act under its lease; they are cut off with it.

Map leases

A storage node may act as a primary only while it holds a current map lease from the map service, renewed by its heartbeats. A node cut off from the map service stops serving before the map service gives its PGs to other nodes, so two nodes never both accept writes for one PG.

Down and out

A node that stops answering is down: its PGs go on with the other copies, and nothing is copied, so a reboot moves no data. A node that keeps going down and coming back is held down a little longer each time, and health warns that it flaps. A device that is out, because its node has been down for ten minutes, it failed, or an administrator took it out, gets no placement, and its PGs are copied to other devices.

The client library

hyperstor-client is a Rust crate. It holds a copy of the cluster map, keeps connections to storage nodes, splits each request at chunk boundaries, sends the pieces in parallel to their primaries, and retries when the map changes.

Adding the dependency

The crate is not on crates.io yet. Depend on it from git, with the reactor it runs on:

[dependencies]
hyperstor-client = { git = "https://github.com/CMKL-APEX/hyperstor" }
hyperstor-reactor = { git = "https://github.com/CMKL-APEX/hyperstor" }

Pin a revision (rev = "...") while the API is changing.

The reactor

The client runs on Hyperstor’s own io_uring reactor, not on tokio or another async runtime. hyperstor_reactor::block_on runs a future, and everything it spawns, on the current thread. A Client belongs to the thread that created it (it is not Send); use one client per thread.

Writing and reading

use hyperstor_client::Client;
use hyperstor_reactor::block_on;

fn main() {
    let meta = "127.0.0.1:19000".parse().unwrap();
    block_on(async move {
        // The second argument identifies this client to the cluster.
        let client = Client::connect(meta, 1).await.expect("connect");

        let pool = 1;
        let volume: u128 = 0x1234;
        let data = vec![0xab; 64 * 1024];

        // Offsets and lengths are multiples of 4096.
        client.write(pool, volume, 0, data.clone()).await.expect("write");
        let back = client.read(pool, volume, 0, 64 * 1024).await.expect("read");
        assert_eq!(back, data);
    });
}
  • Client::connect(meta, id) fetches the map from the map service at meta. With several map service members, use Client::connect_members(vec![a, b, c], id): any member serves the map, and requests only the leader answers follow its redirects.
  • write(pool, volume, offset, data) returns once every reachable copy of every chunk touched has the data (see guarantees).
  • read(pool, volume, offset, len) returns len bytes; blocks never written are zeros.
  • map() returns the client’s current copy of the cluster map, for example to list pools.

The full API is in the client API reference.

Volumes

write and read above address a lineage directly: nothing records that it exists, and nothing stops two programs from writing to it at once. Programs that share a cluster use volumes, which the cluster keeps a record of, and which one client at a time attaches:

#![allow(unused)]
fn main() {
// Create a 1 GiB volume in pool 1, with a random id (or Some(id)).
let v = client.create_volume(1, 1 << 30, None, "scratch").await?;

// Attach it: take its lease. I/O goes through the handle.
let disk = client.attach(v.id).await?;
disk.write(0, vec![0xab; 4096]).await?;
let back = disk.read(0, 4096).await?;
disk.detach().await?;
}
  • create_volume(pool, size, id, name) makes the volume’s header; the size is a multiple of 4096. A retried create is recognised, not doubled. volume(id), list_volumes(pool), expand_volume(id, size) (volumes don’t shrink) and delete_volume(id) manage them; hyperstorctl does the same for administrators.
  • A Volume’s state is Active, Trashed (see The trash) or Deleting (a delete under way, or one that stopped half-way: delete it again to finish).
  • Ids are 128-bit, chosen by you (for example a disk’s UUID) or drawn at random. Names are shown, not unique.

Attaching a volume

attach(id) takes the volume’s lease. The client renews it every second in the background, and a lease not renewed for 4 s runs out. While one client holds it, another’s attach fails with LeaseHeld.

  • detach() gives the lease up. A handle dropped without it stops renewing, and its lease runs out.
  • take_over(id) attaches a volume whose holder has died or is cut off: it waits for the holder’s lease to run out, blocklists that lease, then takes it. From then on every storage node refuses requests made under the old lease, so none of the old holder’s writes can land after the new holder’s. A holder that is still renewing is left alone (LeaseHeld).
  • preempt(id) takes a volume from a live holder, for example one an operator moves: it blocklists the holder’s lease first. Only that volume’s lease is cut off: the old holder’s other volumes go on, and it can attach the volume again later.
  • lease() is the handle’s lease identity, which every request through it carries.
  • set_lease_label(label) sets a short label (up to 64 bytes) recorded with every lease the client takes, and attach_as(id, how, label) sets one lease’s. LeaseHeld and a volume’s holder_label give it, so whoever finds a volume held knows what holds it.
  • Delegates act under a holder’s lease from another client, such as a library inside a VM: add_delegate() on the holder’s handle returns a new identity, and Client::delegate(id, identity) opens the volume with it there. A delegate renews nothing. It is cut off when the holder removes it (remove_delegate), detaches, or loses the lease to a take-over, and a snapshot waits for it to pause as for the holder.
  • Once a handle’s lease is lost, its I/O fails with LeaseLost, and lost() returns true.
  • An attached volume can’t be deleted (VolumeAttached); detach it first, or use force_delete_volume(id), which preempts the holder.
  • Read-only attachments (of snapshots, by several clients at once) are planned.

Snapshots and clones

#![allow(unused)]
fn main() {
let snap = client.snapshot(v.id, "before-upgrade").await?;   // crash-consistent
let copy = client.clone_snapshot(v.id, snap.epoch, "copy", None).await?;
client.rollback(v.id, snap.epoch).await?;                    // detached volumes only
client.delete_snapshot(v.id, snap.epoch).await?;
}
  • snapshot(id, name) takes a crash-consistent snapshot: the volume as it would be after a power cut at one instant. If a client has the volume attached, its writes are paused while the snapshot is cut, at most 2 s; past that the snapshot is abandoned (Server with code Busy), and you can try again. A snapshot is identified by its epoch; volume(id) lists them in snapshots.
  • snapshot_group(ids, name) takes a snapshot of several volumes at one instant (a consistency group), for example a database’s data and log volumes; delete_group removes them all.
  • clone_snapshot(id, epoch, name, new_id) makes a new volume from a snapshot at once: it shares the snapshot’s data, and writes to the clone go to its own copies.
  • rollback(id, epoch) returns a detached volume to a snapshot. To the newest snapshot it is done in place and is instant.
  • flatten(id) copies into a clone what it still reads from its parents, so they can be deleted.
  • delete_snapshot(id, epoch) merges the snapshot’s data into what still needs it, without copying blocks, and is refused (SnapshotInUse) while a clone or a rollback depends on it.

The trash

delete_volume(id) and delete_snapshot(id, epoch) delete at once. The cluster API, hyperstorctl and the web UI move what they delete to the trash instead, where the map service purges it after the pool’s grace period. A program can do the same:

#![allow(unused)]
fn main() {
client.trash_volume(v.id, false).await?;      // true: preempt a holder first
client.restore_volume(v.id, None).await?;     // or Some("new-name")
client.purge_volume(v.id).await?;             // only from the trash
}
  • trash_volume(id, force) moves a volume, with its snapshots, to the trash. An attached volume is refused (VolumeAttached) unless force, which preempts its holder.
  • restore_volume(id, name) brings it back, under its own name, or NAME-restored if another volume of its pool took the name meanwhile.
  • purge_volume(id) deletes a trashed volume for good; an active one is refused (Refused).
  • trash_snapshot(id, epoch), restore_snapshot(id, epoch), purge_snapshot(id, epoch) and trash_group(group) do the same for snapshots and consistency groups.
  • list_volumes(pool) returns trashed volumes too, with their state; hyperstor_client::trash::trash_of(&volumes) picks out what is in the trash.

The read cache

Each Client keeps a read cache in memory, 256 MiB by default, shared by every volume it has attached. It holds only blocks of versions that can no longer change: a snapshot’s, or the parent’s that a clone reads through. So clones of one image, attached by one client (for example by hyperstor-vhost for the VMs of a host), read the image’s blocks from the cluster once. A volume’s own newest writes are never cached, so the cache never needs invalidating.

  • set_read_cache_bytes(bytes) sets its size; 0 turns it off.
  • read_cache_stats() returns its hits, misses and blocks held.

The cache is new and still being completed.

Data guarantees and errors

What a successful write means

When write returns Ok, every copy of the data that the pool’s PGs currently use has written it to its device and flushed it. Normally that is size copies; while a node is down, it can be as few as the pool’s min. A write that returned Ok survives a crash or power loss of any node holding a copy, and the failure of all but one of its copies.

A write that returns an error may have reached some copies and not others. Write the same data again: writes to a range are idempotent.

Order and concurrency

  • A read that starts after a write returned sees that write.
  • Two writes in flight at the same time to overlapping ranges land in an order you can’t choose. Wait for one before starting the other if the order matters.
  • A write that spans several chunks is not atomic across them: after a failure, some chunks may have the new data and others the old.

Integrity

Every 4 KiB block carries a CRC32C checksum from the client to the device and back. A block that doesn’t match its checksum is never returned as data. When the primary’s copy is damaged, the primary reads another copy, repairs its own and returns the good data. If no copy is good, the read fails (Server with code Checksum); Checksum on its own means the data was damaged on the way to the client.

A read that waits too long for a slow device (2 s by default) is served from another copy instead; if none answers, the client retries it as it does Unavailable.

Full devices

A device past its full threshold (95 % by default, set by the administrator) refuses writes that would take more of its space: writes to blocks never written, and new objects. They fail with Server and code NoSpace, which the client does not retry. Overwrites of written blocks, deletes and snapshot deletes still work, so space can always be freed. A pool is full while any device it uses is, and the cluster API then refuses new volumes, clones and snapshots in it; the client library’s own calls don’t check this.

hyperstor-ublk passes NoSpace to its block device as ENOSPC. hyperstor-vhost holds the write instead and tries it again every second for up to 5 minutes (its --hold-full), so the VM sees no error if space is freed in time; after that the guest gets an I/O error. See Full devices.

Volumes and leases

A volume attached through attach, take_over or preempt has one writer at a time. After a take-over or preemption, the old holder is refused by every storage node, so no write of its lands after the new holder’s first write. A write that failed with LeaseLost may have landed or not.

Snapshots

A snapshot holds every write acknowledged before it was cut, and none issued after. A write in flight while it is cut is in it or not, as after a power cut. A consistency group gives the same guarantee across all its volumes at one instant. Writes to a clone never change its snapshot, and writes to the volume never change its snapshots.

Errors

The client already retries what is worth retrying: a map change, a primary that moved, a PG with no reachable primary, too few copies reachable (Unavailable), a dropped connection. It refreshes its map between attempts and gives up after 20 attempts, about two seconds. A node failure takes a few seconds to detect (see the administrator’s failures page), so a program should be ready to retry an Exhausted error itself.

Running a cluster

A Hyperstor cluster today is:

  • the map service (hyperstor-meta): one member, or three or five that keep the map together. It holds the cluster map, detects failed nodes, grants map leases and serves the cluster API;
  • three or more storage nodes (hyperstord), each with one or more devices;
  • the management service (hyperstor-mgmt) on a map service host: the web UI, people’s logins, and the cluster API on their behalf;
  • on hosts that run VMs, hyperstor-vhost, which serves volumes to them as disks;
  • clients: programs using the client library, hyperstor-ublk and hyperstorctl.

The cluster is described by one text file, the cluster file, read by the map service at start. Hosts can also join a running cluster with a token, and devices and pools can be added and removed while it runs.

Security. The cluster API needs a client certificate (mutual TLS), and the management service a login. The map service’s and the storage nodes’ data ports have no authentication and no encryption yet: anyone who can reach them can read and overwrite every volume. Run clusters only on an isolated network that untrusted hosts cannot reach, and keep test data only.

Installation

There are no packages yet: build the binaries from source and copy them to each machine.

Requirements

  • Linux on x86-64 (other architectures are untested), with io_uring enabled. hyperstor-install check fails below Linux 5.19 and warns below 6.1, which is what Hyperstor is tested on. Some distributions turn io_uring off with the kernel.io_uring_disabled sysctl; it must be 0.
  • Rust 1.88 or later, with cargo.
  • For storage devices: a filesystem that supports O_DIRECT for device files, or whole block devices.
  • For the web UI: bun, to build it (optional; without it, the management service serves a simpler built-in dashboard).
  • TCP connectivity between all storage nodes, and from clients to the map service and to every storage node; UDP too between storage nodes (see Planning a cluster). See the security note in Running a cluster.

Installing a trial cluster

hyperstor-install sets up a whole cluster on one Linux host: the map service with its cluster API, three storage nodes on files, a pool with three copies and a cache pool, systemd units, and hyperstorctl. It is for trying Hyperstor and testing changes, not for data you want to keep.

cargo build --release
target/release/hyperstor-install check           # host checks, changes nothing
sudo target/release/hyperstor-install install --all-in-one
hyperstorctl status
hyperstorctl io-test

check reports each requirement as ok, info, warn or FAIL. On a storage host whose devices have endpoints, it also warns about endpoint addresses that share a subnet with another port and have no routing rule of their own (routing). install runs the checks, copies the binaries to /usr/local/bin, creates the hyperstor user, writes the configuration in /etc/hyperstor, the cluster’s certificates in /etc/hyperstor/pki, and the units, and starts hyperstor-meta, hyperstord@0 to hyperstord@2, the management service hyperstor-mgmt and its password helper hyperstor-authd. The cluster API (8850), the map service (8849) and the storage nodes (9100 to 9102) listen on 127.0.0.1; the management service listens on every address over HTTPS, on 8852 (--mgmt-listen loopback keeps it on 127.0.0.1). Device files go to /var/lib/hyperstor (4 GiB each, sparse).

The installer is convergent: run it again after rebuilding and it updates what changed (binaries, configuration, units) and restarts the services affected; with nothing changed it says so and does nothing. The options of the last run are saved, so sudo hyperstor-install install is enough later. sudo hyperstor-install uninstall stops and removes the services and binaries and keeps the configuration and data. All options are in the reference.

hyperstorctl needs the administrator certificate, readable by root and the hyperstor-admin group: run it with sudo, or join the group (sudo usermod -aG hyperstor-admin $USER, then log in again).

To log in to the web UI, see Logins and roles. Then see Managing a cluster.

Joining hosts with tokens

Install the map service on one host first. It makes the cluster’s certificates and serves the cluster API on its own address, where the other hosts reach it:

# on the map service's host (192.0.2.10); the cluster file may list no
# storage node at all: they join
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role meta --map 192.0.2.10:8849

Then, for each storage host, make a token on the map service’s host and use it on the new host:

# on the map service's host; umask 077 keeps the file private
(umask 077; sudo hyperstorctl token create --role node > token)
# copy `token` to the new host, readable by root only, then there:
sudo target/release/hyperstor-install install --join 192.0.2.10:8850 \
    --token-file token --role storage --address 192.0.2.21 --reactors 2

The new host pins the cluster by the root fingerprint in the token before it sends anything, makes its own key (which never leaves it), and gets a certificate for a new storage node number. The map service adds the node to the map, down until its first heartbeat, and its PGs start moving to it once it runs. The node gets one reactor per --reactors, each on a file of --size-gib GiB in the data directory and on its own port from --node-port, and its metrics on --address at port 8853.

  • A token is used once, expires after an hour (--ttl SECS, at most a week), and can be revoked with hyperstorctl token revoke --id ID; hyperstorctl token list shows them, never the secrets. Tokens are kept in the map service’s replicated store, so they survive restarts; they are made and used through the leader.
  • The token is never saved. Later runs of the installer, such as the daily timer’s, need none; they renew the host’s certificate through the API with the certificate itself.
  • Installing a host again with the same addresses gets its node back.

Several map service members. Install the first member with the whole member list, then join the others with meta tokens; they get the cluster file, the root’s certificate and the intermediate CA, so every member signs with the same CA (the root’s key stays on the first host):

M=1=192.0.2.10:8851/192.0.2.10:8849,2=192.0.2.11:8851/192.0.2.11:8849,3=192.0.2.12:8851/192.0.2.12:8849
# first member
sudo hyperstor-install install --cluster cluster.txt --role meta --members $M --member-id 1
(umask 077; sudo hyperstorctl token create --role meta > token-2)
# second member (and likewise the third)
sudo hyperstor-install install --join 192.0.2.10:8850 --token-file token-2 \
    --role meta --members $M --member-id 2

A member’s host can also run a storage node: list the nodes in the cluster file, and give each member --role both --node N (the first with --cluster, the others with --join); a joined member gets the file, and so its node, from the first:

sudo hyperstor-install install --cluster cluster.txt --role both --node 0 \
    --members $M --member-id 1
sudo hyperstor-install install --join 192.0.2.10:8850 --token-file token-2 \
    --role both --node 1 --members $M --member-id 2

--node is checked before the token is sent, so a run refused for it leaves the token usable.

Tokens are made and used through the leader; the other members refuse with the leader’s address. Before the members have formed a group, the first member makes the meta tokens itself.

Back up the root CA’s key on the first host, which alone has it (see hyperstor-install):

sudo hyperstor-install root-backup --out /media/usb/root.bak --passphrase-file pass

Installing a cluster across hosts from one file

Without tokens, write the cluster file once, copy it to every host, and install each host’s part of it:

# on the map service's host (192.0.2.10)
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role meta --map 192.0.2.10:8849
# on each storage host, with its node number from the file
sudo target/release/hyperstor-install install --cluster cluster.txt \
    --role storage --node 0 --map 192.0.2.10:8849

A storage node gets one reactor for each address the cluster file lists for it. Adding a host means editing every copy of the file. Storage hosts installed this way get no certificate; joined ones do, though the storage network doesn’t use them yet: it has no authentication (see Running a cluster).

Hosts that run VMs

hyperstor-vhost serves volumes to the VMs on a host, for glidex’s hyperstor datastores. Add it to a host’s role, or install a host that only runs VMs:

sudo hyperstor-install install --vhost --vhost-user glidex          # with what the host runs already
sudo hyperstor-install install --role vhost --map 192.0.2.10:8849 --vhost-user glidex

--vhost-user glidex lets glidex’s control plane attach volumes and its hypervisors open their sockets. Restarting the service (an upgrade, say) keeps the VMs’ disks; --no-vhost and uninstall detach them first. See VM disks.

Planning a cluster

Nodes and devices

  • Use at least as many storage nodes as the largest pool’s size, in distinct failure domains, plus one so that a failed node’s data can be copied to a stand-in (see Failures and recovery). Three nodes run a three-copy pool; it keeps working with two copies while one node is down, but can’t restore the third until the node returns.
  • Give each node one device per CPU core you want to dedicate to storage. Each device has its own thread and its own port.
  • Device files grow up to the size given to hyperstord as data is written. Keep that much room on the filesystem.
  • Devices of different sizes are fine: each gets data in proportion to its capacity (its weight; see Device weights).
  • Nodes, devices and pools can be added and removed later, while the cluster runs (see Managing a cluster): start with what you have.

Node numbers and addresses

Every node has a number, unique in the cluster, and one address per device. The addresses in the cluster file and the --shard options of hyperstord must match, in the same order: the first address listed for node 3 is node 3’s first --shard. Devices are numbered node × 1000 + i; an address can name its device’s number instead (1002@192.0.2.21:9102). Numbers are never given again once a device is removed. Hosts that join with a token get their numbers from the map service.

Device classes

Each device has a class: its kind (nvme, ssd, hdd, or file for a device file) unless you set another. A pool that names classes places its PGs only on those devices, so one cluster can hold a fast pool on NVMe and a large one on hard disks. A pool mixing hard disks and flash is refused unless forced: a replicated write waits for its slowest copy. See Device classes.

Capacity

  • Usable space. A pool’s usable space is its devices’ space divided by its copies, counted so that no failure domain holds more than one copy of a PG: with as many hosts as copies, the smallest host bounds the pool. Pools that share devices share their space.
  • Volumes are thin. A volume takes space only as it is written, so the volumes in a pool can add up to more than the pool holds. Watch the space (hyperstorctl pools, the web UI) rather than the volumes’ sizes.
  • Thresholds. Health warns when a device passes 85 % (nearfull), devices past 90 % take no backfill (backfillfull), and past 95 % (full) a device refuses new data. See Full devices.
  • Room to recover. When a host is lost for good, its data is copied onto the others. Keep enough free space below backfillfull on the remaining hosts to hold one host’s data, or the copies wait for room.
  • The trash. Deleted volumes and snapshots keep their space for their pool’s grace period (a day by default). See The trash.

The map service

Run three members on three hosts (five for large clusters), so that the map survives a lost host; one member is a single point of failure. The installer runs the management service on the map service’s hosts. See The map service.

Network

Each storage node device needs one port reachable from every client and every other storage node, for TCP and for UDP: storage nodes ping each other over UDP at the same port number, and fall back to TCP for a peer that doesn’t answer (a firewall that drops UDP makes failures slower to notice under load). The map service needs one TCP port reachable from all of them, and its members one more between themselves. Pick ports and firewall rules accordingly, and keep the storage network isolated (see Running a cluster).

Several networks

A host with several network ports (a management port, and fast storage or InfiniBand ports) can carry reads, writes and replication on the fast ones and keep the rest on the management network:

  • Declare the networks in the cluster file, each control, data or both.
  • Give each device one or more endpoint lines on a data network. The device’s own address (on its node line) stays where the map service and pings reach it.
  • Install as usual. Each storage node then also listens on its devices’ endpoints, and reaches the other nodes at their endpoints on the data networks it has endpoints on.
  • Clients choose too: hyperstor-vhost --networks for VM disks. A client on no network uses devices’ addresses.

Put each endpoint on a port close to its device: on the same PCIe switch or, failing that, the same CPU socket. With several ports in one subnet (InfiniBand ports often are), Linux sends from every address through one of them unless each address has a routing rule of its own; add those, or traffic leaves by one port; hyperstor-install check warns about endpoints without one.

Choosing endpoints for you, from the host’s topology, and moving traffic between ports as load changes are planned.

Managing a cluster

hyperstorctl talks to the cluster API. On a host set up with hyperstor-install it finds the API by itself; elsewhere, give --api IP:PORT or set HYPERSTOR_API.

Dashboard

The installer runs the management service (hyperstor-mgmt) on the map service’s hosts, on port 8852. Installed with --ui (see Installation), it serves the web UI: an overview, nodes and devices (take out, bring in, drain, weights), pools and a grid of their PGs, volumes with their snapshots and clones, the trash, operations, the map service’s members, security (people and roles, API tokens, join tokens, certificates) and the audit log. Each action acts as the person logged in, and shows its hyperstorctl command. Without --ui, a built-in dashboard only shows: health with its reasons, I/O rates, space, pools with their PG states (and each PG’s acting and up sets), and every storage node with its state, last heartbeat, I/O, write and read p99 latency, space, log use and map epoch. Both refresh every two seconds.

Reaching it. mgmt listens on every address of the map service’s host, over HTTPS: https://HOST:8852/. Its certificate comes from the cluster’s own CA, so a browser warns until you import the cluster’s root once (/etc/hyperstor/pki/root.crt, as a trusted authority for websites). To avoid that, give it a certificate browsers already trust:

  • your own, kept current by an ACME client: sudo hyperstor-install install --web-tls /etc/hyperstor/web (see hyperstor-mgmt);
  • on Tailscale, the node’s own: sudo hyperstor-install install --tailscale-cert, then https://NODE.TAILNET.ts.net:8852/.

Air-gapped sites. Nothing here needs the internet: the cluster’s CA and mgmt’s certificate are made on the map service’s host, and renewed there. To have browsers trust it without a warning, either distribute the cluster’s root (/etc/hyperstor/pki/root.crt) to the site’s machines once, with whatever configuration management the site uses, after which every hyperstor host verifies; or issue mgmt a certificate from the site’s own internal CA and give it with --web-tls DIR (mgmt re-reads the files when they are renewed). mgmt serves no self-signed certificate.

To keep it on loopback instead, --mgmt-listen loopback, and reach it through a tunnel:

ssh -L 8852:127.0.0.1:8852 the-map-service-host
# then open http://127.0.0.1:8852/

Logins and roles

People log in with their user name and password on the map service’s host, checked by hyperstor-authd through PAM; they must be in the group hyperstor-users:

sudo usermod -aG hyperstor-users ann

hyperstor-mgmt can also log people in with an OIDC identity provider (--oidc FILE, see hyperstor-mgmt); the installer doesn’t set that up yet.

The first to log in with the claim code becomes the first security administrator, who then gives people roles. The code is in the service’s log, valid for an hour:

journalctl -u hyperstor-mgmt | grep 'claim code'
# a new one: sudo systemctl restart hyperstor-mgmt

Someone who logs in without a role sees nothing until given one. Each role adds to the one before, except the last:

RoleMay
viewerRead: status, PGs, volumes, snapshots, the trash, operations, members
operatorAlso take devices out and in, add and remove devices, set weights, classes and fullness thresholds, drain nodes, cancel operations, take snapshots, restore from the trash
storage-adminAlso create, change and delete pools, volumes, snapshots and clones, roll volumes back, purge the trash and set its grace, add and remove members
security-adminPeople and their roles, join tokens, certificates, map backups and the audit log; nothing else

The exact list is in hyperstor-mgmt. Deleting, rolling back, purging, removing a device, making tokens, revoking certificates, fetching a backup and changing roles need a login of the last 10 minutes (step-up), since they are hard to undo: the UI asks you to log in again. Sessions last 12 hours, or 30 minutes idle.

API tokens. For scripts, each person makes API tokens for themselves on the UI’s Security page (90 days by default, a year at most). A token acts with its owner’s roles, but never counts as a fresh login. hyperstorctl uses one through mgmt with --mgmt, so the map service’s audit names the person rather than a certificate:

# the token in a file only you can read
hyperstorctl --mgmt https://192.0.2.10:8852 --token-file ~/.hyperstor-token status

HYPERSTOR_MGMT can stand for --mgmt. What needs a fresh login is refused that way with (reauth_required): do it on the UI, or with the administrator’s certificate. See hyperstorctl.

The web UI does what this page and Pools and devices do with hyperstorctl, each action on the page of what it changes, showing the command it stands for: on Nodes, adding a device, setting its weight or class, taking it out or in, removing it (its plan first) and draining a node; on Pools, creating a pool, changing it, choosing the devices it uses and deleting it (what it holds listed first); on Volumes, creating, expanding, snapshotting, cloning, flattening and deleting volumes. It shows only what your roles allow, and asks you to log in again for what needs a fresh login.

The trash

Deleting a volume or a snapshot moves it to the trash: it disappears from the lists and can’t be attached, but its data stays, and its space still counts against the pool, for the pool’s grace period (a day by default). Then the map service purges it.

hyperstorctl delete-volume --id ID        # → the trash, purged in a day
hyperstorctl trash list
hyperstorctl trash restore --id ID        # back, under its name
hyperstorctl trash purge --id ID --wait 600   # gone now (a fresh login, through mgmt)
hyperstorctl trash settings --pool 1 --grace 604800   # keep a week

A restored volume whose name another volume took meanwhile comes back as NAME-restored. --on-full purge lets a full pool purge its oldest trash rather than refuse new data: while a pool is past full (Full devices), the leader purges its trash oldest first, one item at a time, and waits for the devices’ next reports before the next, so it stops once the pool is no longer full. Each purge is an operation of map-service/purger. The default, keep, never loses data an operator may still want; the pool stays full until space is freed. The UI’s Trash page does the same.

The audit log

Every change, every refused call and every break-glass call is recorded: when, who (a certificate’s identity, local:uid=N on the socket, or a person user:NAME through hyperstor-mgmt), what, on what, and how it went. Each record goes to the service’s journal at once, and to the cluster’s audit log in .meta within a second, kept a year by default:

hyperstorctl audit list --since 1d --op DeleteVolume
hyperstorctl audit list --principal user:ann --json
hyperstorctl audit settings --retention-days 730
journalctl -u hyperstor-meta -u hyperstor-mgmt | grep '"audit":1'

Security administrators read it on the UI’s Audit page, and can export it there as JSON lines.

A client that keeps retrying a refused call doesn’t flood the log: of one principal’s calls refused for one reason, the first ten a minute are recorded, and when the minute ends one Refused record says how many more there were. The journal has every one:

hyperstorctl audit list --op Refused

A node that goes down is kept down for a while before it can come back: 2 s, doubled each time it goes down again within 10 minutes, up to a minute. Each storage node logs:

  • device D open in N ms when it starts. A node is marked up only once every device of it is open, so a slow open delays the node but doesn’t make it flap.
  • device D: reactor held N ms: ... when the thread serving a device is held 100 ms or more, and device D: a commit of N list(s) took N ms when a commit is the cause. These count in hyperstor_reactor_stalls_total. The rest of the line says where the time went: the thread on a CPU, waiting for one (the host was running something else), or off one (asleep, or blocked in the kernel); then the longest single task poll, with the source line that started the task, and the longest call into io_uring. A long poll points at that task; a long wait for a CPU, or both of a node’s devices held at once, points at the host.
  • device D: a commit of N list(s) waited N ms for the device when the device took 100 ms or more to write and flush a commit. The thread goes on serving meanwhile, so this alone doesn’t make a node flap; requests for that device’s data wait.
  • device D: node P silent for N ms; reporting it once each time it reports a peer to the map service.

Draining a node

hyperstorctl drain --node N takes every device of node N out and follows its PGs as an operation, until none lives on the node and none is still moving: then the node can be switched off or serviced.

hyperstorctl drain --node 3 --dry-run   # what would move; nothing changes
hyperstorctl drain --node 3 --wait 600  # drain and follow it to the end
hyperstorctl op list                    # running and recent operations
hyperstorctl op watch --id ID           # follow one
hyperstorctl op cancel --id ID          # stop; the devices come back in
hyperstorctl in --node 3                # after the service

drain prints each PG that moves, with its acting set before and where it goes. Removing a device, deleting a pool with --force, flattening a clone, copying or moving a volume and purging from the trash are operations too, as is each purge the map service makes when a grace period ends or a full pool purges its trash. The web UI’s Operations page shows them. Operations are kept in the map service’s replicated store, a week after they finish, and a new leader carries on with those still running. A drain, a device removal, a copy and a move can be cancelled. op watch exits with status 1 if the operation failed or was cancelled, for scripts.

Revoking a certificate

A certificate that leaked, or a host that is gone, is revoked by serial:

hyperstorctl cert list                       # certificates issued through the API
hyperstorctl cert show --file /path/node.crt # a certificate file's serial
hyperstorctl cert revoke --serial SERIAL

Every map service member then refuses it, on the cluster API and between members, until it would have expired anyway (30 days at most). The local socket on a map service host needs no certificate, so revoking the administrator’s own never locks root out.

Volumes and snapshots

hyperstorctl create-volume --size 10G --name db      # prints its id
hyperstorctl volumes --pool 1
hyperstorctl snapshot create --id ID --name nightly
hyperstorctl snapshot list --id ID
hyperstorctl snapshot group --ids ID1,ID2 --name db  # one instant for both
hyperstorctl clone-volume --id ID --epoch E --name test-copy
hyperstorctl rollback-volume --id ID --epoch E       # the volume must be detached
hyperstorctl flatten-volume --id CLONE --wait 3600  # so its parents can go
hyperstorctl snapshot delete --id ID --epoch E

A snapshot of an attached volume pauses its client’s writes while it is cut, at most 2 s. A snapshot that a clone or a rollback still reads from can’t be deleted (reason in_use): flatten or delete the clone first. To test a volume as a block device on a host, serve it with hyperstor-ublk. All options are in the hyperstorctl reference.

hyperstorctl expand-volume --id ID --size 20G grows a volume (never shrinks it); a client that has it attached sees the new size once it attaches again. write-volume and read-volume copy a file into or out of a detached volume, such as a disk image.

Deleting a volume or a snapshot moves it to the trash.

Copying and moving between pools

hyperstorctl copy-volume --id ID --epoch E --pool 3 --name db-copy --wait 3600
hyperstorctl move-volume --id ID --pool 3 --wait 3600

copy-volume makes a new volume in another pool from a volume’s snapshot (--epoch), while the volume stays in use, or from its current data, which needs it detached. The copy is flat: no snapshots, no parents. move-volume moves a detached volume, keeping its id, so whatever names it (a glidex disk) needs no change; delete and purge its snapshots first, or copy it instead. Both copy every block that holds data through the map service’s leader, and take the new pool’s space for it; a move then deletes the data in the old pool.

VM disks

hyperstor-vhost serves volumes to the VMs on a host over vhost-user-blk: one service per host, a socket per volume, which Cloud Hypervisor or QEMU opens as the VM’s disk. Install it with hyperstor-install --vhost (see Installation). glidex attaches volumes through its control socket; by hand:

sudo hyperstor-vhost ctl attach ID --serial vm-disk   # prints the socket's path
sudo hyperstor-vhost ctl list                          # what is attached here
sudo hyperstor-vhost ctl detach ID
  • Disks. The guest sees a virtio disk with 512-byte sectors on 4 KiB physical blocks and no volatile write cache: a write is answered once every copy has it. Discard isn’t offered yet.
  • One holder. A volume is attached on one host at a time. Attaching it elsewhere is refused (held, naming the holder, such as vhost:NAME for another host’s service) unless --take-over (its holder died: wait for its lease to run out) or --preempt (take it from a holder still running). Each attached volume has a lease of its own, so preempting one fences that disk alone; the old host’s other VMs keep theirs. The old host’s ctl list shows the volume lost.
  • Restarts. Restarting the service (an upgrade, say) keeps its volumes attached: the hypervisors reconnect, and the guests carry on after a pause of a few seconds. A reboot of the host clears them.
  • Full pools. A write refused for space is held, and tried again every second, for up to 5 minutes (--hold-full) before the guest sees an I/O error. See Full devices.

For glidex. glidex’s hyperstor datastore driver keeps a glidex datastore’s disks as volumes in one pool: blank disks, disks filled from an image, and linked clones of an image’s golden snapshot, staged on each node through hyperstor-vhost. It uses the cluster API as a management client. Make it a mgmt token, named after the client, and give it to the client, which enrols with it (it makes its own key and pins the cluster’s root):

(umask 077; sudo hyperstorctl token create --role mgmt --name glidex > token)
# on the client's side: hyperstorctl enroll --file token --api 192.0.2.10:8850 --out DIR

Testing I/O

hyperstorctl io-test --mib 64

writes 64 MiB of random data to a new volume of the first pool (or --pool P: --pool 2 tests the installer’s cache pool), reads it back and compares, and prints the throughput of each phase. A mismatch or an error exits with status 1. It is a quick end-to-end check; for measurements use hyperstor-bench.

Pools and devices

How to change a running cluster’s devices and pools: take devices out for service and back in, add and remove them, set their weights and classes, handle devices that fill, and make, split and delete pools. Every change is made with hyperstorctl or in the web UI, while the cluster serves; how to plan them is in Planning a cluster.

Taking a device out for service

hyperstorctl out --node 2 --wait 600   # or --device D; waits for the PGs to move
...                                    # service the node
hyperstorctl in --node 2 --wait 600    # and for them to come back

A device that is out gets no placement: its PGs go to other devices, which are refilled from the remaining copies. With as many storage nodes as copies, there is nowhere to move them, so the PGs run with one copy fewer (degraded) until the device is back in. Writes go on while each PG keeps at least the pool’s min copies.

A device deletes its copy of a PG it no longer serves a minute after the PG is clean on its other devices, so space comes back after any move: out, drain, a weight change, or a device added. Its log says deleted its copy of PG P.G. A device brought back in is backfilled.

Without --data, out doesn’t survive a map service restart. A map service without a store reads the cluster file when it starts and doesn’t keep changes made since, so after a restart every device is in again. With --data (every install does this) the map, out devices included, is kept.

Device weights

Each device gets PGs in proportion to its weight. By default the weight is the device’s capacity in TiB, which the map service takes from the device’s own reports: a device twice the size gets twice the data, and devices of one size get the same. A newly joined host gets no PGs until its devices have reported, within a second of starting. hyperstorctl nodes shows each weight.

To place less, or more, on a device than its size says, set its weight; to go back, set it to auto:

hyperstorctl weight --device 2001 --weight 0.5    # kept until set back
hyperstorctl weight --device 2001 --weight auto   # follows its capacity

A weight you set is marked * in hyperstorctl nodes. The device’s PGs move as soon as the weight changes, as for out and in. Setting a weight changes the map’s format: do it only once every storage node and map service member runs a build that has hyperstorctl weight.

A pool’s usable space (hyperstorctl pools) counts what it can hold with each copy on a different host (or rack): with as many hosts as copies, the smallest host bounds it.

Full devices

A thin-provisioned cluster can run out of space. Each device is held to three thresholds, percentages of its data area, the same for every device:

ThresholdDefaultPast it
nearfull85 %Health warns
backfillfull90 %Health warns, and no PG is backfilled onto the device; a PG that needs it waits, degraded or remapped, until there is room
full95 %Health is an error. The device refuses what would grow its used space: new objects and writes to blocks not yet written

A pool is nearfull or full while any device it uses is: hyperstorctl pools shows it with the device, hyperstorctl nodes each device’s state, and the web UI’s Pools page the pool’s. While a pool is full, new volumes, clones and snapshots in it are refused (pool_full). Each device’s change is in the audit log, as operation DeviceFullness by hyperstor-meta.

Past full, overwrites of written blocks, deletes, discards and snapshot deletes still work, so you can always free space. A refused write reaches a host’s block device (hyperstor-ublk) as ENOSPC. A VM’s disk has no such error: hyperstor-vhost holds the write instead, trying it again every second for up to 5 minutes (--hold-full), so space freed in time lets it finish. Meanwhile the guest waits: Linux logs a task blocked for more than 120 s, nothing worse. Past the hold the guest sees an I/O error, which may abort its filesystem’s journal (ext4 then needs a remount). The service logs when it starts and stops holding writes for a volume. Free space by deleting volumes or snapshots and purging the trash, or add devices. A pool whose trash is set to --on-full purge (The trash) purges its oldest trash by itself.

hyperstorctl full-ratios                       # the thresholds now
hyperstorctl full-ratios --full 97             # one or more of them

Each is between 50 and 99, with nearfull below backfillfull below full. Setting them to anything but the defaults changes the map’s format: do it only once every storage node and map service member runs a build that has hyperstorctl full-ratios.

Adding a device to a node

A node can take more devices while the cluster runs. On the node’s host, if it runs the map service too:

sudo hyperstor-install install --node 1 --device /dev/disk/by-id/nvme-NAME

The installer refuses a device that holds anything it recognises (a partition table, LVM, a Ceph OSD, a filesystem…; --force-format overwrites it), registers it with the map service, formats it, lets the hyperstor user open it (a udev rule for that disk only), records it in install.conf and restarts the node with it. Later runs, the daily renewal included, keep it. Name devices by /dev/disk/by-id/.

The device is the node’s next one, node × 1000 + i, and starts at weight 0: nothing moves until the node runs it. Once it has reported its capacity, within a second of starting, it gets its weight and PGs move onto it, as after a weight change.

By hand, or on a host without the map service: hyperstorctl device add --node 1 --address 192.0.2.21:9102 (from a host that has the administrator’s certificate), hyperstor-install format-device --path PATH --id D on the node’s host, then one more --shard 192.0.2.21:9102=PATH:0 in the node’s options (which a later installer run rewrites).

Removing a device

A device leaves once its data has moved:

hyperstorctl device remove --device 1001 --dry-run   # what would move; nothing changes
hyperstorctl device remove --device 1001 --wait 3600

The device is taken out at once, and its PGs move to the other devices of their pools, under the backfill budget. An operation follows them; once no PG lists the device, the map service removes it from the map, and the node with it if it was the node’s last device. Neither id is given again. hyperstorctl op cancel --id ID before then brings the device back in.

It is refused when a pool using the device would be left with fewer failure domains (hosts, by default) than its copies. --force allows it: the pool keeps fewer copies until a device in another domain is added, but never fewer than its min. It is refused, forced or not, when a device taking the data would pass 95% full. --dry-run shows the PGs that move, the pools left short and each receiving device’s space after. Through hyperstor-mgmt it needs a fresh login (step-up).

Then drop the device from its node, on the node’s host:

sudo hyperstor-install install --node 1 --remove-device 1001

The installer checks that the map no longer has the device (on a host with the administrator’s certificate), records it in install.conf so later runs leave its --shard out too, and restarts the node without it. A node started by hand with a removed device’s --shard stops, saying so. The device’s data is left as it was; wipe it separately. A node’s last device leaves the map with the node: uninstall the storage role there instead.

Device classes

Each node reports what its devices are: nvme, ssd, hdd, or file for a device file. A device takes its kind as its class, which hyperstorctl nodes shows in the CLASS column, unless you set one:

hyperstorctl device class --device 2001 --class archive   # kept, marked +
hyperstorctl device class --device 2001 --class auto      # its kind again

A class holds devices of one kind, and a class named after a kind (nvme, ssd, hdd, file) only that kind. Pools that name classes place their PGs on those devices; the others use every device, so classes change nothing for them. To limit a pool to some classes, or let it use every device again:

hyperstorctl pool set --pool 1 --classes nvme,ssd
hyperstorctl pool set --pool 1 --classes any

The same command renames a pool or changes its failure domain, a copy per device, host or rack; what isn’t given stays:

hyperstorctl pool set --pool 1 --name blocks --domain rack

The classes’ devices must span at least as many failure domains (hosts, by default) as the pool keeps copies. A set with hard disks and flash both is refused unless --force: a write waits for its slowest copy. .meta always uses every device but hard disks.

A pool can also use one device beyond its classes, or leave out one of them, without changing any device’s class: other pools keep using it as before.

hyperstorctl pool add-device --pool 1 --device 3001
hyperstorctl pool remove-device --pool 1 --device 2000

Each is checked as pool set is, and its PGs move the same way; hyperstorctl pools shows the classes, then +3001-2000. A device’s space is shared by every pool that uses it, so a pool has no size of its own: its free space is that of its devices.

A pool is made on the classes it names:

hyperstorctl pool create --name fast --classes nvme --copies 3

It gets about 100 PGs per device of its classes per copy, as a power of two, unless --pgs says otherwise; the PG count can’t grow yet, so give more if many devices are to come. Volumes go to it with create-volume --pool P. Kinds appear once every running node has a build that reports them; a node from before that starts after that can’t read the map, so upgrade it first.

Splitting a pool’s PGs

A pool’s PG count doubles in place: each PG splits into itself and a new one, with no data copied.

hyperstorctl pool set --pool 1 --pgs 128 --wait 600

The map service splits a few PGs at a time, the clean ones. Each PG’s devices pause its I/O for a moment, move the objects that now belong to the new PG to its keys, and report; once all have, clients use the new PG. Volumes stay attached and writes go on, retried over each pause. hyperstorctl pools shows how far it has got. The new PGs start on their parents’ devices; then, whenever every PG of the pool is clean, the map service places a few more on their own devices, and they move under the backfill budget, until all are placed. A cache pool keeps its data through all of it: its new PGs are copied to their devices, not started empty, and a restart doesn’t empty its devices either. A split is refused for any count but twice the pool’s, while one runs, and until the last one’s PGs have moved. A device that was down during the split catches up when it returns.

A cache pool also waits for a node that goes down: a PG whose copies are all on down nodes stays there for the pool’s grace, 60 seconds unless set with hyperstorctl pool set --pool P --cache-grace SECS (0 to 3600; 0 doesn’t wait), so a host that restarts, or comes back from a short crash, keeps its share of the cache. Meanwhile reads of those PGs miss (a volume reads zeros there), health warns that they are waiting, and a write to one moves it at once to another device, empty. A PG moved that way, or because the grace passed, moves back to the node when it returns and starts empty there.

The map service also splits on its own: when a pool’s devices call for at least twice its PGs (about 100 per device, counting copies), typically after devices were added, it doubles the count, one pool at a time and only while every PG is clean. Its log names each split. To keep a pool’s count as set:

hyperstorctl pool set --pool 1 --autoscale off

hyperstorctl pools lists the pools with it off; pool create takes --autoscale off too.

Deleting a pool

A pool is deleted once it holds nothing: no volume, no snapshot, and nothing in the trash. List what it holds, delete and purge that, then delete it:

hyperstorctl pool delete --pool 3 --dry-run
hyperstorctl pool delete --pool 3

It leaves the map at once, and clients using it get not_found. Its id is never given to another pool. Each device deletes the pool’s data about a minute later; a device that was down does when it returns. Through hyperstor-mgmt it needs a fresh login (step-up).

To delete a pool with what it holds, list it first, then force:

hyperstorctl pool delete --pool 3 --dry-run
hyperstorctl pool delete --pool 3 --force --wait 600

An operation moves each volume to the trash, preempting a client that has it attached, and purges it with its snapshots, each audited; then it deletes the pool. Nothing of it can be restored.

The map service

hyperstor-meta holds the cluster map, answers map requests from storage nodes and clients, detects failed nodes from their heartbeats, and grants map leases: a storage node serves I/O only while its lease is current.

Starting it

hyperstor-meta --listen 192.0.2.10:9000 --cluster /etc/hyperstor/cluster.txt

It prints the size of the map it loaded, then runs until stopped. All options are in the reference.

With --api 127.0.0.1:8850 it also serves the cluster API, which hyperstorctl, the management service and other management clients use. Add --api-tls DIR to require client certificates; without it, keep the API on loopback. The installer also gives it a local socket (--api-socket), which root and the hyperstor-admin group use without a certificate, so an expired or lost certificate never locks the administrator out.

Leases and failure detection

OptionDefaultEffect
--lease-ms600How long a storage node may serve after its last heartbeat was answered
--down-after-ms800How long without a heartbeat before a node is marked down; at least 1.25 × the lease
--down-out-secs600How long a node stays down before its devices are marked out and its data is copied elsewhere

A node marked down loses its roles: its placement groups get new primaries and run with the other copies, and a node cut off from the map service has already stopped serving, because its lease ran out first. Nothing is copied until --down-out-secs pass, so a reboot moves no data (see Failures and recovery). Shorter times detect failures sooner, at the cost of false alarms on a slow or busy network.

Storage nodes also watch each other: a node that two others report silent is marked down even while its heartbeats arrive. A node marked down is held down for at least 2 s, longer each time it goes down again within 10 minutes (up to a minute), so a node that keeps going down and up doesn’t move its PGs back and forth; health then warns that it flaps (see Failures and recovery).

Several members

Run the map service as a group of three members (five for large clusters), each on its own host, so that it keeps working when one is down (two, with five). Each member keeps the map in a store of its own (--data), and they replicate it with Raft:

# On each of the three hosts, with its own --id and the same --member list:
hyperstor-meta --listen 192.0.2.10:9000 --cluster /etc/hyperstor/cluster.txt \
  --data /var/lib/hyperstor/meta --id 1 \
  --member 1=192.0.2.10:8851/192.0.2.10:9000 \
  --member 2=192.0.2.11:8851/192.0.2.11:9000 \
  --member 3=192.0.2.12:8851/192.0.2.12:9000 \
  --api-tls /etc/hyperstor/pki

Give storage nodes and clients every member (hyperstord --meta 192.0.2.10:9000,192.0.2.11:9000,192.0.2.12:9000). Any member serves the map; the leader also grants leases, watches heartbeats and changes the map, and the others send nodes to it.

  • When the leader fails, the others elect a new one within about half a second. Storage nodes keep serving on their leases meanwhile and get new ones from the new leader at once, so I/O pauses for about one lease at most. The new leader then waits until every lease the old one gave has run out before it marks any node down or moves any data.
  • The map survives restarts, of one member or all of them: a member that comes back catches up with the others. The cluster file seeds the map the first time; after that, hosts and pools you add to the file (on every member) are added when a leader is next elected: restart the members, one at a time. Hosts can also join with a token, and devices and pools be added and removed with hyperstorctl, with no restart (see Managing a cluster).
  • Any member answers hyperstorctl and the web UI. What only the leader knows (devices’ space, when each node was last heard from, flapping nodes, scrub’s findings) a member that doesn’t lead asks the leader for, so the answers are the same wherever you ask.
  • Members talk over mutual TLS with their --api-tls certificates, which must name each member’s address. hyperstor-install sets this up when members join the first one with a token (see Installation).
  • Changing members while the group runs, and recovering a group that lost its majority, are below: see Adding and removing members and Recovering a lost majority.

One member

Without --member, the map service is one member: with --data it keeps its map across restarts, and without it, it keeps the map in memory only. A single member is a single point of failure:

  • While it is down, clients can’t connect, and storage nodes stop serving I/O once their leases run out. Run it on a reliable host and restart it automatically.
  • Without --data, it forgets. On restart it reads the cluster file again and starts with every node up; it forgets which nodes were down and which were being refilled, so restart it only while all storage nodes are up and no recovery is running (see Failures and recovery).

Backups and restoring

Installed map services keep backups of their store in /var/lib/hyperstor/meta-backups: the leader writes one when the map, the join tokens or the certificate lists have changed, at most every 5 minutes, and keeps the last 24. Take one at any time, to keep off the cluster:

hyperstorctl map backup --out map.hsbackup

A backup holds what the map service holds, not data: volumes and their contents live on the storage nodes. If every member’s store is lost, start one member from a backup, into an empty data directory, and the storage nodes reconnect to it:

sudo systemctl stop hyperstor-meta
sudo mv /var/lib/hyperstor/meta /var/lib/hyperstor/meta.lost
# The backup must be readable by the service's user.
echo "HS_ONCE=--restore /var/lib/hyperstor/meta-backups/map-…hsbackup" \
    | sudo tee /etc/hyperstor/meta-once.env
sudo systemctl start hyperstor-meta
hyperstorctl status --wait 60
sudo rm /etc/hyperstor/meta-once.env

/etc/hyperstor/meta-once.env holds options for one start; the restored store stays in the data directory, and the next start needs none. It is a map service of one; with several members, the others join it again. Changes made after the backup was taken are lost: hosts joined since then join again.

Adding and removing members

Members can be added and removed while the map service runs. Install the new member first, with a meta token from the leader and a member list that includes it, and start it; then add it on the leader:

# on the new host (member 4)
sudo hyperstor-install install --join 192.0.2.10:8850 --token-file token \
    --role meta --members "$M,4=192.0.2.13:8851/192.0.2.13:8849" --member-id 4
# on the leader
hyperstorctl member add --id 4 --raft 192.0.2.13:8851 --map 192.0.2.13:8849
hyperstorctl member list

The new member is a learner until it has the log, then a voter. member remove --id N takes one out; fewer than three voters survive no failure, so going below three needs --force. Replacing a member on another host is add, then remove. Storage nodes keep the member list they were installed with and are redirected to the leader by any member they reach; installing them again gives them the new list.

Recovering a lost majority

If most members are lost for good, the rest can serve the map but not change it: nothing is marked down and no host joins. Force one survivor alone, on its host, with every other member stopped:

sudo systemctl stop hyperstor-meta
echo "HS_ONCE=--force-alone CLUSTER_ID" | sudo tee /etc/hyperstor/meta-once.env
sudo systemctl start hyperstor-meta
hyperstorctl member list            # one member, leading
sudo rm /etc/hyperstor/meta-once.env

It refuses while another member answers, since two groups would then split the cluster, and unless given the cluster’s id. It revokes the other members’ certificates issued until then, so an old member that comes back with its log is refused; reinstall those with fresh data directories, join them with meta tokens, and add them. Map changes the survivor hadn’t received before the loss are lost: hosts joined in that window join again.

Storage nodes

hyperstord runs one storage node. Each --shard gives it one device and the address it serves that device on:

hyperstord --node 3 --meta 192.0.2.10:9000 \
    --shard 192.0.2.23:9100=/var/lib/hyperstor/dev0.img:100 \
    --shard 192.0.2.23:9101=/dev/nvme1n1:0 \
    --cpus 2,3

All options are in the reference.

Devices

A device is a file or a block device:

  • A file is created if needed and extended to the size given, in GiB, after the colon. It is sparse at first and fills up as data is written; keep that much space free on its filesystem.
  • A block device is used whole. Give its size as 0 (/dev/nvme1n1:0).
  • A file without Hyperstor’s format is formatted on first start. A block device never is: format it first with sudo hyperstor-install format-device --path /dev/disk/by-id/NAME --id D, which refuses a device that holds anything else (a partition table, LVM, a Ceph OSD, a filesystem…) unless --force-format. A node given a blank block device stops, saying so. Name block devices by /dev/disk/by-id/: /dev/nvmeXnY numbers can change at boot.
  • A device that holds another device’s data, or another cluster’s, is refused: the node stops and says whose it is (swapped paths, a drive from another host). Nothing is written to it. Each device’s superblock records its device number and its cluster for this check.
  • A device the map doesn’t have, or has on another node or at another address, is refused too. --shard ID@ADDR=PATH:SIZE names the device’s number when it isn’t the node’s next (after a device was removed, say).
  • A device formatted by a newer build, with features this build doesn’t know, is refused rather than misread; so is one whose superblocks are damaged. Neither is formatted again.

Devices can be added to a running node and removed from it, and each gets PGs in proportion to its weight (its capacity, unless set): see Managing a cluster.

Devices are opened with O_DIRECT and driven through io_uring. --buffered goes through the page cache instead, for filesystems that refuse O_DIRECT; use it for testing only.

Space on a device

  • Each device keeps room for its next checkpoint, so a device that fills up keeps working: it refuses new data, while overwrites and deletes go on and free space.
  • Past the cluster’s full threshold (95 % by default) a device refuses new objects and writes to blocks not yet written. See Full devices.
  • A device deletes its copy of a PG it no longer serves a minute after the PG is clean on its other devices, so the space comes back after data moves.
  • Checkpoints write only the parts of the index that changed since the last one, so their cost follows the rate of change, not the size of the device.

Hard disks

Flash devices write every change to a new place. --hdd tells the node its devices are hard disks: small overwrites then go through the log first and are applied in place later, which suits disks’ slow seeks. It applies to every device of the node.

CPUs

Each device is served by one thread. --cpus 2,3 pins the thread of the first --shard to CPU 2 and the second to CPU 3. Pin to cores that nothing else busy uses, and keep them on the same NUMA node as the device and the network card where you can.

The thread doesn’t wait for its device on commits and client reads: it answers its peers’ pings and takes new requests meanwhile, and only the requests that need the commit in flight wait for it. A commit that takes longer than --io-timeout-secs (30 s), or three reads in a row that take longer than --read-timeout-ms (2 s), fail the device (see Failures and recovery). Checkpoints, and reads for backfill and scrub, still run on the thread. The node logs each time the thread is held 100 ms or more (see Health).

Starting, stopping and restarting

  • A node stops on SIGINT or SIGTERM by exiting.
  • On the next start, each device recovers on its own: it replays its log and checks the last writes against their checksums. Writes that were acknowledged are never lost. Each device logs how long it took to open (device D open in N ms).
  • The node is marked up only once every device of it is open, so a slow device delays the node rather than making it go down and up.
  • While a node is stopped, the map service marks it down after --down-after-ms, and its placement groups go on without it. When it starts again it stays down for at least 2 s after it was marked down, then is refilled (see Failures and recovery).
  • Keep a node’s number and device paths the same across restarts: they identify its data, and a device given the wrong path is refused.

Failures and recovery

A storage node fails

  1. The node stops sending heartbeats to the map service and answering its peers’ pings. Clients’ requests to it fail, and the client library retries.
  2. After --down-after-ms (0.8 s by default) without a heartbeat, or once two other nodes report it silent, the map service marks the node down. Each placement group the node held goes on with the copies left, if at least the pool’s min remain; a new primary takes over where the failed node was primary. Before it serves, the new primary makes the other copies match its own, so a write the failed node never confirmed to its client is kept by every copy or by none.
  3. Writes continue with fewer copies (the PGs are degraded). Nothing is copied yet: the node keeps its place, so a short reboot moves no data.
  4. If the node is still down after hyperstor-meta --down-out-secs (10 minutes by default), its devices are marked out. Where the pool’s failure domain allows, their PGs are placed on other devices, and each primary backfills the new copy (copies every object of the PG to it) while writes go on. Once full, it counts as a copy. Where no other domain is free (three nodes and three copies by host), the PGs stay degraded until the node returns.

If every copy of a PG is down, the PG stays down, and requests for its data fail until one of its nodes returns. It is never reset to empty.

A storage node returns

When the node starts again and sends heartbeats, the map service marks it up, and marks its devices in again if they were marked out while it was down. Placement wants it back for the PGs it held. For each of them, the current primary backfills it: it compares what the node holds with its own copy, object by object, and sends only the objects that differ (deleting those it no longer has), since the node may have missed writes. Only then does the node count as a full copy again, and any copy placed elsewhere meanwhile is dropped.

A node marked down stays down for at least 2 s, and longer if it keeps going down and up (see A node that flaps).

So a node that was down briefly receives about what was written while it was away. A new or empty node receives all of its PGs’ data: plan for that traffic when you add or replace one.

A device you took out yourself (hyperstorctl out) stays out until you bring it back in.

A node that flaps

A node whose thread is held (a stalled device, a host short of CPU or memory) can miss its peers’ pings for long enough to be reported, then answer again: it goes down and up. Each time is costly, since its PGs change primaries and are refilled. So the map service holds a node that went down: 2 s the first time, doubled for each further time within 10 minutes, up to a minute; ten quiet minutes reset it. Health warns node N flapping (K transitions in 10 min). Look at that node’s log for what holds it (see Health).

A storage node is cut off from its peers

Storage nodes ping each other several times a second, over UDP (TCP for a peer that doesn’t answer over UDP). A node silent for about 300 ms is reported to the map service. A node reported by two others is marked down even while its heartbeats still reach the map service: it can’t serve its PGs’ copies if its peers can’t reach it. One report alone marks nothing down, and a node not heard from since the map service started is not marked down by reports: it may still be opening its devices.

A replica is slow or unreachable

A primary that gets no answer from one of a PG’s copies within 2 s, or can’t connect to it at all, reports it to the map service. The map service takes that copy out of that one PG, as long as the pool’s min copies remain, and the primary backfills it back once it answers again. The node itself stays up, and its other PGs are not affected. This also covers a network cut between two storage nodes only, which the map service can’t see from heartbeats.

The client sees Unavailable for the write that timed out, and retries. A slow primary is not handled yet: its clients wait for it.

A device fails

A device that returns an I/O error is failed: its node answers every request for it with Unavailable (clients retry) and reports it to the map service, which marks it failed and out and places its PGs elsewhere at once, without waiting for --down-out-secs. The node’s other devices go on serving. One I/O error is enough: there is no error-rate threshold yet. A device that takes more than 30 s (hyperstord --io-timeout-secs) to write and flush a commit is failed the same way, and its node’s log says why (the device took over 30000 ms to write a commit); before, a hung device held its node’s thread, and the whole node went down. A read that waits more than 2 s for its device (--read-timeout-ms) is served from another copy, and counted in hyperstor_read_timeouts_total; three in a row fail the device the same way (3 reads in a row took over 2000 ms).

If the device is broken, replace it, format the new one (a block device with hyperstor-install format-device; a file is formatted by the node) and start the node again, then bring it back in with hyperstorctl in --device D: its PGs are backfilled. To retire a device instead, remove it (see Removing a device).

A device fills up

Past the full threshold (95 % by default) a device refuses new data, and its pools are full: new volumes, clones and snapshots in them are refused. Overwrites, deletes and discards still work, so space can always be freed. A VM’s disk holds a write refused for space for up to a minute before the guest sees an I/O error. See Full devices.

Cache pools

A cache pool keeps one copy by default and doesn’t recover a lost one: when a device fails, its cache PGs start empty elsewhere, and clients recompute what they miss. When a node goes down, its cache PGs wait for it for the pool’s grace (60 s by default): back in time, it keeps their data. Meanwhile reads of them miss (a volume reads zeros there), and a write to one moves it at once to another device, empty. Health warns while PGs wait.

Damaged data

Every 4 KiB block carries a checksum. When a primary reads a block whose checksum doesn’t match, it fetches the object from another copy, replaces its own copy and answers the read with the good data. A damaged block is never returned to a client.

Scrub

Every storage node compares, once a day by default (hyperstord --scrub-hours), the copies of each placement group it leads. A copy that differs from the others, when the rest agree, is replaced from the majority’s copy, the primary’s own included. Once a week (and on the first scrub after a start) the scrub is deep: every copy is read in full and each block’s checksum checked, at a limited rate, so damage that no client has read yet is found and replaced from the other copies (kind="damaged"). When no majority agrees, nothing is changed: the object is counted under hyperstor_scrub_objects_total{kind="unresolved"} and logged, and hyperstorctl status warns with the PG (PG(s) inconsistent), for an operator to look at.

A storage node is cut off from the map service

A node that can reach clients but not the map service keeps serving until its map lease runs out (--lease-ms, 0.6 s by default), then stops. The map service waits longer than the lease before giving its PGs to other nodes, so no acknowledged write is lost and two nodes never serve the same PG.

A client holding a volume fails

A volume is attached by one client at a time, which renews its lease every second. If that client dies or is cut off, another client takes the volume over: it waits for the old lease to run out (up to 4 s) and blocklists the old lease, so every storage node refuses the old client’s requests for that volume from then on, even if it comes back. Each attached volume has a lease of its own, so the old client’s other volumes are not affected. See the client library.

The same holds for VM disks: when a VM moves to another host because its old host failed, that host’s hyperstor-vhost takes the volume over or preempts the old one, and only that disk is fenced; the other VMs on the old host keep theirs. See VM disks.

The map service fails

See The map service: with three or five members, the others elect a new leader within about half a second and I/O pauses for about one lease. A single member is a single point of failure: the cluster stops serving within a lease period, and resumes when it is back.

Not handled yet

  • A slow primary.

See Status.

Measuring performance

hyperstor-bench measures a device, the engine alone, or a running cluster. It prints Markdown table rows: test, operations per second, MB/s, and latencies. Each test runs for HS_BENCH_SECS seconds (3 by default). All modes are in the reference.

Before a cluster

Measure each device raw, then with the engine on top:

hyperstor-bench raw /var/lib/hyperstor/bench.img 2
hyperstor-bench engine /var/lib/hyperstor/bench.img 2
rm /var/lib/hyperstor/bench.img

The gap between the two is the engine’s cost. Run it on the filesystem or device the node will use, never on a device that holds data: the file is overwritten.

A running cluster

HS_BENCH_SECS=10 hyperstor-bench remote 192.0.2.10:8849

Give it the map service’s address (its --listen; port 8849 on an installed cluster). It connects as a client, writes 512 MiB of test data to pool 1, then reports 4 KiB random and 1 MiB sequential results over it. The test data stays in the pool: use a test cluster.

hyperstor-bench cluster mem runs a whole cluster in one process, on memory, to measure the code without a network or devices.

Tips

  • Run the client on a host other than the storage nodes, or results include the client’s CPU use.
  • Pin storage threads with --cpus and compare; unpinned threads move between cores.
  • Compare against the raw device numbers: a replicated write costs one network round trip and a flush on every copy.

Goals in one paragraph

Hyperstor is a sharded, distributed store written in pure Rust on Linux io_uring. It keeps two or three copies of every chunk (erasure coding is planned) on many storage nodes, places them by failure domain, and keeps serving when nodes, devices or links fail. Block volumes come first: for virtual machines through vhost-user-blk (built), and for other hosts through NVMe over Fabrics (planned). A read cache for data that can’t change is being built into the client library. The same object layer is meant to carry GPU-direct reads into GPU memory, an S3 gateway and a distributed filesystem later, with NFS proposed on top of it. It is built for the glidex platform, which runs agent VMs, inference, fine-tuning and retrieval workloads, and it also runs on its own.

A write, end to end

  1. The client splits the request at chunk boundaries (4 MiB chunks by default; offsets and lengths are multiples of 4 KiB). Each piece is sent in parallel.
  2. It routes each piece without asking anyone: the chunk’s placement group (PG) is a hash of the volume’s lineage and the chunk index (while a pool splits its PGs, the map says whether a PG’s new sibling serves it yet), and the PG’s primary is the first device of its acting set in the client’s copy of the map (placement).
  3. The primary checks the request: it holds a current map lease, the PG is not fenced for a map change, the request’s PG epoch matches its own, it is the primary, neither the client nor the volume lease the request names is blocklisted, and every block’s CRC32C matches. A request at an old epoch is answered StaleMap; at a new epoch, the primary first makes the other copies match its own (peering).
  4. It replicates: it gives the write the PG’s next sequence number, sends it to every other copy and queues its own commit, with nothing in between, so every copy applies the PG’s writes in the same order.
  5. Each copy commits through its engine’s group commit: the reactor gathers queued changes, writes their data to new extents and one log record, flushes once, and acknowledges them all. The reactor submits those writes and the flush on its io_uring and serves other requests while the device works (data path). A device past its full ratio refuses changes that take space: a new object, or a write to blocks the object doesn’t hold yet. Overwrites and deletes go on.
  6. The primary answers the client only when its own commit and every copy’s have been acknowledged.
  7. On failure the client retries: on a stale map, a moved primary, Unavailable, or a dropped connection, it refreshes its map and tries again, up to 20 times with a growing back-off (about two seconds in all). “No space” and “fenced” are not retried: the caller decides.

A read, end to end

The client first looks in its host read cache: blocks of a version that can no longer change (a snapshot, or a clone’s parent) may already be there (volumes). Otherwise it sends the read to the PG’s primary, which serves it from its own engine while it holds its map lease. Every block’s CRC is checked on the device and again by the client. If the primary’s copy fails its check, the primary fetches the object from another copy, replaces its own, and answers with the good data. If its device takes longer than the read timeout (2 s), the primary asks another acting copy to answer instead. Blocks never written read as zeros.

Why reads go to the primary only: it is the one copy guaranteed to have every acknowledged write. Reads from any copy are planned for snapshots, which never change. A read of a volume with snapshots or clones carries its layers (see snapshots), and the primary reads each block from the newest version that holds it.

The map and its epochs

Every node and client holds a copy of the cluster map: nodes and their devices, pools and their rules, and for every PG its up set (where placement wants it), its acting set (the copies that have every acknowledged write) and its primary. Each change bumps the map epoch; each PG also has a PG epoch, the map epoch of the last change to its acting set. A request carries both, so a node or client with an older map is told so and fetches the new one, and no copy acts on a write meant for an earlier arrangement. See the map service.

The data path: reactor and engine

Each storage device is split into shards, and each shard is owned by one reactor: a thread pinned to a core, running Hyperstor’s own io_uring event loop. The shard’s engine, its network port, its replication and its recovery all run on that thread. Nothing on the data path takes a lock shared with another core.

Waiting for the device

A reactor that waits for its device serves nothing else meanwhile, pings included: one slow flush got healthy nodes reported and marked down. So the engine is being made completion-driven: it plans an operation in memory, the reactor submits the device I/O on its own ring, and the operation finishes when the completions arrive. Memory devices and the test rig’s devices have no file descriptor and still complete in their own calls. On a cluster of three hosts at 15,000 writes a second, no reactor was held 100 ms or more once commits waited off the thread; before, at that cluster’s ordinary load, one node’s flushes held its reactor for up to 205 ms.

Two timeouts follow, since a hung device no longer stops its node’s pings and would otherwise hang unseen:

  • I/O timeout (30 s, hyperstord --io-timeout-secs, as Linux gives an NVMe command): a commit whose writes and flush take longer fails, and the device is failed and its PGs placed elsewhere, as after an I/O error. The node stays up.
  • Read timeout (2 s, hyperstord --read-timeout-ms): the primary abandons the read and asks the PG’s other acting copies, in turn, to answer from their own copies, once the writes queued before the read are applied there. If none answers in time, the client gets Unavailable and retries. Three timeouts in a row fail the device; a read in time resets the count.

Reads in flight and freed space. A read plans which physical blocks to read, then waits. If a commit meanwhile frees those blocks (an overwrite moved the data elsewhere) and a later write reuses them, the read would return the wrong data. So extents freed while reads are in flight are held, by generation, until every read begun before the free has ended; and while a read is in flight, a small overwrite is redirected rather than deferred in place (on hard disks). The cost: one counter per read, and space freed at most a read timeout late. A randomized test runs reads, writes and deletes begun and ended in any order against a model.

The engine

The engine stores objects. An object has sparse data in 4 KiB blocks, a table of attributes, and an ordered key–value table. Volumes are made of chunk objects; volume headers, and later the key–value store, S3 and the filesystem, use the same objects in their own namespaces.

Operation lists

A change is an operation list, applied atomically: all of it or none of it survives a crash. Operations include Write, Zero, Truncate, SetAttr, KvPut, KvDelRange, Delete, and asserts (AssertRevision, AssertExists, AssertAbsent) checked before the list applies. Asserts make compare-and-set possible, which the volume headers use. Absorb serves snapshot deletion: it hands the blocks an older version of a chunk holds, and a newer one lacks, to the newer one, then deletes the older, all in one log record and without copying any data. Take moves a whole object (blocks, attributes and key–value table) to a new key in one constant-size log record, which a PG split uses (placement). Reads can go through layers: each block comes from the first of a list of objects (a chunk’s versions) that holds it, zeros if none does. Every change gets a revision from a counter that never repeats, so compare-and-set has no ABA problem.

On-device format

device:  [superblock A][superblock B][shard 0][shard 1] ... [shard n]
shard:   [super A][super B][log ring][data area]
  • The device superblock, in two copies, names the device (its id in the map), the cluster, the format version and three words of feature flags: compatible ones, which a build that doesn’t know them ignores; read-only-compatible ones, which it could only read past (and refuses, since no build opens a device read-only); and incompatible ones, which it refuses. Every format change from now on takes a flag, as in ext4 and XFS.
  • The two shard superblocks alternate by sequence number, so a torn superblock write leaves the other one valid.
  • The log ring is a sixteenth of the shard, between 1 MiB and 1 GiB. It holds whole-block records, each with a CRC32C seeded by a salt that changes on every open, so an old record left in the ring is never mistaken for a new one.
  • The data area holds extents. Every 4 KiB block in an extent has its own CRC32C, kept in the index and carried on the wire unchanged from the client to the device and back.

Whose device it is

Before a device is opened, hyperstord connects to the map service and reads the device superblock alone, before any log is replayed:

  • The device id must be the one this reactor serves, and the cluster the map’s. A drive moved from another host or cluster, or two device paths swapped, is refused with what it holds, and never written. A superblock written before the cluster was recorded gets it recorded once, the second copy first, so a crash leaves the old or the new.
  • Only a blank device is formatted: one where neither copy holds a Hyperstor superblock. A newer format version, a damaged superblock or a shard without one is refused, never formatted over.
  • hyperstord formats only files. Block devices are formatted by the installer, after it looks for other systems’ signatures (partition tables, filesystems, swap, LVM, md RAID, LUKS, Ceph BlueStore) in the device’s first and last 128 KiB, unless the operator forces it.

Why: the superblock recorded its device, but nothing read it; a swapped drive would have been replayed and served as this device’s data. Checking from the superblock alone keeps a refused device untouched.

Redirect-on-write, and deferral for hard disks

On flash, every write goes to new extents, and the log record that commits it names them: data is written once. On hard disks (hyperstord --hdd), a small overwrite (under 64 KiB) of blocks an object already holds goes into the log record and is applied in place later, so the disk doesn’t seek to a new place for every small write.

Why: on flash, deferring writes data twice. Measured on the same drive, redirecting gave 1.6× the 4 KiB write throughput, and end to end 19 % more throughput with a 2.6× lower p99 (Performance).

Group commit

A per-reactor committer drains the queue of operation lists: it writes their new extents and one log record, issues one flush for the whole round, then acknowledges every list in it. At batch 32 the log costs about 128 bytes per update (257 B with checkpoints).

Checkpoints

The index lives in memory and is written out by fuzzy checkpoints: starting when a quarter of the log is used, each commit round also writes 64 KiB of the checkpoint (8× that past half), and the checkpoint must be done by three quarters. The superblock then names the new checkpoint and the log position after it.

Why fuzzy: writing the whole checkpoint at once stalled commits for 8–13 ms at p99. In slices, commit p99 is 109 µs at the same throughput.

Paged. The index is cut into pages by key range, about 128 KiB each. Every change marks the page holding its key, and a checkpoint writes only the pages marked since the last one began, each to fresh blocks, then a directory of every page. A page that grows past its size is cut in two; one left empty is dropped, its range joining the page before. Why it is safe: a page that nothing changed since the last checkpoint began is still right as written then, and every change it lacks is in a page written now or in the log replayed after it. What it gains: checkpoint traffic follows the share of the index that changes, not its size: 2.4× less when a tenth of the chunks are written, 16× less for a hundredth. Uniform random writes touch every page and gain nothing. Recovery time is unchanged.

When a shard fills

  • Room for a checkpoint is kept. A change that would take the space a whole checkpoint needs is refused (no space), while one that only frees (delete, truncate, zero, absorb) goes through. A checkpoint that still finds no room is abandoned, not fatal, and runs again once room is back. Why: a checkpoint that failed used to poison the shard, so every volume on it got I/O errors instead of “no space”.
  • The full ratio (95 % by default, set cluster-wide in the map) refuses, from each commit round, a list that takes room past it: a new object, or a write to blocks an object doesn’t hold yet. Overwrites, and an existing object’s keys and attributes, go on, so volume leases and headers keep working on a full device. See fullness.

Recovery

On open, the engine loads the checkpoint the newer superblock names, replays the log from there, and checks the data CRCs of the last commit group: a record whose data didn’t reach the media is dropped, with everything after it. Replay runs at about 270 MiB of log per second; opening takes about 0.3 s plus 4.5 ms per MiB replayed.

The index

Each object’s block map starts as a list of runs (extents). When a chunk gets fragmented by random overwrites, it switches to a dense map: 8 bytes per block (a 32-bit physical block and its CRC), and back to runs when it compacts again.

Why: after random overwrites, run maps cost about 33 GiB of memory per TiB of data; dense maps cap it at 2 GiB per TiB. A copy-on-write B+tree on the device, which pages the index out of memory, is planned for when index memory calls for it; paged checkpoints already write only what changed (see decisions). Snapshots don’t wait for it: they are versions of chunk objects (volumes).

Content digests

The engine can compute a 64-bit digest of each object from its index alone, reading no data: FNV-1a over its size, each non-zero block’s number and CRC32C, its attributes and its key–value table. Replication uses these digests for peering, delta recovery and light scrub (replication). Listing them costs about 0.5 µs per small object and 20–50 µs per 4 MiB chunk. An object’s digest is cached until it changes. A large one (an object with a key–value table of hundreds of MiB) is taken in parts of 1 MiB with a yield between them, and digest lists and backfill compare in batches of 64 objects, so no PG holds the reactor for long; the digest is the same as taken at once, so nodes of both versions agree.

Crash testing

The engine’s crash test runs random operation lists against a reference model (a sorted map in memory), and cuts the power at random device operations: blocks not yet flushed are randomly kept or lost, so writes are torn and reordered, and it cuts the power again during recovery. After each crash the recovered shard must equal the model after every acknowledged list plus some prefix of the ones in flight. 300 seeds run on every change (HS_CRASH_SEEDS sets more); a 5,000-seed run (30,000 crashes) has passed.

Placement and replication

Placement

Chunks and placement groups

A volume is cut into chunks (4 MiB by default). A chunk’s name is its volume’s lineage (128 bits) and its index. A pool has a power-of-two number of placement groups (PGs), and a chunk’s PG is a hash of its lineage and index, masked to the PG count. Other objects (volume headers, the audit log) are placed by a hash of their name. Hashes are SplitMix64’s finalizer for integers and FNV-1a for byte strings; their values are pinned in tests, because changing them would move every chunk.

Why PGs: a cluster with millions of chunks needs placement, recovery and peering decisions for only thousands of PGs. Why by lineage: a clone shares its parent’s lineage, so a read that falls through to the parent’s chunks stays on the same devices.

Weighted rendezvous hashing

Each PG is placed on devices by weighted rendezvous hashing (also called highest random weight, HRW): every candidate gets a score from a hash of the PG and the candidate, and the best scores win. Hyperstor uses the exponential form, score = −ln(u) / weight with u from the hash’s top 53 bits, lowest score winning, so a candidate wins with probability proportional to its weight.

Placement is hierarchical, over the pool’s failure domain (device, host or rack): it picks distinct domains at that level, then a host within each chosen rack, then a device within each host, each level salted differently, with device weights summed up the tree. No two copies share a failure domain.

Which devices a pool may use. A device is a candidate when it is in, has a weight above 0, and the pool may use it: its class is in the pool’s class set (or the set is empty, meaning every device), or it was added to the pool by hand, and it wasn’t removed from it. A device’s class is its kind (nvme, ssd, hdd, file), which the node reports, unless an operator labels it. A pool whose classes mix hard disks and flash is refused unless forced (or a cache pool), and .meta never uses hard disks. Why: a replicated write waits for its slowest copy.

Weights are capacities. A device’s weight is its data region in TiB, set by the map service’s leader from the device’s own space reports. A new weight is committed only when the size differs by more than 1 %, and changes to devices already weighted wait until every live device has reported, then go in one map change: so an upgraded cluster, or devices all of one size, move nothing. A device added to a running node, or a joining host, starts at weight 0, so nothing is placed on a guess, and gets its weight from its first report. An operator may fix a weight (hyperstorctl weight), which the map keeps until set back to auto.

Up, acting and primary

For each PG, placement gives the up set: where it wants the copies. The acting set is the copies that hold every acknowledged write; the first one is the primary. When up and acting differ (a device was added, or one returns), the primary backfills the new copies while writes go on, and once they are full a map change makes acting equal to up with a new PG epoch.

Backfill is bounded. A reactor’s backfills to one target keep at most 16 MiB of pushes on the wire together; a backfill that finds the budget spent waits for its answers, then for room. A device past its backfillfull ratio gets no new backfill. Why the bound: when an empty host rejoined a three-host cluster, every primary started a backfill for each of its PGs at once, and pings and replicated writes queued behind hundreds of MiB. The budget bounds what a write waits behind; pings now have a connection of their own as well.

Stray copies. A device that is in neither up nor acting of a PG it still holds objects of deletes its copy once the PG is clean (acting is up and every member is live) and has stayed so, at one PG epoch, for 60 s. It deletes through its commit queue, 64 objects at a time, checking before each batch that nothing changed. A PG the map lacks is left alone, and a node cut off from the map service deletes nothing. Why: every rebalance, drain or weight change used to leave the old copies for ever, so space never came back. The grace keeps a copy through a quick change back; waiting for clean means nothing a recovery could need is deleted.

PG counts grow by splitting

A pool’s PG count doubles as devices are added, without moving data twice. Because a chunk’s PG is its hash masked to the count, doubling the count sends the chunks of PG p either to p or to its new sibling p + n (for n PGs before), and both start on the same devices.

  1. Split in place. The map marks a few clean PGs of the pool at a time (4). Each member of a marked PG pauses its I/O (Unavailable, which clients retry), moves the objects that now belong to the sibling to their new keys with the engine’s Take (metadata only, no data copied), and reports. Once every member has, the map flips the PG: the sibling appears with the same acting and up sets, and clients route by the key they send. The last flip doubles the PG count.
  2. Move gradually. A placement count stays at the old count, so a sibling is placed as its parent and nothing moves yet. The leader then raises it a few PGs at a time (4), each time every PG of the pool is clean; each step moves exactly the PGs it passes, under the backfill budget.

The autoscaler on the map service’s leader doubles a pool’s count when its devices call for at least twice its PGs (a target of about 100 PGs per device, counting each copy), one pool at a time, never .meta, and only while every PG is clean. An operator can split by hand (hyperstorctl pool set --pgs) or turn it off per pool. Merges are not built. Why this way: each pause is short and bounded, a slow device holds up only its own PGs, and the slow part, moving data, is spread out. Ceph splits the same way (pg_num, then pgp_num).

The replicated write

Hyperstor uses primary-copy replication: the client sends a write to the PG’s primary, which sends it to every other copy in the acting set and answers the client only when every copy has made it durable.

  • A PG with fewer than its pool’s min copies refuses writes rather than accept them on fewer.
  • Each PG’s writes get a sequence number from the primary, and every copy applies them in that order.
  • A copy being backfilled also receives live writes, so it doesn’t fall behind while it fills.
  • Each request names the volume lease it acts under; storage nodes refuse one whose lease or client is blocklisted (volumes). Only client connections are checked: a primary decides for its copies, so a write it accepted is never refused by a copy.

Why all copies, not a quorum: with every acknowledged write on every acting copy, any copy can become primary without a log comparison, and reads need only the primary. The cost is that one slow copy slows the PG’s writes, which is why slow copies are dropped (below).

The map service

hyperstor-meta holds the cluster map and is the only process that changes it. Three or five members replicate it with Raft (through openraft, with the map kept in an embedded redb store); the leader grants leases, watches heartbeats and changes the map, and the followers serve map reads and send everything else to the leader. The map service is off the I/O path: clients and storage nodes compute placement themselves.

Storage nodes send heartbeats, space reports and scrub results to the leader only. A follower asked for the cluster’s status gets what only the leader knows (when each node was last heard from, each device’s space, flapping nodes, unrepaired PGs) from the leader, kept for 1 s, so every member answers in full without clients needing to find the leader.

Map leases and fencing

A storage node serves a PG only while it holds a map lease, renewed by each heartbeat answer. The node counts its lease from the moment it sent the heartbeat, and the map service counts it from when it answered, plus a quarter: so whatever the network delay, the node’s lease ends first, and the extra quarter covers clocks that run at slightly different rates. No synchronized clocks are needed.

Before publishing a change that takes a role away from a device, the leader fences it: the device stops accepting new work for those PGs and answers once its writes in flight are done. A device that doesn’t answer gets no more leases, and the leader waits until its last lease has run out (1.25 leases after the last grant). Only then does it publish the new map and push it to every node.

The result: two primaries never accept writes for one PG, and the lease is also what makes reads from the primary safe, with no separate read leases. The cost: if the whole map service is down, I/O stops after one lease, which is why it runs as three or five members.

A new Raft leader serves the map at once but waits 1.25 leases before changing any role, because leases are kept in the old leader’s memory only. Replicating them would cost a Raft write per node per heartbeat.

Peer pings

Each device pings the nodes it shares a PG with every 100 ms and reports one that stays silent for 300 ms; the map service marks a node down on reports from two different nodes.

  • Over UDP. A device answers 12-byte pings on UDP at its TCP port’s number. Each ping carries a random 64-bit nonce that its answer echoes; an answer matching no ping in flight is ignored. A peer is pinged over TCP as well (on a connection of its own, apart from data) until it first answers over UDP; one that never does stays on TCP, logged once. Why: on a busy network a few packets in a thousand are lost. On TCP a lost ping waits at least 200 ms for its retransmission, and the pings behind it wait with it, which made single 300–400 ms silences under load. A lost UDP ping costs only its own slot.
  • A held reactor reports no one. A watcher whose 100 ms tick comes 100 ms late or more was held itself; it counts every peer’s silence afresh, since its peers’ answers were waiting for it to read them.
  • A starting node isn’t reported. A node heartbeats only once all its devices are open, and the map service ignores reports about a node it hasn’t had a heartbeat from since it took the lead. A device still opening answers no pings, so those reports said only that it was starting; the heartbeat timeout still catches one that never comes up.

Flap damping

A node marked down comes back up only after a hold: 2 s, doubled for each further down within 10 minutes, at most 60 s; ten quiet minutes start it afresh. A node still goes down, and loses its lease, at once. Health warns about a node that went down twice or more in the window. Why: a node whose reactor stalled past the peer timeout went down and up about 150 times a minute on a test cluster; each change bumped the map and shrank or refilled PGs until some fell below min. Holding it down turns a flapping node into a down one, which the cluster handles.

In a full pool, new volumes, clones and snapshots are refused, and a pool set to purge its trash when full (hyperstorctl trash settings --on-full purge) purges its oldest item, one at a time, waiting for the space freed to be counted before choosing the next. Clients see “no space”: hyperstor-ublk answers ENOSPC at once, while hyperstor-vhost holds the write and tries again every second for up to 5 minutes (--hold-full), since virtio-blk has no “no space” status and an I/O error can turn a guest’s filesystem read-only.

Why overwrites go on: leases and volume headers are updated in place, and refusing them would stop every volume on the device, not only the ones that grow. Why backfillfull: recovering a lost device must not fill the survivors before their own writes stop.

A pool’s usable space is computed by the leader from the devices’ reports under its failure-domain rule: no domain counts for more than one copy of each PG. With as many hosts as copies, the smallest host bounds the pool, which a plain sum would overstate.

Cache pools

A cache pool holds data that can be recomputed: one copy by default, no backfill after a failure, and a read of a missing object answers “not found”. Each cache PG has a generation in the map, which moves when a member joins without the data; a device serving a cache PG at another generation than it last did first empties its copy, so a returning node never serves data older than a write made while it was away. A PG all of whose copies are on down nodes waits for them for the pool’s grace (60 s by default, hyperstorctl pool set --cache-grace), so a node back in time keeps its data: reads meanwhile answer as an empty device would, and a write ends the wait, moving the PG at once. Expiry and eviction are not built yet.

Peering and recovery by content digests

When a PG gets a new primary, the primary peers before it serves: it asks every acting copy for its list of (object, digest) pairs (digests), compares them with its own, and pushes its own version, or a delete, of each object that differs.

Why this is safe: every acknowledged write is on every acting copy, the new primary included. So any difference is a write that was never acknowledged, and making every copy match the primary means no client can read a value and later find it gone.

Delta recovery and backfill work the same way: a returning or new copy lists its digests, and the primary sends only the objects that differ, as whole objects (data, CRCs, attributes, key–value table), on the same connection as live writes so a push never overtakes a write. An object too large for one frame (a key–value table of hundreds of MiB) is pushed, or fetched, in parts. A node returning after 1 % of a volume changed received 2 MiB instead of 192 MiB.

The alternative, a PG log (Ceph’s approach): keep the last operations of each PG, and replay the missing ones to a returning copy. It sends only what changed, but it is persisted state to write on every operation, crash-test, and trim, and a copy away longer than the log still needs a full comparison. Digests need no new state and cover every case with one mechanism. Their cost is a scan of the PG’s index entries (not its data) on both sides. The log will be built only if measurements on large PGs show the scan is too slow.

Scrub

Each storage node compares, every 24 hours by default (hyperstord --scrub-hours), the copies of each clean PG it leads, spread evenly over the interval:

  • Light scrub compares digests. A difference is looked at again after 200 ms, so a write in flight isn’t counted as damage.
  • Deep scrub, on the first pass after a start and every seventh, has every copy first read all its blocks and check their CRCs, at most 64 MiB/s per device. A damaged copy gets a digest that never matches, so it never counts toward a majority.
  • Repair by majority: if the primary’s copy is in a strict majority, it is pushed to the others; if another value is, the primary first pulls that copy, then pushes it. With no majority, nothing is changed: the object is reported, and cluster health warns.

When a client’s read finds a damaged block on the primary, the primary fetches the object from another copy, replaces its own and serves the read, holding writes to that object meanwhile.

Known limits

  • A slow primary is handled only for reads: a read past the read timeout is served by another copy, but writes wait for it.
  • One I/O error fails the whole device; there is no error-rate threshold.
  • Peer reports don’t yet require reporters in different failure domains.
  • Backfill is bounded by bytes in flight, not by a rate or a priority class, and the bound is per reactor and target, not per link.
  • Down times, flap holds, space reports and scrub results are kept in the leader’s memory; a new leader starts them again.

Volumes, leases and the blocklist

Volume metadata

Volume records are not in the map service. They are objects in a replicated pool of their own, .meta (pool 0: three copies where there are three nodes, 256 PGs):

ObjectContents
Header h/{id}The volume’s pool, size, lineage, state and name, a version number, a creation token; while attached, its lease (identity, client, mode and label) and delegates; in the trash, when it went there
Directory d/{pool}/{shard}The pool’s volumes, in 64 shards by id, one key–value entry each

Every change to a header is a compare-and-set on its version: an operation list that asserts the version it read, then writes the new header, decided by the header’s PG primary under a lock on the key. Creating a volume carries a token, so a retry after a lost answer is recognised rather than doubled. Create writes the header and then the directory entry; expand raises the size (never lowers it). A delete moves the volume to the trash: the header is marked with the time, and a trashed volume is neither listed nor attachable, but its data stays until it is restored or purged (after its pool’s grace period, a day by default, or at once on request). A purge marks the header deleting, removes the data, then the entry, then the header, so every step can be resumed. In a full pool, creating volumes, clones and snapshots is refused.

Why not in Raft: volume operations then scale with the number of PGs, not with one Raft group, and a Raft write is needed only for map changes. This is the pattern Ceph’s RBD uses with its header objects.

One writer per volume: leases

A client attaches a volume by taking its lease: the header’s PG primary records the holder in the header and keeps the expiry in memory. Each attach has a lease identity of its own, a random 64-bit number recorded with the holder and carried by every request under the lease, so one client’s leases can be fenced one at a time. A lease also records a short label from its holder (vhost:<node> for a VM disk, hyperstorctl for a tool), which a refused attach names, so the caller can tell a VM’s disk from a tool’s hold.

The blocklist and forced takeovers

If a holder dies or is cut off, another client must not start writing while the old one might still have writes in flight. Hyperstor uses a blocklist in the cluster map:

  1. take_over waits until the old holder’s lease has run out (up to 4 s). A holder that is still renewing is left alone.
  2. It adds the old lease’s identity, and its delegates’ (below), to the blocklist: one Raft write. The leader pushes the map and waits until every storage node has acknowledged it, or 1.25 map leases have passed (after which a node that didn’t acknowledge has stopped serving).
  3. It takes the lease.

From then on every storage node refuses requests under the old lease, checked again just before a write is queued, so none of its writes lands after the new holder’s; the old holder’s other volumes go on. Fencing a whole client is the same with its instance, which every connection names at Hello. preempt does the same for a live holder, for example when glidex finds a disk still held by a node its VM no longer runs on: it blocklists first, then waits out the lease. A forced delete preempts the holder and moves the volume to the trash while holding its lease. Blocklist entries expire after an hour.

Delegates act under a holder’s lease from another client: the holder records their identities in the header, they renew nothing, and they are blocklisted with the holder, before the holder detaches, and when the holder removes one. A snapshot’s quiesce waits for each.

Why a blocklist, not a token checked on every write: checking a lease token against the header on every write adds work to every write and state to every copy. Requests do carry the lease identity, but only to look it up in the blocklist, which costs nothing on the write path that could be measured, and one Raft write per takeover. Ceph uses the same approach for RBD exclusive locks.

Why an identity per lease, not per client: one hyperstor-vhost serves every VM of its node through one client. Fencing the client took every disk off the node to move one. With an identity per lease, the connection stays shared and only the lease taken is fenced. Only client connections are checked: a primary forwards its client’s request to its copies, and a copy must not refuse a write its primary accepted.

A forced takeover takes one volume lease, about 4.0 s; a preemption about 3.8 s.

Snapshots and clones

Versions by epoch

A volume has a head epoch. Each chunk write creates or updates the chunk’s version at the head epoch: a separate engine object, named by the chunk and the epoch. A snapshot is one compare-and-set on the header that records the current epoch as a snapshot and moves the head epoch on. Nothing is copied, and storage nodes take no part in the cut: the next write to each chunk simply starts a new version, which holds only the blocks written since (redirect-on-write).

A read at the head goes through layers: the chunk’s versions from newest to oldest, and the primary takes each block from the first version that has it. A snapshot reads the versions up to its own epoch.

Pausing the writer

If a client has the volume attached, its writes in flight must be on the right side of the cut. The holder keeps one long-poll Watch request open on its header’s primary. To take a snapshot, the primary tells it to quiesce: it pauses new writes, drains those in flight, answers, and after the compare-and-set resumes at the new epoch. If it doesn’t drain within 2 s, the snapshot is abandoned (Busy) rather than stall the volume. Why a watch: news carried by the 1 s lease renewals could take most of a second to arrive; the watch costs milliseconds plus the drain.

A consistency group holds every member’s writer with one token, snapshots each under its hold, then releases them all and marks the group complete; on any failure it deletes the snapshots taken and releases the holds.

Clones, branches and rollback

A clone is a new volume on a new branch of the same lineage: its chunk versions carry its branch number, and it reads through its own branch first, then the snapshot’s chain. Sharing the lineage keeps a clone’s chunks in the same PGs as its parent’s, so a read that falls through stays on the same devices. A lineage object records every branch and what it reads, so a snapshot that something still reads can’t be deleted. Flatten copies into a clone what it still reads from its parents, so it no longer depends on them.

A rollback to the newest snapshot of the head’s branch is done in place: the header moves the head epoch on and records the epochs since the snapshot as skipped, so reads skip them at once, and their versions are deleted afterwards. A rollback to an older snapshot makes a new branch. Why in place: agent VMs are reset to a clean snapshot after every task. A new branch per reset would add a level to the read chain each time, and the chain is limited to 16 levels; in place, the chain never grows.

Deleting a snapshot

When nothing between them reads it, a snapshot’s versions are merged into the next newer ones with the engine’s Absorb: the newer version takes the blocks it lacks, by reference, and the older is deleted, in one log record. No data is copied. Versions nothing reads are deleted outright. Why: deleting snapshots is the hot background job when VMs are reset after every task; this way it costs index work, not device I/O.

The host read cache

Every client keeps an LRU cache of 4 KiB blocks in memory (256 MiB by default; 0 turns it off). It holds only blocks of versions that can no longer change: a block read from a version other than the volume’s head (a snapshot’s, or a clone’s parent’s). Why no invalidation: versions are never rewritten, epochs never reused, and a merge only adds blocks a version lacked, so an entry never goes stale. Entries are keyed by lineage, the lineage’s random incarnation (so a volume deleted and made again never matches), branch, epoch, chunk and block.

  • Each read answer names the version each block came from. An attached volume remembers that source per block until it writes the block or its header changes; a read that overlapped a write records nothing.
  • When the cache holds blocks of the lineage and a read’s sources aren’t known, the client first asks the primary for them alone, without the data. If every block comes from a cached version, the read is served from memory; otherwise it is read as usual.

Why ask first: clones of one golden image then share what any of them has read, for one small round trip per miss, asked only once the lineage is cached. Not built yet: serving the cached part of a read that also needs head blocks (such a read fetches everything), a second tier on local NVMe, and measurements on hardware.

512e. Guests and their boot loaders expect 512-byte sectors, while a volume stores 4 KiB blocks with a CRC each. A read of part of a block reads the whole block and returns the part. A write takes a lock on the range of whole blocks it touches, and, when it starts or ends inside a block, reads that block, merges and writes the span. Reads take no lock: a read racing a write may see either, as on any disk. Without the lock, two writes into one block’s sectors lose one of them; a test checks it.

Flush is answered at once: a write is acknowledged only once every copy has it durable, so the disk has no volatile cache to flush.

Held writes. virtio-blk has no “no space” status, and an I/O error can turn a guest’s filesystem read-only. So hyperstor-vhost tries a write refused for space again every second, up to --hold-full (60 s by default), while trash is purged or a device added. Each try reads the data from guest memory again, which stays the guest’s until the request completes, so the usual path copies nothing more.

Restarts. Stopping hyperstor-vhost doesn’t detach its volumes. A state file in the runtime directory names its client and each volume’s lease identity and serial; the next start takes each lease back from that identity (waiting out the lease, about 4 s) and opens the sockets again, and the hypervisors reconnect. Requests the guest had in flight are found in the hypervisor’s in-flight buffer (a shared memory region where each request is marked when taken and cleared when answered) and run again. Why the runtime directory: after a reboot, no VM uses the volumes, and their leases should lapse, not come back. A volume another node took meanwhile is left to it. One taken while the service runs is listed as lost, its I/O failing, until it is attached afresh.

For glidex. Hyperstor’s side of glidex’s driver is built: hyperstor-vhost’s control socket (one JSON request per line: attach, with the node’s name as the lease’s label; detach; list); a management identity enrolled with a single-use join token (hyperstorctl enroll); expand-volume; and hyperstorctl write-volume and read-volume for images (--sparse skips zero blocks). The label is what lets a driver starting a VM preempt a disk still held by another node’s hyperstor-vhost after a crash or a failed detach, fencing only that lease, while it waits for a tool’s hold.

glidex’s driver is built on these: a disk on a hyperstor datastore is a volume, blank, filled from an image, or a linked clone of the image volume’s golden snapshot, grown to the disk’s size; the VM’s node stages it through its hyperstor-vhost, and Cloud Hypervisor or QEMU connects over vhost-user-blk. A deleted disk’s clone waits in the trash, keeping the image volume it reads from; glidex deletes leftover image volumes once their image is gone and the clone is purged. Metering of hyperstor disks in glidex is still to come.

Planned

  • Read-only attachments of snapshots, by several clients at once, with reads from any copy.
  • Discard and write-zeroes that allocate nothing: discard can’t simply unmap the head’s blocks, or a read would fall through to a snapshot’s, so it needs a “zeroed” marker in the head version.
  • Telling a running guest its disk grew (virtio’s config-change event); today it sees the new size at its next attach.
  • In hyperstor-vhost: queues on several reactors, one per NUMA node, adaptive polling, and zero copy from guest memory.
  • A delegate’s identity handed to a guest over virtio-vsock.

Design decisions and trade-offs

Each section lists a decision, why it was made, and what was weighed against it. Status says whether it is built; the Status page has the final word.

Data path and runtime

Pure Rust on io_uring, with no SPDK or DPDK
DecisionEvery storage core runs Hyperstor’s own reactor on io_uring. NVMe stays on the kernel’s driver (passthrough through uring_cmd is planned); the network goes through kernel sockets, and later RDMA verbs
WhyOne language and one build, with no C framework in the data path. Devices aren’t unbound from the kernel, so lsblk, SMART, partitions and the rest of the host keep working, and no DPDK process competes with the host’s virtual switch. Idle cores sleep instead of polling. The client library can be embedded in any program. Owning the loop puts disk, sockets, RDMA and virtqueue polling in one place
AlternativesSPDK and DPDK, used by Mayastor, Longhorn’s V2 engine, simplyblock and DAOS: the fastest path today, but they take devices and NICs from the kernel, need huge pages, and poll whole cores. tokio: multi-threaded work stealing moves tasks between cores. glommio, monoio, compio: thread-per-core io_uring runtimes, but each would own the loop that RDMA and virtqueues must share
CostSome per-core speed against SPDK, to be measured on NVMe hardware; an NVMe-oF target of its own (planned)
StatusBuilt; the comparison with SPDK is still to run

tokio only on the control path

Raft, the cluster API, the installer and the CLI use tokio, on threads of their own, and pass changes to reactors over channels. They need TLS, HTTP/2 and gRPC, and none is latency-critical. Running openraft on the reactor was rejected: a runtime adapter would be large and risky for no gain.

A device wait never holds a reactor
DecisionThe engine plans an operation in memory, submits its device I/O on the reactor’s own io_uring, returns to the reactor, and finishes when the completions arrive. It comes in stages: commits first (one in flight per device), then reads (up to 128 in flight per device), then checkpoint slices and in-place writes
WhyA reactor waiting on its device answers no pings. On a three-host test cluster, a flush of 100–200 ms or a 1 MiB read held a reactor long enough for peers to report a healthy node silent. The same submission path is what NVMe passthrough needs
AlternativesAn engine thread per device: a hop per operation, and threads off the reactors’ cores. Pings on a thread of their own: a stuck reactor would look alive
Rules that come with itA commit’s writes and flush get 30 s (hyperstord --io-timeout-secs), as Linux gives an NVMe command; past that the device is failed and its PGs placed elsewhere. Without it, a hung device would no longer stop its node’s pings and would hang unseen. A read gets 2 s (--read-timeout-ms); past that the primary serves it from another copy, and three in a row fail the device. Space a commit frees while reads are in flight is held until those reads end, so a read never sees its blocks reused
StatusCommits and reads are on main and in testing; checkpoint slices and in-place writes are next

A custom framed protocol between nodes

Every frame has a 32-byte header with its own CRC32C; block data travels after the body with a CRC per block. Every request carries the map and PG epochs, and the lease it acts under (see fencing one volume). Alternative: NVMe-oF between nodes, which would need reservations and vendor commands for fencing. NVMe-oF is planned as a front end for clients instead.

Redirect-on-write on flash, deferral only on hard disks

See the data path. Deferral everywhere was the first design; measurement showed it cost about a third of batched 4 KiB write throughput on flash (85k against 133k writes per second at batch 128).

Cut CPU per operation before adding RDMA

Software costs 40–90 µs per request today, more than a TCP round trip on a fast network. Polling for 200 µs after each request took QD1 writes from 109 to 84 µs. Shorter polling (50 µs) gets about half the gain; it is the option for power-limited or shared-core hosts.

Devices name themselves, and carry feature flags
DecisionEach device’s superblock records its device id and cluster id, and a node checks them before opening it. The superblock carries compatible, read-only-compatible and incompatible feature flags, as ext4 and XFS do. Only a blank device is ever formatted: a newer format or a damaged superblock is refused, not taken for blank. The installer formats block devices, and only those with no other system’s signature (partition table, LVM, md RAID, Ceph, a filesystem); hyperstord formats files only. Device ids are never given again
WhyNVMe names can change at boot, and a drive moved between hosts or clusters must not be served as another. Flags let later format changes (an on-device index, encryption) reach a running cluster one device at a time: an older build refuses a device it can’t read instead of misreading it. Before, a newer format or two damaged superblock copies read as blank and would have been formatted
StatusBuilt

Protection and placement

Its own object store, not per-device volumes

Every device is an extent store of general objects with attributes and key–value tables, like Ceph’s RADOS with its object maps. Alternative: a thin volume manager per device (LVM-thin, SPDK logical volumes): every snapshot would then need coordination across replicas, and erasure coding doesn’t fit it.

4 MiB chunks, rendezvous hashing, placement by lineage

See placement. Alternative: CRUSH, which moves more data for erasure-coded pools and needs tuning.

A device’s weight is its capacity
DecisionThe map service sets each device’s weight, in TiB, from the size the device reports. A new report changes the map only when it differs by more than 1 %. An operator can pin a weight (hyperstorctl weight) until it is set back to auto. A change moves its PGs at once, under a per-target backfill budget
WhyEvery device used to join with weight 1, so a small device filled first. Capacity by default needs no step to forget; the override covers a slower drive or a slow drain. The 1 % threshold keeps reports every 5 s from churning the map
AlternativesA balancer that sets a second weight from how full each device is (Ceph’s crush-compat): added only if a device reaches nearfull while its class has room. Per-PG overrides in the map (Ceph’s upmap): not used, so placement stays a pure function of the map’s weights
StatusBuilt

Pools grow and shrink with their devices
DecisionA pool names a set of device classes and places on any device of them, by capacity. Devices can be added to a running node (the installer registers and formats the device, then restarts the node), and added to or removed from one pool. A device is removed only after its PGs have moved, and its node with its last device. A pool’s PG count grows by splitting PGs in place, then moving the new PGs a few at a time; the map service doubles a pool’s count as devices are added, unless that is turned off. A pool’s copies or layout change only by making a new pool
WhyStorage is bought and retired over a cluster’s life; a pool fixed at creation would strand both. A split moves objects to their new PG’s key without copying, and the new PGs start on their parent’s devices, so no data moves twice (Ceph splits the same way). Changing copies in place would rewrite every PG under running volumes, for a need a new pool meets
LimitsHard disks and flash don’t share a pool unless forced, because a replicated write waits for its slowest copy. A pool that holds data is deleted only when forced, after a dry run lists what goes with it. PG merges come later, and only by the operator. Adding a device restarts its node for now; starting a reactor in a running node comes later
StatusBuilt, apart from parts of adding a device to a running node, which are in progress

A pool’s usable space follows its failure-domain rule

Every device reports its data region and free bytes to the map service every 5 s, beside its heartbeat and outside the replicated map: space changes all the time and decides no placement. A pool’s usable space counts no failure domain for more than one copy of each PG, so with as many hosts as copies, the smallest host bounds the pool. Alternatives: a plain sum divided by the copies, which overstates a pool on uneven hosts; Ceph’s MAX AVAIL, limited by the device that fills first, which jumps when one device runs ahead.

Fullness is measured on each device
DecisionThree cluster-wide ratios in the map: nearfull (85 %) warns, a device past backfillfull (90 %) takes no new backfill, and a device past full (95 %) refuses what would grow its used space: new objects and writes to unwritten blocks. Overwrites, deletes and discards go on. A pool is as full as the fullest device it uses; a full pool takes no new volumes, clones or snapshots. Each change shows in health and in the audit log
WhyA thin pool that runs out must still let the operator free space. The device is what runs out, and it knows at once, with no map change in between. Pools share devices, so a per-pool ratio would have no single meaning, and stopping a whole pool (as Ceph does) would stop every pool on the device. Refusing creations shows the problem to an operator before a guest’s write fails. Recovery must not fill the survivors until their own writes stop
For VMsvirtio-blk has no “no space” status, and an I/O error can turn a guest’s filesystem read-only. hyperstor-vhost holds such a write and retries it every second for up to 5 minutes (--hold-full), so space freed in time (trash purged, a device added) lets it finish. Pausing the VM, as QEMU’s werror=stop does, waits until holding proves too short. hyperstor-ublk answers ENOSPC at once
The trashA pool can be set to purge its oldest trash when full (trash settings --on-full purge); the default keeps it
StatusBuilt

A device deletes copies it no longer serves

Once a PG has been clean without a device (every member live, and the device in neither its up nor its acting set) for a minute, at one epoch, the device deletes its copy of that PG, a batch at a time. Why: every rebalance, drain or weight change used to leave the old copies for ever, and a device could reach full with data nothing serves. The grace keeps a copy through a quick change back, and waiting for a clean PG keeps every copy recovery could still need. A deleted pool’s data goes the same way.

Erasure coding through a replicated log (planned)

Small writes to an erasure-coded pool go to a three-copy log and are written out as full stripes later; full-stripe writes skip the log. Why: replica-like write latency, with no read-modify-write in the foreground.

Cache pools for data that can be recomputed

A third pool kind beside replicated and erasure-coded: one copy, no recovery, evicted by expiry then least recent use (eviction is planned). Why: replicating an inference engine’s offloaded KV cache wastes bandwidth on data that can be recomputed. Alternative: a replicated pool with one copy, which would still pay for recovery.

A cache pool keeps its data across PG splits and restarts: each cache PG has a generation in the map, and a device drops its copy only when the generation has moved. A cache PG whose copies are all on down nodes waits for them for the pool’s grace (60 s by default, --cache-grace): reads miss meanwhile, and a write ends the wait for its PG. Why: a node is marked down after 0.8 s, and a restart takes seconds. Reads miss rather than wait, so nothing stalls on a cache; a write can’t be skipped without leaving the returning copy stale.

Encryption at rest (designed, not built)

Chosen per pool and done on the PG’s primary before it replicates, with AES-256-XTS and a key per volume branch, wrapped by a cluster key. Why on the primary: every copy then holds the same ciphertext, so backfill, digest comparison and scrub work unchanged. Alternatives: keys per device, or dm-crypt under the engine, which would break digest comparison between copies; encrypting in the client, which costs the GPU-direct path and later storage-side work. Deleting a key makes a purge or a tenant’s removal final.

Volume metadata in header objects, not in Raft

Failover in about one second

Map lease 0.6 s, down after 0.8 s, heartbeats every 100 ms, peers report after 0.3 s. Measured: 0.66 s of I/O gap when a primary dies, against 2.5–3.1 s with the first 2 s / 3 s timings. Trade-off: more heartbeat traffic, and a higher risk of a false failure on a busy network. On a three-host cluster over 1 GbE under load, the only silences seen came from lost packets on TCP pings; the timeouts stay where they are until they have been measured on faster networks.

Peers report each other, pinged over UDP

A node is marked down early on reports from two peers. Alternative: detection by the map service alone, which waits for the full timeout.

Peers ping each other over UDP, on each device’s TCP port number, with a nonce each pong echoes; a peer that never answers over UDP keeps TCP. Why: on TCP, one lost ping or pong waits for the 200 ms retransmission timeout, and the pings behind it with it: that caused the 300–400 ms silences seen under load. Over UDP a lost ping costs only its own 100 ms slot. The TCP fallback needs no coordination during a rolling upgrade, and a firewall that drops UDP leaves pings on TCP rather than silent.

A node that flaps is held down

The map service brings a node marked down back up only after a hold: 2 s, doubled for each further down within 10 minutes, at most 60 s. Health warns while a node flaps. Why: a node whose reactor stalled past the peer timeout went down and up about 150 times a minute on a test cluster, and every change bumped the map and shrank or refilled PGs. A down node is something the cluster handles; the warning says someone should find out why.

Recovery

No PG log: peering and recovery by content digests

See peering. The log comes only if digest scans prove too slow on large PGs. Large key–value tables are digested in 1 MiB parts with a yield between, so one object can’t hold a reactor.

A primary drops a slow copy from one PG

Alternative: leave it to liveness detection, which can’t see a hung disk on a live node.

Backfill is budgeted per target

A reactor’s backfills to one target keep at most 16 MiB of pushes on the wire, objects too large for one frame go in parts, and pings travel apart from data. Why: an empty node rejoining got a backfill of every PG at once; pings and replicated writes waited behind hundreds of MiB, and the cluster flapped. Alternative: a cap on PGs backfilling at once, which also stopped it but kept PGs at one copy longer.

The fault-injection rig runs in process

Alternative: a rig across hosts with traffic control, network namespaces and delayed devices: it needs root on test hosts, and its failures don’t replay exactly. The device timeouts were also checked by hand on a real kernel device slowed with dm-delay.

The log is a sixteenth of the shard, up to 1 GiB: checkpoints then write 52 MB/s per TiB instead of 207, and replay takes up to about 3 s. Alternative: a 4 GiB log, which means about 11 s of recovery.

Front ends

Its own ublk server, on the reactor

hyperstor-ublk serves volumes through the kernel’s ublk driver. Each queue command is a uring_cmd on the same reactor that runs the client, so requests never cross runtimes. Alternative: the libublk crate, which runs each queue on its own io_uring and runtime. Status: built.

VM disks over vhost-user-blk, one service per host
Decisionhyperstor-vhost serves volumes to Cloud Hypervisor and QEMU over vhost-user-blk, one service per host, sending each chunk’s I/O straight to its PG’s primary. It takes rust-vmm’s vhost, virtio-queue and vm-memory crates as libraries and drives them from its own reactor; each queue is a task waiting on its kick eventfd
WhyOne hop from the guest’s queue to the storage node, with proven protocol and ring code and no second event loop on the data path
AlternativesA kernel NVMe-oF initiator, which adds a hop through a gateway. rust-vmm’s vhost-user-backend daemon, which runs an epoll thread per queue
StagingA scheduler attaches and detaches disks through a local control socket (one JSON request per line, the caller’s uid checked). Creating, expanding and deleting volumes go to the cluster API. Staging is local to the host, so it doesn’t depend on reaching the cluster API
RestartsStopping the service keeps its volumes: a state file names them, and the next start takes each back, only from its own previous lease, so a volume moved meanwhile is never stolen. Requests in flight are tracked in the hypervisor’s in-flight buffer and run again after a restart; without it, a guest waited for ever on requests the old process had taken. Both hypervisors reconnect to the restarted service (QEMU when told to)
512e disks512-byte logical sectors on 4 KiB physical blocks. Cloud images keep their partition table in 512-byte sectors and firmware looks for the GPT at sector 1, so a 4 KiB-sector disk doesn’t boot them. A partial block is read, merged and written back under a per-volume block lock; guests align filesystem I/O to the physical block, so this is rare. Rejected: a block size per volume, and converting images
StatusIn progress: VMs boot from volumes under both hypervisors, and restarts keep their disks. Adaptive polling, queues on reactors per NUMA node and zero copy from guest memory are planned

The host read cache lives in the client library

Each client keeps an in-memory cache (256 MiB by default) of blocks from versions that can never change: snapshots, and the parents that clones read through. The head of a volume is never cached. Why: such data needs no invalidation, so the cache needs no protocol; and in the client, hyperstor-ublk and hyperstor-vhost both get it. It serves the common heavy readers: many VMs booting clones of one image, or loading the same model weights. Status: in progress; a second tier on local NVMe comes later.

NFS and pNFS: a settled direction, the rest proposed

Settled: Hyperstor will serve unmodified NFSv4.1 and 4.2 clients with a server of its own in Rust, on the reactor, with pNFS data servers inside the storage nodes and file data placed in stripe groups of consecutive PGs. Why: with no gateway on the data path, a pNFS write reaches the primary in one hop, under the same leases and fencing. Alternatives: NFS-Ganesha (C through FFI, its pNFS unmaintained) and the kernel’s nfsd (no usable layout for an object store). The layouts, state handling and build steps are proposals; nothing is built, and it comes after the filesystem.

  • Opening a shard (replaying its log) takes as long as before.

Comparison with other systems

Hyperstor is early. Today it has replicated pools that grow and shrink with their devices, the replicated map service, failure handling, recovery, scrub, volumes with leases and per-volume fencing, snapshots, clones and consistency groups. Volumes are used as VM disks over vhost-user-blk (Cloud Hypervisor and QEMU), as ublk block devices, or through a Rust client library. Administration has a CLI and a web UI with logins, roles, a trash, an audit log and long operations. Erasure coding, NVMe-oF for remote hosts, RDMA, GPU-direct, S3 and the filesystem are designed but not built, and NFS is a proposal. The systems below are mature products; this page compares designs, and says where Hyperstor is behind.

System by system

Ceph

The closest relative: Hyperstor shares its model of placement groups, a primary per PG, map epochs, min_size, header objects for volumes and a blocklist for exclusive locks.

  • Different pieces: rendezvous hashing instead of CRUSH, Raft instead of Paxos monitors, and content digests instead of the PG log (why).
  • Map leases: a cut-off primary stops within one 0.6 s lease, and the same lease makes primary reads safe.
  • The data path Ceph is moving to: Crimson rebuilds the OSD as thread-per-core on Seastar. Hyperstor started there, on io_uring without Seastar or SPDK.
  • Snapshots: Hyperstor deletes a snapshot by handing its blocks to the newer version in one log record, without copying data, and resets a volume to its newest snapshot in place, which suits VMs reset after every task.
  • Fullness: both use the same three ratios with the same defaults (nearfull 85 %, backfillfull 90 %, full 95 %). In Ceph, an OSD past full stops client writes; Hyperstor refuses only what would grow a full device, so overwrites and deletes go on, and its pool space counts each failure domain once, which doesn’t jump when one device runs ahead (why).
  • Behind: Ceph has erasure coding, S3, a filesystem, multi-site replication and years of production at scale. Hyperstor has none of these yet.

Longhorn and OpenEBS Mayastor

Kubernetes-native block storage. Both replicate whole volumes: Longhorn with an engine per volume, Mayastor through a “nexus” on SPDK.

  • Sharding: Hyperstor cuts every volume into chunks over all PGs, so one volume spreads its load and its recovery over the whole cluster.
  • Kernel bypass: Mayastor and Longhorn’s V2 engine take devices from the kernel with SPDK and poll whole cores; Hyperstor keeps the kernel driver and sleeps when idle, and has yet to show how close it gets to SPDK on NVMe.
  • Behind: both ship NVMe/TCP, Kubernetes integration and backups today. Hyperstor has a web UI and VM disks, but none of those three.

LINSTOR and DRBD

DRBD replicates a block device in the kernel; LINSTOR places resources across nodes. Very low latency on two or three nodes, and decades of production.

  • Different scale model: DRBD’s unit is a whole device on a fixed set of nodes; Hyperstor’s is a 4 MiB chunk placed by hash, so data and recovery spread over every node.
  • Fencing: DRBD uses quorum and tiebreakers; Hyperstor uses map leases for primaries and volume leases with a blocklist for clients.

Portworx

Enterprise Kubernetes storage. Its internal key–value store can be down while I/O goes on, with volume operations blocked. Hyperstor’s map service is off the I/O path too, but storage nodes stop after one map lease without it: that is the price of bounding a stale primary, which is why the map service runs as three or five members.

Lightbits and simplyblock

NVMe/TCP block storage: Lightbits with its own userspace target, simplyblock on SPDK with erasure coding first. Both ship what Hyperstor plans: an NVMe-oF target and erasure-coded pools. Hyperstor’s difference is the same object layer under VMs (vhost-user-blk, built, without NVMe-oF in between) and, planned, GPU-direct reads, S3 and a filesystem.

DAOS

An object store for HPC and AI, with Raft-replicated services and key–value semantics close to Hyperstor’s object layer. It depends on SPDK and libfabric, and targets POSIX and MPI-IO. Hyperstor is block first for virtual machines, on io_uring and RDMA verbs.

WEKA and VAST Data

Parallel file and object systems for AI, both on NVIDIA’s GPUDirect Storage list. WEKA bypasses the kernel with DPDK; VAST separates stateless servers from shared flash enclosures and protects data with very wide codes.

  • GPU-direct: Hyperstor plans to keep the cuFile and hipFile APIs but move data by RDMA straight into GPU memory registered through dma-buf, which works for NVIDIA and AMD GPUs alike, in one hop to the storage node. Unmodified GDS programs keep a kernel NVMe-oF path. None of this is built.
  • Behind: both are qualified and in production for GPU clusters.

MinIO AIStor

S3 object storage. AIStor ships S3 over RDMA (the x-amz-rdma-token extension) into GPU memory. Hyperstor plans the same extension on its S3 gateway, with the transfer made by the storage nodes that hold the data, so the gateway stays off the data path.

The control socket takes one JSON request per line and answers each on one line:

{"id": 1, "op": "attach", "args": {"volume": "<32 hex digits>", "serial": "vm-disk", "take": "attach"}}
{"id": 1, "ok": {"socket": "/run/hyperstor/vhost/<id>.sock", "size": 21474836480}}

Errors are {"id": N, "error": {"code": C, "message": M}}, with codes invalid, denied, held, not_found, not_attached, unavailable and internal. An attach may name who asks, "holder": "<name>" (up to 58 printable characters; glidex gives its node’s name): the lease is labelled vhost:<name> (vhost without one). A held error names the label of whoever holds the volume, "holder": vhost:<name> for another node’s service, hyperstorctl for a tool.

Restarts

Stopping or restarting the service doesn’t detach its volumes. It keeps them in DIR/state.json, and its next start takes them back and opens their sockets again; the hypervisors reconnect and the guests carry on, after a pause of about 4 s. Requests the guest had in flight are run again from the hypervisor’s in-flight buffer. Cloud Hypervisor reconnects by itself; give QEMU’s chardev reconnect=1 (QEMU 9.2 and later: reconnect-ms=1000). A volume another node took while the service was down is left to it.

The state file is in the runtime directory: a reboot clears it, and with it the VMs that used the volumes. To stop the service for good, detach its volumes first (ctl detach); a stopped service’s volumes stay held. hyperstor-install uninstall and --no-vhost do this.

hyperstor-install --vhost installs it as hyperstor-vhost.service (see hyperstor-install).

The root CA’s key. Deleting a volume, a snapshot or a member, rolling a volume back, purging the trash or changing its grace period, changing how long the audit log is kept, making a join token or an API token, revoking a certificate, fetching a map backup, and changing people’s roles need a login of the last 10 minutes; an API token is never fresh enough for these.

The first security administrator. While no one is one, the service prints a claim code to its log (journalctl -u hyperstor-mgmt), valid for an hour: whoever logs in with it becomes the first. Restarting the service prints a new one while the cluster is unclaimed.

Sessions last 12 hours, or 30 minutes idle. They are kept, with accounts and tokens, in the map service’s store, so they outlive a restart of hyperstor-mgmt.

Protections

  • It answers only requests whose Host is one of its names on its port (against DNS rebinding).
  • The session cookie is HttpOnly; SameSite=Strict (and Secure over HTTPS). A write with the cookie must send its CSRF value in X-Hyperstor-CSRF, and a write from another site’s Origin is refused.
  • Pages carry a strict Content-Security-Policy and may not be framed.
  • Every login and every change is audited on standard error as a JSON line with the person (user:NAME) and how they logged in, and sent to the cluster’s audit log in .meta. mgmt names the person to the map service (X-Hyperstor-On-Behalf-Of, believed only from mgmt’s certificate), whose audit then reads …/mgmt/dashboard for user:NAME; a browser’s own such header is dropped.

Cluster API

hyperstor-meta --api ADDR serves the cluster API, hyperstor.v1, which hyperstorctl uses. One service answers the Connect protocol (JSON or protobuf over HTTP/1.1 or HTTP/2), gRPC and gRPC-Web, so any of these work: curl, grpcurl (with the proto file), generated clients.

The definitions are cluster.proto (ClusterService) and admin.proto (TokenService, CaService, NodeService, OperationService), in crates/hyperstor-api/proto/hyperstor/v1/.

Security

With --api-tls, the API speaks only TLS. Every call but Join needs a client certificate issued by the cluster’s CA, whose identity (hyperstor://<cluster>/<role>/<id>) decides what it may do:

RoleMay
admin (hyperstorctl), mgmtEverything
node, metaRead (GetStatus, ListPgs, ListVolumes, ListTokens, GetOperation, ListOperations, DrainNode with dry_run), and renew their own certificate
hostRenew its own certificate; nothing else

A certificate of another cluster is refused, and so is a revoked one: RevokeCertificate (hyperstorctl cert revoke) puts its serial on a list every map service member checks, on the API and between members, until the certificate would have expired. hyperstor-install makes the certificates in /etc/hyperstor/pki.

Joining. Join is the only call without a client certificate: a single-use token from CreateToken authorizes it. The joining host pins the cluster’s root by the fingerprint the token carries before it sends anything, and sends a certificate request for a key it keeps; the token decides the identity it gets. Tokens are kept in the map service’s replicated store, only their SHA-256, so they survive restarts and work through any member; the leader makes, uses and revokes them (another member refuses with not_leader and changes nothing). Before the map service has its first map, only its first member makes tokens, and only meta ones, for the other members to join.

Local socket. With --api-socket, the API is also served on a Unix socket (/run/hyperstor-meta/api.sock when installed). There the kernel names the caller: root, the service’s user and members of hyperstor-admin may do everything, others nothing. It is the way in when certificates are broken; its use is audited like any other.

Without --api-tls the API is plain HTTP and accepts every request: only for loopback and tests.

Audit. Every change (SetDeviceIn, SetDeviceWeight, SetFullRatios, AddDevice, RemoveDevice, SetDeviceClass, CreatePool, SetPool, SetPoolDevice, DeletePool, CreateVolume, ExpandVolume, DeleteVolume, CopyVolume, MoveVolume, the snapshot calls but ListSnapshots, CreateToken, RevokeToken, Join, RenewCertificate, RevokeCertificate, DrainNode, CancelOperation) and every refused call is written as one JSON line on the map service’s standard error, which systemd keeps in the journal:

What the answers mean

  • Reads (GetStatus, ListPgs) come from the published map: what storage nodes and clients see.
  • SetDeviceIn, SetDeviceWeight, SetFullRatios and AddDevice change the map service’s working map. The change is published once the devices losing roles have been fenced, usually within a second, and GetStatus then shows the PGs moving.
  • Health is HEALTH_ERROR when a PG can’t take writes (fewer copies than the pool’s min, or no primary), HEALTH_WARN while a node is down, a device is out, or PGs are degraded or backfilling, and HEALTH_OK otherwise. Each reason is listed. A node the map service hasn’t heard from since it started is also HEALTH_WARN: the map counts it up for a short grace period after a restart.
