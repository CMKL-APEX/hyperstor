Hyperstor

hyperstorctl

Manages and tests a cluster through the cluster API. See Managing a cluster.

Refused (exit 1) for .meta, for a name another pool has, when the pool’s devices would span fewer failure domains than its copies, and when the classes hold hard disks and flash both, unless --force, which warns (D172). pools lists each pool’s classes, ! marking a forced mix

A device serves every pool that uses it, sharing its space

Refused (exit 1) when the pool’s devices would span fewer failure domains than its copies. pools lists a pool’s classes, then +D for each device added and -D for each removed
pool deleteDeletes pool --pool P (D176, D181): it leaves the map at once, its id is never given again, and each device deletes its data within a minute or so. Refused (exit 1) for .meta and while the pool holds a volume, a snapshot or anything in the trash: delete and purge them first. --dry-run lists what it holds, deletes nothing, and exits 1 if it holds anything. --force deletes that first, as an operation: each volume, even attached (its holder is preempted), goes to the trash and is purged with its snapshots, clones before what they were cloned from, each audited; then the pool. Through hyperstor-mgmt. With --mgmt, hyperstorctl is a person, not an administrator’s certificate: make an API token on the dashboard (or POST /auth/tokens), keep it in a file only you can read, and your roles decide what you may do. What needs a fresh login (deleting, rolling back, tokens, revocations, backups) is refused with (reauth_required): do it from the dashboard, or with the certificate. The map service’s audit names you (… for user:NAME).

export HYPERSTOR_MGMT=https://the-map-service-host:8852
export HYPERSTOR_TOKEN="$(cat ~/.hyperstor-token)"
hyperstorctl status

Without --api, the address is $HYPERSTOR_API, else the api line of /etc/hyperstor/hyperstorctl.conf (written by hyperstor-install), else 127.0.0.1:8850. Likewise, without --tls the certificates are those of the tls line in that file, if any; with neither, it uses plain HTTP.

On the map service’s host, when neither --api nor --tls is given and the configuration’s socket line names a socket that exists, hyperstorctl uses that local socket: the kernel tells the map service who is calling, and root and members of the hyperstor-admin group may do everything. This keeps working when certificates have expired or are lost. Elsewhere it uses the API address and the administrator certificate, which root and hyperstor-admin can read.

io-test reaches the storage nodes as a client would: it asks the API where the map service is, then writes and reads through the client library. It prints the time and throughput of each phase.

A refused request prints the API’s message and its reason, a stable word for scripts such as (not_found), (token_used) or (not_leader); the cluster API lists them.

Exit statusMeaning
0Done; for status, health is ok
1status: health is warn or error. Otherwise a failed request (no such device, pool or operation), a failed or cancelled operation, or a failed io-test
2A missing or malformed option, or certificates that can’t be read
3The cluster API (or, for io-test, the map service) can’t be reached, or the map service member asked isn’t the leader
4Not allowed: no certificate, or one whose role may not do this
